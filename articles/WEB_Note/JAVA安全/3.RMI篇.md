# 1. RMI的基本角色

>Remote Method Invocation，远程⽅方法调用

Java独有的一种机制，让某个Java虚拟机上的对象调用另一个Java虚拟机中对象上的方法

一个完整的RMI过程通常包含<u>三个参与者</u>：

- **RMI Registry**（注册表）：远程对象的注册表，只保存名字到远程对象引用的绑定关系
- **RMI Server**（服务端）：真正导出远程对象、执行远程方法的服务端
- **RMI Client**（客户端）：通过 Registry 查询对象引用，再调用远程方法的一方

<img src="/assets/images/web-note/web-note-024.png" alt="RMI" style="zoom: 25%;" />

```
RMI Registry就像一个网关，他自己是不会执行远程方法的，但RMI Server可以在RMI Registry上注册一个Name到对象的绑定关系；
RMI Client通过Name向RMI Registry查询，得到这个绑定关系，然后再连接RMI Server；
最后，远程方法实际上在RMI Server上调用。
```

---

**代码演示：**

首先编写一个**RMI Server**

> [!NOTE]
>
> 为了让客户端知晓有哪些方法可以调用，<u>远程调用函数</u>必须定义在继承了 `java.rmi.Remote` 的接口中 

```java
package org.vulhub.RMI;

import java.rmi.Naming;
import java.rmi.Remote;
import java.rmi.RemoteException;
import java.rmi.registry.LocateRegistry;
import java.rmi.server.UnicastRemoteObject;

public class RMIServer {
    // 1. 定义远程接口，必须继承 Remote，方法必须抛出 RemoteException
    public interface IRemoteHelloWorld extends Remote {
        public String hello() throws RemoteException;
    }

    // 2. 接口实现类，继承 UnicastRemoteObject
    public static class RemoteHelloWorld extends UnicastRemoteObject implements IRemoteHelloWorld {
        protected RemoteHelloWorld() throws RemoteException {
            super();
        }
        @Override
        public String hello() throws RemoteException {
            System.out.println("call from client");
            return "Hello world";
        }
    }

    private void start() throws Exception {
        RemoteHelloWorld h = new RemoteHelloWorld();
        // 创建并运行 RMI Registry 监听在 1099 端口
        LocateRegistry.createRegistry(1099);
        // 将远程对象绑定到 URL 路径上
        Naming.rebind("rmi://127.0.0.1:1099/Hello", h);
    }

    public static void main(String[] args) throws Exception {
        new RMIServer().start();
    }
}
```

该RMI Server可分为三部分：

1. ⼀个继承了 `java.rmi.Remote` 的**接⼝**，其中定义要远程调⽤的函数，⽐如这⾥的 **`hello()`**
2. ⼀个**实现**了此接⼝的**类**
3. ⼀个**主类**，⽤来创建Registry，并将上⾯的类实例化后绑定到⼀个地址。———Server

然后编写一个**RMI Client**

```java
package org.vulhub.Train;

import org.vulhub.RMI.RMIServer;
import java.rmi.Naming;

public class TrainMain {
    public static void main(String[] args) throws Exception {
        // 使用 Naming.lookup 在 Registry 中寻找对应名字的对象
        RMIServer.IRemoteHelloWorld hello = (RMIServer.IRemoteHelloWorld) 
            Naming.lookup("rmi://192.168.135.142:1099/Hello");
        // 像本地对象一样调用远程方法
        String ret = hello.hello();
        System.out.println(ret);
    }
}
```

客户端就简单多了，使⽤ Naming.lookup 在Registry中寻找到名字是Hello的对象，然后就可以像本地对象一样调用远程方法

---

上面的常见示例里看起来只有 Server 和 Client，是因为 Server 代码经常同时创建 Registry 并绑定对象，例如：

```java
LocateRegistry.createRegistry(1099);
Naming.rebind("rmi://127.0.0.1:1099/Hello", remoteObject);
```

这里第一行启动 Registry，第二行把远程对象绑定到 `Hello` 这个名字上。

## RMI调用流程

>先找 Registry，再连 Server

客户端通常通过：

```java
Naming.lookup("rmi://192.168.135.142:1099/Hello");
```

向 Registry 查询名为 `Hello` 的对象。Registry 返回的不是直接执行结果，而是一个序列化后的远程对象引用。客户端反序列化后得到远程对象的 Stub/Proxy，其中包含真正 RMI Server 的地址和端口，然后客户端再新建 TCP 连接去调用远程方法。

![一次 RMI 调用中的两条 TCP 连接](/assets/images/web-note/web-note-025.png)

抓包里可以看到两段关键通信：

1. 客户端连接 Registry 的 `1099` 端口，发送 `Call` 请求。
2. Registry 返回 `ReturnData`，其中包含远程对象引用，例如 `UnicastRef` 里的服务端 IP 和动态端口。
3. 客户端再连接这个动态端口，真正执行 `hello()` 等远程方法。

RMI 底层数据流中经常能看到 `0xAC ED`，这是 Java 序列化流的魔数。也就是说，RMI 的很多关键数据传递都建立在 Java 序列化/反序列化之上。

## 3. RMI Registry 的攻击面

当攻击者能访问目标 RMI Registry 时，首先会想到能否远程修改绑定关系，例如调用 `bind`、`rebind`、`unbind`。但 Java 对这些敏感操作做了来源限制：只有本地 `localhost` 来源才能执行这些方法。

![远程 rebind 被 Registry 拒绝](/assets/images/web-note/web-note-026.png)

不过，`list` 和 `lookup` 是可以远程调用的：

```java
String[] names = Naming.list("rmi://192.168.135.142:1099");
Object obj = Naming.lookup("rmi://192.168.135.142:1099/refObj");
```

因此，Registry 暴露后仍有风险：

- 可以枚举目标暴露了哪些远程对象。
- 如果远程对象中存在危险方法，攻击者可以直接调用。
- 可配合工具探测远程对象接口和可疑方法。
- 更深层的风险来自 RMI 传输过程中可控序列化数据和历史 `codebase` 机制。

## 4. codebase 远程加载机制

`codebase` 可以理解为“远程类搜索路径”。当 JVM 在反序列化对象时发现本地 `CLASSPATH` 中没有对应类，就可能根据 `codebase` 去远程 URL 下载 `.class` 文件。

例如，如果 `codebase` 为：

```text
http://example.com/
```

而 JVM 需要加载：

```text
org.vulhub.example.Example
```

那么它会尝试请求：

```text
http://example.com/org/vulhub/example/Example.class
```

在 RMI 中，客户端和服务端之间传递的都是序列化对象。如果某一端反序列化时本地找不到类，并且又信任对方传来的 `codebase`，就可能从攻击者控制的 HTTP 服务下载恶意类并加载。

## 5. codebase 任意代码执行的触发条件

文章强调，这类利用不是默认无条件可打，通常需要满足历史或特殊配置条件：

- RMI 服务端安装并配置了 `SecurityManager`。
- Java 版本低于 `7u21` / `6u45`，或者显式设置：

```text
java.rmi.server.useCodebaseOnly=false
```

`java.rmi.server.useCodebaseOnly` 在 Java `7u21` / `6u45` 后默认改为 `true`。当它为 `true` 时，JVM 只信任本地预配置的 `codebase`，不再信任 RMI 请求中传来的远程 `codebase`。

一次复现流程可以概括为：

1. RMI Server 导出一个远程对象，例如 `ICalc.sum(List<Integer>)`。
2. 客户端传入一个服务端本地不存在的自定义类，例如 `RMIClient$Payload`。
3. 客户端启动时指定恶意 `codebase`。
4. 服务端反序列化参数时本地找不到该类，于是访问 `codebase` 下载 `.class`。
5. 如果下载的是恶意类，就可能触发代码执行。

![服务端尝试加载 codebase 类但 class 内容不合法](/assets/images/web-note/web-note-027.png)

从 Web 日志中可以看到 JVM 会去请求对应的 class 文件：

![JVM 从 codebase 请求 RMIClient$Payload.class](/assets/images/web-note/web-note-028.png)

关键点不是 `magic value` 错误本身，而是错误证明了服务端确实根据 `codebase` 去远程拉取了类文件。只要放置合法且带恶意逻辑的 class，就能进入真正的利用阶段。

## 6. codebase 在协议里怎么传递

第三篇文章重点回答了一个问题：`codebase` 到底是怎么混进 RMI 数据流的？

抓包分析显示，攻击场景里仍然有两条 TCP 流：

1. 本机与 RMI Registry 通信，例如 `1099` 端口。
2. 本机与 RMI Server 通信，例如动态端口 `64000`。

Registry 通信可以被 Wireshark 识别为 RMI/JRMP：

![Registry 通信流](/assets/images/web-note/web-note-029.png)

在 Registry 返回的数据中，可以解析出一个 `java.lang.reflect.Proxy` 对象。这个对象内部通过 `RemoteObjectInvocationHandler` 和 `UnicastRef` 描述真正远程对象的位置，也就是 RMI Server 的地址和端口。

![复制 Java Serialization 数据段](/assets/images/web-note/web-note-030.png)

连接真正的 RMI Server 后，数据包开头是：

```text
50 ac ed
```

其中：

- `0x50` 表示 RMI Call。
- `0xAC ED` 表示后面是 Java 序列化数据。

进一步用 SerializationDumper 解析可以看到，`codebase` 是通过 `[Ljava.rmi.server.ObjID;` 的 `classAnnotations` 传递的：

![SerializationDumper 中的 classAnnotations/codebase](/assets/images/web-note/web-note-031.png)

这意味着，即使没有标准 RMI 客户端，只要能构造或修改序列化数据中的 `classAnnotations`，就可以影响服务端看到的 `codebase`。

## 7. classAnnotations 的含义

Java 序列化时使用 `ObjectOutputStream`。它有一个可被子类重写的方法：

```java
protected void annotateClass(Class<?> cl) throws IOException
```

子类可以通过这个方法向序列化流中写入额外信息。反序列化时，对应逻辑可以读取这些信息并使用。

RMI 中的 `MarshalOutputStream` 就会把当前类对应的 `codebase` 写入 `classAnnotations`。因此，抓包里看到的 `classAnnotations` 并不是凭空出现的字段，而是 RMI 利用 Java 序列化扩展点写进去的类注解信息。

## 8. 安全启示

从这三篇文章可以得到几个审计和防护重点：

- **不要把 RMI Registry 暴露到不可信网络**，至少用防火墙限制来源。
- **避免依赖动态远程类加载**，不要启用不必要的 `codebase`。
- **保持 `java.rmi.server.useCodebaseOnly=true`**，避免信任远程请求携带的 `codebase`。
- **升级 JDK**，旧版本的默认行为更危险。
- **审计远程对象的方法面**，`list` / `lookup` 可被远程调用，暴露的危险业务方法可能被直接触发。
- **关注动态端口**，RMI Registry 只是入口，真实方法调用通常发生在另一个 RMI Server 端口。
- **监控 Java 序列化特征**，例如 `AC ED 00 05`、JRMP/RMI 流量、异常的远程 class 请求。

## 9. 总结

这三篇 RMI 文章的主线可以概括为：

1. RMI 调用不是简单的一条请求，而是先查 Registry，再连接真正的 RMI Server。
2. Registry 本身不能远程随意 `bind/rebind/unbind`，但 `list/lookup` 暴露后仍能泄露对象信息并扩大攻击面。
3. RMI 数据大量依赖 Java 序列化，远程对象引用、服务器地址、动态端口都在序列化数据中传递。
4. 历史 `codebase` 机制允许 JVM 在本地缺类时远程下载 class；当 `codebase` 可控且服务端配置不安全时，就可能形成 RCE。
5. `codebase` 本质上通过序列化流中的 `classAnnotations` 传递，背后是 `ObjectOutputStream.annotateClass` 这一扩展机制。

理解这条链路后，RMI 安全审计的重点就很清晰：先看 Registry 暴露和远程对象面，再看 JDK 版本、`useCodebaseOnly`、`SecurityManager`、远程类加载配置，最后结合抓包确认是否存在可控序列化流和远程 class 请求。
